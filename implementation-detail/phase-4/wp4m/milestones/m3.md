## Hypothesis and implementation

Retained M1b still spent a contemporaneous median 519,308,625 ns in full-create mapping/CAS. It encoded 5,284 raw chunks plus 86 mapping/root objects by first owning Bytes payloads and then independently hashing the same generated canonical bytes once to derive the `ObjectId` and again to authenticate the `(ObjectId, canonical)` pair before SQLite insertion. The M3 hypothesis was that those ownership copies and duplicate authentication hashes were material create-path work.

The accepted implementation is deliberately narrow:

- the existing core object codec now exposes a shared borrowed-slice Bytes encoder; it factors only the existing canonical header/length validation and produces byte-for-byte identical canonical encoding;
- full-create `FileBuilder` calls a private generated-Bytes insertion helper for raw chunks, mapping leaves/branches, and the file root;
- that helper computes the canonical `ObjectId` once, reuses that authenticated result for insertion, and still performs the original SQLite `INSERT OR IGNORE`;
- externally supplied `(ObjectId, canonical)` pairs continue through the original full identity validation, and a conflicting existing row is still re-read and fully authenticated before reuse;
- namespace and transition objects intentionally remain on the general path, so the two mapping-phase canonical authentication hashes covering their 119 canonical bytes remain;
- exact borrowed-encode, borrowed-source, reused-ID authentication, physical authentication-hash, and semantic authentication counters were added.

No batching was added because existing counters did not justify changing SQLite statement shape. No dependency, schema, database mode, WAL, worker/pool, cache/map, source staging, append/pack, object identity, receipt, publication boundary, or COMMIT count changed. M2's bounded reconstruction and M1b's private residual read helper remain unchanged. Same-middle was not affected and therefore was not run.

## COMMIT phase investigation and regressions

The COMMIT phase regressed reproducibly: median 116,510,959 → 152,995,834 ns, +36,484,875 ns / +31.315%, with 0/5 candidate wins. This is **not classified as noise**.

The implementation did not change COMMIT code, the transaction or timer boundary, the single-COMMIT protocol, object/SQL/BLOB counts, W/D, logical/apparent bytes, or canonical byte order/identity. The candidate reduced pre-COMMIT CPU work and reached the durability boundary sooner; a resulting shift in writeback work into COMMIT is plausible, but it is only an inference because host physical I/O and fsync observations are unavailable. The report therefore records the phase regression without asserting causality.

The gate classification follows the controlling text rather than an averaging argument. `../../mapping/logical-persistence.md:1455-1469` enumerates the protected file outcomes/resources as complete capture/full validation, range, same-count edit, forced `+1`, CPU, allocated-store delta, logical Q, and external RSS; it does not enumerate the additive COMMIT phase. `../../rollback/spec.md:390-424` separately requires COMMIT and other additive phase times as mandatory observations. COMMIT is therefore a mandatory diagnostic but not an independently protected outcome under the controlling contract. No new diagnostic rerun is needed because no phase-redistribution claim is being made.

The protected durable-capture outcome improved 7.057% with 5/5 wins, so the COMMIT increase is visible inside, and fully reconciled with, the faster durable total; no work or timer boundary was moved. Other non-controlling increases are system CPU +17.391%; reconstruction +0.814%; closure +0.032%. Total CPU, lifecycle, RSS, allocated-storage median, and all correctness/identity/storage-semantic guards pass. The COMMIT direction remains a real unresolved diagnostic, not noise and not evidence about M4.

## Big-O and bounded memory

M3 does not change asymptotic work: full create remains Θ(source bytes + references + canonical bytes), and the authoritative lifecycle still authenticates Θ(total canonical bytes + references). It is a constant-factor reduction: one fewer canonical hash for 5,370 locally generated objects and no raw-payload ownership copy before their canonical Bytes encoding.

Additional live semantic memory remains O(largest canonical object + K) with K=64 from M2 reconstruction. Q stays 33,611,532 bytes. There is no unbounded cache/map, source staging, append/pack, or new database/schema.

## Verdict

**PASS for the predeclared affected mapping/CAS metric.** Semantic correctness, identities, canonical bytes, trust-boundary authentication, exact equations, intended borrowed-encode/reused-ID counters, one-COMMIT publication, Q, and the contract-enumerated protected outcomes/resources passed. Mapping/CAS improved 20.899% with 5/5 balanced wins, exceeding the 5% + 4-of-5 affected-metric gate. M3 is accepted for M4 under that exact scope.

The throughput claim is limited to the affected mapping/CAS metric on this retained fixture. Complete lifecycle improved only 4.457% versus contemporaneous M1b and about 4.006% versus frozen c96, so there is no >=5% whole-lifecycle claim. Median durable capture is 104.840558 MiB/s (953.829334 ms); it is not a 200 MiB/s result and would require another 47.580% wall reduction to reach 500 ms. No profile qualification, selection, promotion, rejection, M4-prediction, or asymptotic-performance claim is made.
