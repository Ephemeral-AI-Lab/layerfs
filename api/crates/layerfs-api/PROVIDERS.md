# Sandbox runtimes in the SDK

Status: Current general guide. Native macOS is implemented and host-verified; Linux native was removed in 2.0 (#533 O27) and Linux runs local Sandboxes with namespaces; the Docker runtime is the default. `layerfs-sandbox` selects between them with the concrete `Runtime` enum; there are no provider traits.

`layerfs-sandbox` exposes `Runtime` (a deployment's choice: `Docker`, `MacosNative` (macOS only), `Namespaces` (Linux only); `LinuxNative` was removed in 2.0, #533 O27; Windows has none and runs the Linux build through WSL2 or a VM) and `Sandbox` (the launched owner of one Sandbox). `layerfs_sandbox::{Runtime, Sandbox}` re-export both; the crate root also re-exports the inputs and records they share (formerly `layerfs_sandbox::provider`, #527 step 9a). Backend-specific items are in `layerfs_sandbox::docker`, `::native` and `::namespaces` (formerly under `layerfs_sandbox::backend`, #527 step 9b); the providers, `Docker` and `HelperSpec` are also at the root. `ExecRequest` lives in the shared types layer; its Docker re-export remains compatible. `SandboxId` aliases the existing `ContainerId`, preserving encoded identities and records. The runtime layer has no daemon control dependency.

`Runtime::Namespaces(NamespaceProvider)` (Linux) runs each daemon in its own mount, PID and IPC namespaces and cgroup v2 directory, on a root overlaid on the Sandbox image; it is selected by `deploy.sandbox` `namespaces` (LAYERFS_SANDBOX; the former `deploy.sandboxBackend` `namespaces` under `deploy.sandbox` `native` is still mapped for one release, #527 step 11). `Runtime::MacosNative(..)` wraps `NativeMacosProvider::new(root)` (macOS only): Darwin process facts, the `mount` table and `umount -f`, the caller identity, inherited PATH and loopback NFS. Linux has no native runtime (#533 O27): `deploy.sandbox` `native` on Linux is refused `Unsupported` before any effect, naming `namespaces`, and no other backend is chosen in its place. A `native` record written by a Linux host before 2.0 is still reopened by its record (#529), so it can be stopped, deleted and reclaimed. The caller selects the kernel route in the daemon setup (`nfs` for host_process, `fuse` for namespaces and docker). Launch preserves the original single-attempt process lifecycle, native identity, inherited PATH, NFS environment and partial owner on failure. `inspect` reports exact process liveness; unknown exit/storage facts stay absent. There is no Windows runtime (#527 D2): Windows runs the Linux build through WSL2 or a VM. Records remain the Node binding's responsibility; runtimes neither scan directories nor infer project ownership. B8 list aggregation and doctor remain future work.

`SandboxApi::with_runtime(Arc<Runtime>)` and `create_provider_file(ProviderCreate, store, manifest)` (or `create(ProviderCreate, project)`) launch through the deployment's runtime and return `ProviderSandbox`, whose `runtime` field is the `Sandbox` handle. Both Docker (via `Runtime::Docker(DockerProvider)`) and native runtimes route through this single unified API path. `WorkspaceApi::exec` delegates ordinary execution through `sandbox.runtime.run(...)` with streaming stdout/stderr buffers, and `api.close` drains and removes instances via `sandbox.runtime.stop(1)` and `sandbox.runtime.delete()`. Before launch, API validates authentication identities, selected Store, command identity and local resource ownership: overlay and mount home must belong to the instance, Store must live outside it, and native listen uses dynamic loopback. API encodes daemon configuration, then uses the shared TCP/Noise/Hello and Store-install pipeline in `sandbox/connection.rs`. Failures retain their phase, original cause, runtime, control, observed status, installation acknowledgement and handshake work. No automatic retry or cleanup occurs in API.

`layerfs-node` builds a `Runtime` from `deploy.sandbox` (`docker` by default, `native` on Linux and macOS, `namespaces` on Linux; its `runtime.rs` is the one validator, mapping the former `deploy.sandboxBackend` and refusing a conflicting pair), keeps the launched `Sandbox` in its Sandbox state, and reads records, image, scratch directory and background-process tracking through it. Legacy deprecated forwarders (`SandboxApi::new(Docker)`, `SandboxCreate`, `ManagedSandbox`, `from_managed`, `internal::split/exec/control_managed`) remain removed.

The Store remains explicitly Disposable/WAL/OFF. Native macOS keeps #427's direct Store access without a worker; this refactor does not change persistence authorization or filesystem semantics.
