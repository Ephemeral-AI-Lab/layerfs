# Sandbox runtimes in the SDK

Status: Current general guide. Native macOS is implemented and host-verified; Linux native was removed in 2.0 (#533 O27) and Linux runs local Sandboxes with namespaces; the docker backend was retired by D-8 (layerfs-project#111), and the docker machine's worker container runs namespaces Sandboxes. `layerfs-sandbox-backend` selects between them with the concrete `Runtime` enum; there are no provider traits.

`layerfs-sandbox-backend` exposes `Runtime` (a deployment's choice: `HostProcess` (macOS only), `Namespaces` (Linux only); `LinuxNative` was removed in 2.0, #533 O27; Windows has none and runs the Linux build through WSL2 or a VM) and `Sandbox` (the launched owner of one Sandbox). `layerfs_sandbox_backend::{Runtime, Sandbox}` re-export both; the crate root also re-exports the inputs and records they share (formerly `layerfs_sandbox_backend::provider`, #527 step 9a). Backend-specific items are in `layerfs_sandbox_backend::host_process` and `::namespaces` (formerly under `layerfs_sandbox_backend::backend`, #527 step 9b); the providers and `HelperSpec` are also at the root. `ExecRequest` lives in the shared types layer. `SandboxId` aliases the existing `ContainerId`, preserving encoded identities and records. The runtime layer has no daemon control dependency.

`Runtime::Namespaces(NamespaceProvider)` (Linux) runs each daemon in its own mount, PID and IPC namespaces and cgroup v2 directory, on a root overlaid on the Sandbox image; it is selected by `deploy.sandbox` `namespaces` (LAYERFS_SANDBOX; the former refinement `deploy.sandboxBackend` is gone since both sides build `deploy`, layerfs-project#108). `Runtime::MacosNative(..)` wraps `NativeMacosProvider::new(root)` (macOS only): Darwin process facts, the `mount` table and `umount -f`, the caller identity, inherited PATH and loopback NFS. Linux has no native runtime (#533 O27): `deploy.sandbox` `native` on Linux is refused `Unsupported` before any effect, naming `namespaces`, and no other backend is chosen in its place. A `native` record written by a Linux host before 2.0 is still reopened by its record (#529), so it can be stopped, deleted and reclaimed. The caller selects the kernel route in the daemon setup (`nfs` for host_process, `fuse` for namespaces). Launch preserves the original single-attempt process lifecycle, native identity, inherited PATH, NFS environment and partial owner on failure. `inspect` reports exact process liveness; unknown exit/storage facts stay absent. There is no Windows runtime (#527 D2): Windows runs the Linux build through WSL2 or a VM. Records remain the Node binding's responsibility; runtimes neither scan directories nor infer project ownership. B8 list aggregation and doctor remain future work.

The launch facade lives in `layerfs-control` (`sandbox/launch/`, #536). `SandboxApi::with_runtime(Arc<Runtime>)` and `create_provider_file(ProviderCreate, store, manifest)` (or `create_provider_postgres(ProviderCreate)` for a PostgreSQL Store) launch through the deployment's runtime and return `ProviderSandbox`, whose `runtime` field is the `Sandbox` handle. Native and namespaces runtimes route through this single path. Commands run through the Sandbox's runtime (`sandbox/runtime.rs`), and `sandbox.close` stops and deletes the instance (`lifecycle.rs`; a record of the retired docker backend is forgotten instead, D-8); the test-only `SandboxApi::create`, `SandboxApi::close` and `WorkspaceApi::exec` were removed in #536 step 2. Before launch, the facade validates authentication identities, selected Store, command identity and local resource ownership: overlay and mount home must belong to the instance, Store must live outside it, and native listen uses dynamic loopback. It encodes daemon configuration, then uses the shared TCP/Noise/Hello and Store-install pipeline in `sandbox/launch/connection.rs`. Failures retain their phase, original cause, runtime, control, observed status, installation acknowledgement and handshake work. No automatic retry or cleanup occurs in it.

`layerfs-control` builds a `Runtime` from `deploy.sandbox` (`native` on macOS, `namespaces` on Linux; an unset or `docker` value is refused `Unsupported` since D-8; its `sandbox/runtime.rs` is the one validator), keeps the launched `Sandbox` in its Sandbox state, and reads records, image and scratch directory through it. Legacy deprecated forwarders (`SandboxApi::new(Docker)` and the Docker runtime itself, `SandboxCreate`, `ManagedSandbox`, `from_managed`, `internal::split/exec/control_managed`) remain removed.

The Store remains explicitly Disposable/WAL/OFF. Native macOS keeps #427's direct Store access without a worker; this refactor does not change persistence authorization or filesystem semantics.
