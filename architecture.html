LayerFS / target system architecture

One canonical filesystem. Many private operations.

Working state stays close to execution. Durable authority moves only at explicit version-control boundaries.

  • one portable filesystem meaning
  • one private workspace per operation
  • two physically distinct stores

The operation loop

Durable origin. Working execution. Exact acceptance.

A version is fetched into a nearby WorkingStore. An arbitrary tool runs in one private view. Its final filesystem effect becomes a canonical candidate, then one exact-head commit either wins or preserves a conflict.

Three presentations

One candidate root; different physical costs.

Direct, mounted and materialized operations share the same workspace lifecycle and canonical result. They deliberately retain different dirty representations and performance envelopes.

No path

Direct logical

Exact snapshot reads pin an immutable verified version without creating an Operation. Logical mutations use a private OperationWorkspace.

  • range reads touch intersecting extent paths and returned bytes
  • replacement and splice construct canonical changed spines directly
  • no native filesystem compatibility layer
Expected-local edit: replacement bytes + changed tree height

Private filesystem path

Mount / FUSE

Ordinary POSIX tools, Bash and package managers operate on logical extents through a kernel mount backed by the nearby WorkingStore.

  • bounded dirty ranges, namespace overlay and disk spool
  • no whole-file hydration, backing-tree materialization or capture
  • count-changing logical edits avoid ordinary native suffix rewrite
Syscall plane: WorkingStore only · zero Durable RPCs

Private real-file path

Materialize / APFS

Native macOS tools receive ordinary files. A quiescent capture converts the final physical result into the same canonical candidate.

  • changed-path refresh and clone/patch only when semantics are safe
  • supported metadata and hard-link closure round-trip exactly
  • different-length and unsafe cases report explicit FullFallback
Cold materialization and arbitrary capture may remain byte-linear

History and exact heads

Strict destinations; no generic merge graph.

LayerFS exposes filesystem version control, not search or agent-orchestration policy. Every accepted transition names an exact source, destination and expected head.

Commit

OperationCommit binds one OperationDelta, creates one OperationVersion and CASes one Branch head.

Forks

LayerBranchFork starts from a retained Layer. ChildBranchFork starts from an exact completed parent OperationRecordRef.

2

Merges

ChildBranchMerge targets only the immediate parent. LayerStackMerge targets the inherited originating LayerStack from any depth.

2

Rollbacks

BranchRollback and LayerStackRollback preflight affected leases before moving an exact head.

No cross-tree Branch merge

Sibling, cousin, grandparent-skipping, unrelated Branch and unrelated LayerStack destinations are rejected.

Source Branch survives merge

Its immutable fork-origin lease remains until explicit Branch drop, so later operations and repeated merges stay valid.

Target ownership

One owner for every policy.

The target migration moves existing mechanisms once, migrates callers and retires the former owner. New crate names do not count if old semantic implementations remain active underneath them.

Core boundary

  • no platform or native path
  • no Branch, LayerStack or Store policy

Storage boundary

  • no Working/Durable role switch
  • no duplicated schema or SQL
  • no cross-Store transaction

Workspace boundary

  • no version SQL
  • no synchronization authority
  • no shared sibling dirty state

Explicit synchronization

Accepted records cross. Live work never does.

The bridge carries immutable canonical identity and accepted version-control records. It does not replicate SQLite pages or serialize an active workspace.

Fetch / Push may carry

  • canonical ObjectIds and negotiated missing objects
  • accepted RootTransitions and version/delta records
  • exact heads, publication requests and typed receipts
  • bounded resume and retransmission state

Never synchronized

  • workspace paths, ownership markers or recovery directories
  • mountpoints, dirty maps, spools or native APFS files
  • processes, file descriptors or memory mappings
  • SQLite files, pages or database-local row IDs
