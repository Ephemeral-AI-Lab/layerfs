# Phase 2 finding: full-ingest performance

## Conclusion

The current Phase 2 rerun measures approximately **139–141 MiB/s** for a new
100 MiB full ingest on the current Mac. This is a fresh in-memory baseline, not
a hard limit and not a prediction of SQLite-backed LayerFS throughput.

Full ingest must remain O(file size): every new byte must be read, scanned for CDC boundaries, and incorporated into authenticated chunk identities. The available speedups are constant-factor improvements.

## Current 100 MiB rerun

The current diagnostic run uses the same B6 `S1-100` profile and partitions one
`LogicalFile::full_replace` operation into additive stages:

| Step | Time | Share |
|---|---:|---:|
| Source read / deterministic input generation | 217.377 ms | 30.20% |
| FastCDC scanner and callback bookkeeping | 283.534 ms | 39.39% |
| Full CAS publication | 218.745 ms | 30.39% |
| Logical-file manifest finalization | 0.065 ms | 0.01% |
| **Component total** | **719.721 ms** | **100.00%** |

The outer operation timer measured 719.727 ms. The independent uninstrumented
B6 rerun measured 709.422 ms, or approximately 140.96 MiB/s. The current
working baseline should therefore be treated as approximately 710–720 ms per
100 MiB, rather than the earlier 494.871 ms result. The earlier result is kept
below as historical evidence and is superseded for current planning.

The CDC-plus-CAS portion is:

```text
FastCDC: 283.534 ms
full CAS: 218.745 ms
combined: 502.279 ms ≈ 69.79% of the ingest
```

The run processed exactly 104,857,600 bytes, emitted 5,284 chunks, created and
stored 5,284 unique chunks, and stored 104,857,600 CAS payload bytes. The
resulting logical file matched the deterministic BLAKE3 source fingerprint.

This is a complete CAS-ingest path, but the CAS is the current in-memory
`InMemoryCas` backed by a `BTreeMap<ChunkId, Vec<u8>>`. It is not SQLite,
Postgres, APFS, or durable filesystem storage. The source is also generated by
`DeterministicReader`, not read from an on-disk file. The source stage therefore
includes deterministic generation and the evaluator's source fingerprint
update.

## What the 494.9 ms contains

The timer surrounds `LogicalFile::full_replace` in the evaluator:

```text
synthetic source generation
        │
        ▼
8 KiB reader buffer
        │
        ▼
FastCDC byte scan
        │
        ├── BLAKE3 chunk identity
        ├── CAS lookup
        ├── CAS byte copy
        └── CAS insertion
        │
        ▼
logical-file chunk-reference manifest
```

### 1. Synthetic source generation

The benchmark does not read a real APFS file. It generates deterministic bytes in memory.

For 100 MiB it:

- generates 100 blocks of 1 MiB;
- runs a byte-by-byte deterministic generator over all 104,857,600 bytes;
- copies the generated bytes into the CDC reader buffer in 8 KiB pieces; and
- updates a BLAKE3 source fingerprint on every reader call.

There are approximately 12,800 reader calls:

```text
100 MiB / 8 KiB = 12,800 reader calls
```

The source fingerprint update occurs inside the timed operation. This is useful for correctness, but it is not necessarily production work. LayerFS needs authenticated chunk IDs and a content root; it may not need a second raw-file BLAKE3 fingerprint.

### 2. FastCDC scanning

FastCDC scans all 104,857,600 bytes using an 8 KiB input buffer and processes the data byte-by-byte.

After the minimum chunk size, it evaluates approximately:

```text
(104,857,600 - 8,192) / 2 ≈ 52.4 million two-byte CDC steps
```

Each step performs:

- lookahead handling;
- GEAR-table access;
- rolling-hash updates;
- mask checks;
- chunk-boundary decisions;
- chunk-buffer writes; and
- occasional chunk callback invocation.

This is required for a new full ingest because the system must discover chunk boundaries. The macOS CPU sample also showed hot paths through `FastCdc::scan` and `Scanner::push`.

### 3. BLAKE3 chunk identity calculation

The benchmark created 5,284 unique chunks.

The reported `bytes_hashed` counter is 104,857,600 bytes, but the current CAS path hashes each new chunk twice:

```text
put_chunk(bytes)
    ├── chunk_id(bytes)       // first BLAKE3 hash
    └── put(id, bytes)
          └── chunk_id(bytes) // second BLAKE3 hash
```

For the 100 MiB full ingest:

```text
CAS chunk hashing:       100 MiB × 2 = 200 MiB
benchmark source hash:   100 MiB
total BLAKE3 input:      approximately 300 MiB
```

The `bytes_hashed` counter records one logical hash pass and therefore does not expose the duplicate internal hash.

The first safe optimization is to derive the `ChunkId` once in `put_chunk` and pass the already-authenticated ID to an internal insertion path. The public `put(id, bytes)` method can continue validating externally supplied IDs.

Removing the duplicate hash will not automatically make the complete operation 33% faster. It removes one of three BLAKE3 data passes, while wall time also includes CDC, source generation, allocation, copying, and CAS bookkeeping.

### 4. CAS ownership copy

For each new chunk, the in-memory CAS copies the bytes into owned storage. This is one additional 100 MiB memory copy distributed over 5,284 allocations.

The copy is required by the current borrowing shape: FastCDC owns one reusable chunk buffer, while the CAS must retain immutable bytes after the callback returns.

### 5. CAS map operations

Phase 2 uses an in-memory `BTreeMap` rather than SQLite.

For this ingest it performs approximately:

- 5,284 B-tree insertions;
- 5,284 key/value ownership operations;
- 5,284 chunk allocations; and
- no reuse hits, because the CAS is new.

This is not yet a durable-storage benchmark. SQLite adds statement binding, page-cache work, uniqueness checks, transaction handling, BLOB insertion, journaling, synchronous behavior, and possible fsync activity.

### 6. Logical-file manifest construction

After scanning, LayerFS sums the chunk lengths and builds the ordered chunk-reference list. This is metadata work over 5,284 references; it does not copy another 100 MiB of file content.

## What is outside the 494.9 ms

The following occur after the ingest timer stops:

- reading the logical file back from CAS;
- recomputing the correctness fingerprint;
- comparing the result with the expected source;
- writing `results.jsonl`; and
- writing `summary.md`.

The verification pass is intentionally outside the ingest timer. The source fingerprint itself is incrementally updated during the timed reader path, so the benchmark includes the checksum computation needed by verification but excludes the later verification read.

## Optimization order

| Priority | Change | Reason |
|---:|---|---|
| 1 | Remove duplicate `chunk_id` hashing in `put_chunk` | Eliminates an unnecessary full hash pass over every new chunk. |
| 2 | Split synthetic input generation from ingest timing | The deterministic generator is benchmark machinery, not APFS read performance. |
| 3 | Measure the source fingerprint separately | It adds another full 100 MiB BLAKE3 pass that may not be product work. |
| 4 | Profile and optimize the frozen CDC hot loop | CDC performs tens of millions of rolling-hash decisions. |
| 5 | Benchmark real APFS file reads | Establishes whether the source is CPU-bound, filesystem-bound, or both. |
| 6 | Benchmark SQLite batch insertion | Establishes actual durable-engine ingest cost. |
| 7 | Consider larger chunks only with edit benchmarks | Larger chunks reduce metadata and hash calls but can worsen small-edit reuse. |

## Benchmark decomposition completed

The ingest evaluator now reports four separate timings:

```text
source read/generation
CDC boundary scan
chunk hash + CAS publication
manifest finalization
```

This identifies whether the next optimization belongs in `layerfs-core`, the
benchmark source, or the future SQLite storage engine. The current breakdown
shows CDC as the largest single stage at 39.39%, followed by CAS publication at
30.39%. Together they account for 69.79% of the measured ingest.

## Final qualification

The correct current claim is scope-dependent:

> The post-optimization Rust path measures approximately 403.6 MiB/s median
> for a warm 100 MiB regular APFS file through FastCDC and full in-memory CAS
> publication.

The synthetic-reader diagnostic remains a separate benchmark and measures
approximately 226.1 MiB/s because it includes deterministic source generation
and its source fingerprint inside the timed region. Neither result is SQLite
durable ingest throughput.

## Fast-path optimization result

The frozen CDC profile was preserved, but the scanner was changed from a
byte-at-a-time callback state machine to a pair-oriented loop over the
contiguous chunk buffer. The input buffer is now bounded at the 32 KiB maximum
chunk size. Exact boundary, fragmentation, size-bound, and logical-file tests
remain green.

The fresh CAS path also now computes each new chunk ID once. The externally
supplied put(id, bytes) path still authenticates its supplied ID; only
put_chunk(bytes) avoids recomputing the same digest.

On the same 100 MiB synthetic run, the post-optimization diagnostic was:

| Stage | Time |
|---|---:|
| Synthetic source generation and fingerprint | 211.043 ms |
| FastCDC and callback bookkeeping | 113.189 ms |
| In-memory CAS publication | 118.068 ms |
| Manifest finalization | 0.047 ms |
| Total | 442.351 ms |

That is approximately 226.1 MiB/s including the synthetic source generator.
The source generator is benchmark machinery and is not an APFS file-read
measurement.

The new phase2-ingest-file evaluator creates and syncs the deterministic
source before timing, then measures a regular APFS file read through the same
FastCDC and in-memory CAS path. Three warm-file runs produced:

| Run | Total | Throughput |
|---:|---:|---:|
| 1 | 241.232 ms | 414.5 MiB/s |
| 2 | 247.795 ms | 403.6 MiB/s |
| 3 | 257.652 ms | 388.1 MiB/s |

The median is 247.795 ms / 403.6 MiB/s, with correctness true, 5,284 chunks,
and 100 MiB retained in the in-memory CAS. The environment artifact records
macOS arm64 on APFS:

eval/runs/phase2-ingest-file-s1-100-apfs/environment.json

The benchmark artifacts are:

- eval/runs/phase2-ingest-file-s1-100-apfs/summary.md
- eval/runs/phase2-ingest-file-s1-100-apfs-r2/summary.md

This clears the current 300 MiB/s target for the correctly scoped warm APFS
file-ingest path. The 500 MiB/s stretch target remains open: 500 MiB/s requires
200 ms for 100 MiB, so the current median needs another approximately 19%
reduction. The remaining measured cost is split almost evenly between the
optimized CDC loop and in-memory CAS publication. The next serious 500 MiB/s
work is an owned-chunk/pack-oriented CAS design or an equivalent backend
experiment; more BTreeMap micro-tuning is not justified by the neutral entry
experiment.
