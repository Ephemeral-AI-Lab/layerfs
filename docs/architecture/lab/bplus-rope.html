Fragmentation and safe coalescing

Adjacent slices may merge only when they reference contiguous bytes of the same payload object and policy permits a canonical local normalization.

Three adjacent Object A slices are logically contiguous and eligible for one local merge.

  • Never merge across different payload ObjectIds.
  • Never create a slice beyond the authenticated payload length.
  • Split/merge thresholds need an adversarial occupancy and history-growth study.
  • Periodic full-file “defragmentation” is not admitted on the edit critical path.

Identity conflict requires an ADR

A conventional B+ tree is normally history-shaped. Equal file bytes reached through different edit histories may have different operational roots.

Decision required
IdentityQuestion answeredRecommended role
PayloadObjectIdWhich canonical payload bytes?Hash of canonical payload object
FileStateRootWhich immutable operational structure?History-dependent B+ root allowed
ContentDigestWhich complete logical byte sequence?Independent optional semantic digest
CommitIdWhich history transition?Canonical commit record identity
InodeIdWhich stable filesystem object?Stable across content edits and rename

Current policy wants one content → one operational root. Selecting a conventional measured rope therefore requires an explicit identity/format/storage ADR—not a silent codec swap.

Required migration and evidence

The numbers justify an implementation arm, not format selection.

Not selected
  1. Freeze extent-slice and node canonical codecs with golden bytes/ObjectIds.
  2. Approve separate FileStateRoot, ContentDigest, CommitId, and stable InodeId semantics.
  3. Specify minimum occupancy, split/merge, root collapse, empty-file, and checked-total rules.
  4. Implement arbitrary-root 1/10/100/500 MiB reads and early/middle/late edit traces.
  5. Measure same-content/different-history roots, fragmentation, coalescing, and retained-history slopes.
  6. Prove exact-source publication, one transaction/COMMIT, recovery, Q/RSS/FD/temp bounds.
  7. Ship migration as a new profile; existing v1/v2 identities never change.
