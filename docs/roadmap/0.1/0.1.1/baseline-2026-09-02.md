### Root causes and patch candidate

The released initialization path rebuilt immutable directory and inode state
for each file, retained intermediate structural objects, checked large
candidate membership in small pages, and admitted at most 127 objects per
transaction. The candidate builds final directory and inode state once,
imports independent root directories in parallel with deterministic merge and
hard-link fallback, avoids empty-Store membership scans, and admits up to
8,191 objects or four MiB per initialization transaction. Canonical-equivalence
tests cover nested and empty directories, links, metadata, and a non-empty
Store fallback.

The released localized Commit constructed complete base and final manifests
and materialized a full captured namespace for a ten-byte edit. The candidate
uses the touched-inode fast path, preserves canonical nodes when topology is
unchanged, writes only differing ranges, batches inode/object reads, and keeps
the complete-manifest fallback for namespace, type, and link changes. The
100,000-file receipt contains only eight Commit candidates (about 12 KiB),
which directly demonstrates that Commit work is localized.

The remaining complete-lifecycle cost is exact per-file verification through
POSIX FUSE: the 100,000-file median is 77.904 of 85.564 seconds and the raw OS
supervisor records roughly 404,000 sent and 1,206,000 received messages per
sample. Further acceleration to bulk-I/O byte rates requires a matched
multi-file read/verification API or a packed-object/proxy contract; it is not
another compatible batching change inside the existing public FUSE lifecycle.

### Admission decision

- **Initialization: accept for v0.1.1.** The released behavior is a
  reproducible superlinear defect, while the candidate completes all four
  tiers, restores sub-ten-times 100-to-1,000 scaling, and retains the released
  canonical result.
- **Localized Commit: accept for v0.1.1.** The released path scales with the
  complete namespace for a ten-byte overwrite. The candidate restricts the
  successful fast path to the touched inode, retains the safe whole-manifest
  fallback, and holds Commit to 2.2--4.6 ms across 100--100,000 files.
- **Exact FUSE reopen: defer as a separate contract-design problem.** It is
  correct and scales below ten times per ten-times cardinality step, but its
  per-file POSIX request count—not initialization or Commit—now dominates the
  complete lifecycle. No incompatible SDK, canonical, daemon, or proxy change
  is included in this candidate.

## Post-admission performance audit — 2026-09-02

This section supersedes the earlier conclusion that exact FUSE reopen had no
compatible batching opportunity. Three independent read-only reviews traced
the current initialization, Commit, materialization, Store-read, FUSE, proxy,
and verifier paths. No reviewer edited the worktree; the primary agent applied
and measured each accepted change separately.

### Findings and retained changes

The dominant remaining duplicate operation was not file content reading. A
directory enumeration already materialized every child and computed its full
attributes, but the normal proxy response retained only `(node, kind, name)`.
The following kernel lookup therefore performed one redundant synchronous
host round trip per file to recover attributes that had just been computed.

The retained fix adds an additive internal `ReaddirPlus` request and
attribute-bearing response, implements standard Linux FUSE `READDIRPLUS`, and
negotiates `FUSE_DO_READDIRPLUS` and `FUSE_READDIRPLUS_AUTO`. Existing request
and response tags remain unchanged, normal `readdir` remains the fallback, and
the proxy populates both directory and attribute caches from the plus result.
A structural proxy test proves that one `ReaddirPlus` is followed by zero host
lookups for the returned children.

Initialization also built a reference graph in every parallel directory
buffer and again in the merged buffer, even though the final-only initializer
uses `finish_all_reachable` and never consumes that graph. Initialization-only
buffers now begin without reference tracking. Workspace and reconciliation
candidates retain reachability tracking. Canonical-equality tests, including
the cross-directory hard-link fallback, prove that the change affects neither
canonical bytes nor roots.

Finally, directory `..` resolution previously scanned every materialized node
for every directory. The Workspace now maintains the exact parent of each
directory across materialization, creation, rename, and reclaim. Parent lookup
is therefore constant time instead of `O(materialized nodes)`. A focused test
proves the parent and `..` entry before and after a cross-directory rename.

The expected edited fixture manifest is now computed during excluded setup,
and diagnostic formatting occurs after the final product timestamp. Exact
verification no longer regenerates and hashes the expected namespace inside
`reopen_verify_ns`.

### Rejected experiment

The audit hypothesized that verifier reader threads were redundant because the
proxy has one connection. A single-thread verifier was implemented and
measured separately. At 10,000 files it increased reopen from 3.809 seconds to
6.838 seconds and complete lifecycle from 4.395 seconds to 7.429 seconds. The
kernel/FUSE path obtains real pipeline overlap before the serialized proxy
exchange, so the experiment was reverted exactly. No worker subagent applied
production changes; the existing bounded verifier concurrency remains because
removing it is a measured 69% reopen regression.

### Complexity and remaining ceilings

For the registered fixture shape, initialization and verification are linear
in paths plus logical bytes, with logarithmic inode-table construction.
Directory-parent lookup is constant time, directory and inode reads are
batched, one duplicate synchronous lookup per file is gone, and localized
Commit remains bounded to the touched path.

One synchronous content-read exchange per opened file remains required by the
public POSIX/FUSE read. Read pin and unpin frames are retained because removing
them would break open-after-unlink semantics. Potential future constant-factor
work includes targeted per-directory payload prefetch and a canonical
single-chunk builder for known sub-8-KiB inputs; neither was bundled into this
A/B.

Two general-input ceilings remain outside the registered 100/1,000/10,000
shape: very large single directories still use incremental canonical leaf
construction, and candidate membership falls back to exact linear spill scans
beyond roughly 1.4 million unique IDs. Neither fallback is reached by the
10,000-file tier (about 80,000 objects) or the 100,000-file safety tier (about
808,000 objects). They must be addressed before claiming the same complexity
for a larger or differently shaped namespace.

### Exploratory SQLite write-path profile

An attached macOS `sample` run completed the init-only 100,000-file path in
6.103 seconds. Profiler attachment materially perturbed wall time, so that row
is nonterminal diagnostic evidence and does not replace the unprofiled median
of 4.502 seconds. The call graph locates work rather than measuring release
latency: the main thread spent about 64 percent of sampled time waiting for
source producers, about 17 percent in SQLite insert/step, about 6 percent in
SQLite commit, and about 13 percent in final/root and other work.

The profile and a read-only `dbstat`/VDBE inspection establish that SQLite is
write-bound, not canonical-payload-read-bound. The current rowid schema opens
both the `objects` table and `sqlite_autoindex_objects_1`; each unique object
performs a `NoConflict` primary-key probe, `IdxInsert` into the primary-key
index, and `Insert` into the table. Commit stacks reach `pwrite` through
`sqlite3PagerCommitPhaseOne`; they do not show a payload-`pread` hotspot.
