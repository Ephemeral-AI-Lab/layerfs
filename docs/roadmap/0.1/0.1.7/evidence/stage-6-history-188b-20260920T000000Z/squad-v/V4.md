## 3. The falsification that decides the question: the target is not a richer pool

**Task item 4 — "is it actually true that v0.1.6's producer ran at every commit?"**

**No.** Measured on the hash-matched retained Store:

    SELECT COUNT(*) FROM commits                                -> 17
    SELECT COUNT(*) FROM commits WHERE parent_commit_id IS NULL -> 1
    SELECT COUNT(*) FROM objects                                -> 51,722
    v0.1.6 lane-4 (CompactSmall) objects / canonical            -> 44,141 / 348,460,295

The 17 commits are one chain, and the lane-4 object set is **exactly** the 17-state
canonical set: 44,141 objects, 348,460,295 canonical bytes, **0 canonical
mismatches** on all 44,141. A producer that ran at every commit would have written
the intermediate versions of every path that changed inside a skipped span; the
stride-1 Store (157 states) holds **104,705 objects / 871,588,115 canonical**
(A4 §5). This Store saw 17 states.

**V1 reached the same conclusion by a different instrument**, which is why this is
now a two-instrument result rather than one squad's reading:

* v0.1.6's **base-distance histogram peaks at checkpoint gap 10 — the same as
  ours** (V1 §"FALSIFIED: nearest"), so its bases are no nearer than ours;
* **28,956 of the 33,310 objects both Stores base carry the same base identity**,
  and those frames are **byte-for-byte identical** (V1; my four-way join finds the
  same 28,956 of 33,310, §4);
* **100 % of both Stores' bases are inside the same 44,141-object set** (V1; I
  measured "v0.1.6 bases not present in our Store: 0").

So: **the two generations are comparable on this axis**, and the T1 report's
§"Why the gate does not close", point 1 — *"v0.1.6 ran its producer at every
commit. Its Store holds the intermediate versions, so its delta bases are the
nearest version of each path"* — is **false as stated**. Its bases can only come
from the pool ours can.

**Where the claim came from.** A4 *measured* something true: 31,108 tag-2 records
name a base in a strictly lower pack id, and packs are allocated in save order, so
those bases were "written by an earlier commit" — an earlier **selected** commit.
The step from *"an earlier commit"* to *"a producer that ran at every commit"* is an
inference, and it is the campaign's signature error for the fourth time: a
correlation read as a cause while the falsifying artifact sat unread on disk.

**Is it a modelling difference or a measurement artefact?** Neither. It is a
**declaration-rule difference inside an identical object set**, and V1 located the
rule exactly: the reference tree uses its declared predecessor when there is one
and consults its content-keyed similarity cache **only when there is none**
(`admission.rs:454`), while our default arm declares the same-path previous
version and nothing else. Measured consequences: the driver declares **29,192**
bases against the corpus's **29,122** first-appearance objects that have a same-path
version at the previous selected state (**computed**, §5.3 — agreement 0.24 %); the
product's per-save cache supplies the rest (34,439 − 29,192 = **5,247**, computed);
and **9,702** whole-file objects are offered nothing at all.

### 5.1 The two additivity corrections

**(i) L1 and L2 are the same bytes.** V1 located v0.1.6's rule as *"use the
declared predecessor when there is one; consult the similarity cache only when
there is none"*, and the T1 specification's R1b is *"move the index off the save
owner so it persists across saves"* — the same content-keyed 8-hash index, in the
product instead of the harness. **R1b is L1's product-side form, not a second
5.57 MB or a second 645,974 B.** The T1 report's framing of R1b as "the only
remaining form of R1" is therefore both right (it is the remaining *form*) and
misleading (it is not an *additional* lever).

**(ii) L1 and L1′ are the same bytes.** My own H-V4-1 (basename reuse) and V1's
similarity fallback both target the 2,594 objects with no same-path previous
version. V1's mechanism is better supported — it comes from per-object path
evidence over an oid→(checkpoint, path) map, where mine was a size-multiset
intersection (2,051 of 2,594 covered by the reuse population). **H-V4-1 is
withdrawn in favour of V1's mechanism**, kept only as the floor of the same lever,
and the tag split's 1,954 tag-2 records are reported as A4's provenance reading
rather than as proof of the route: a base reached by basename reuse *is* at a
different path, so it is consistent with V1's 94.5 % cross-path measurement either
way. **The experiment decides it, and the experiment has now been run.**

**(iii) L4 is additive, from the source.** `encoding/delta/select.rs`: the
`Chunk` arm reads `advisory.first()` and **never consults `input.candidates`**,
while `candidates.insert` fires only under `lane == PackLane::WholeFile`
(`:250-257`, `:288`, `:312`, `:336`). The chunk lane and the whole-file index
are disjoint object sets — 1,098 records against 44,141 — so the cursor and L1
cannot compete for the same bytes.

### 5.2 L5, measured on a copy — and the overlap warning (N4)

The T1 report correctly says the `base_object_id` **column** cannot simply be
dropped. It then treats that as the end of the story. It is not: **the column's
*representation* is the lever, not its existence.** Measured by copying
`/tmp/confirm` to `/tmp/v4_probe.sqlite` (deleted after the run), building two
alternative `objects` tables in the same file and reading dbstat:

| objects table variant | bytes | saving |
| --- | --: | --: |
| as shipped — `base_object_id BLOB` (32 B) | 4,124,672 | — |
| `base_ref INTEGER` (the base's ordinal) | 2,957,312 | **−1,167,360** |
| `base_ref INTEGER`, no `object_role` | 2,887,680 | **−1,236,992** |

52,032 rows, 35,356 carrying a base. The residual 1,474,560 − 1,236,992 =
**237,568 B** is 310 more rows than v0.1.6 plus btree fill; not claimed as a lever.
**N4:** v0.1.6 pays the same 32 bytes *inside each lane-4 record* (35,904 × 32 =
1,148,928 B inside its own lane total), so removing our column by decoding the
record is a wash against v0.1.6 and a loss against L5. **L5 is the only net win.**

### 5.3 Why L9–L11 are not levers

* **L9, ordinary lane (+344,456).** Object sets differ by construction: we store
  6,793 lane-1 objects / 10,405,534 canonical; v0.1.6 stores 4,847 / 2,013,482 in
  lane 1 **and** 1,636 / 8,033,879 in lane 6. Only 202 oids are common. The route
  is closed by design: `select.rs:221-239` returns `encode_full` for all ten tree
  roles **before reading the advisory** — *"Tree roles are ordinary framed bytes …
  never choose a payload delta base."* Measured corroboration (A2 §8.3): 0 bases
  across 5,048 tree objects. **The two metadata lanes net +122,917 B on 310 more
  objects; there is nothing here to win.**
* **L10 (+118,252).** Page rounding of the pack blobs and 42 more header/directory
  bytes per pack.
* **L11 (+90,112).** 249,856 vs 159,744 B: our `metadata_value_groups` 90,112 +
  its autoindex 28,672 + `store_policy` 4,096 + schema 4,096 + 30 freelist pages,
  against 15 one-page tables and 17 freelist pages. Table count, not payload.

## 6. The experiment, run

**V1's recommendation, implemented harness-side with zero product lines.** Two
switches were added to `ops/history.rs` (harness-only; **production LOC delta 0**):

* `LAYERFS_HISTORY_FALLBACK_PREDECESSORS=1` — the same-path previous version
  remains the whole list when it exists; the cross-save `SimilarityIndex` is
  consulted **only when it does not**. One variable against the default arm: the
  *condition*.
* `LAYERFS_HISTORY_FALLBACK_CANDIDATES=N` — the width (default 2, the ordered
  arm's own; 4 is `MAXIMUM_ADVISORY_PREDECESSORS`). A second, separate variable.

    B=core/benchmark/fs-bench-pro-storage-content/target/release/fs-bench-storage-content
    C=/Users/yifanxu/Ephemeral-AI-Lab/deepseek-history-data

    # arm 1 — the default, already on disk (T1's best)
    LAYERFS_CONSTRUCTION_WORKERS=1 LAYERFS_HISTORY_ADVISORY=1 $B --case history-stride10 --out /tmp/confirm --corpus $C

    # arm 2 — V1's recommendation, one variable
    LAYERFS_CONSTRUCTION_WORKERS=1 LAYERFS_HISTORY_ADVISORY=1 \
      LAYERFS_HISTORY_FALLBACK_PREDECESSORS=1 $B --case history-stride10 --out /tmp/v4_fb --corpus $C

    LAYERFS_CONSTRUCTION_WORKERS=1 LAYERFS_HISTORY_ADVISORY=1 \

   against 2. The campaign has now measured "more candidates is worse" three times
   (R0's four slots, the full producer, and this), and the mechanism is the same
   each time: a wider candidate list deepens chains and converts gains into
   ineligibility. The counters show the shape of it precisely — the 4-candidate arm
   is **better on every counter** (`prefix_selected` 37,821 vs 37,797,
   `ineligible` 2,185 vs 2,585, `no_candidate` 7,296 vs 7,326) **and 172,032 B
   larger**. More coverage, worse bytes: the same signature as the R0 four-slot
   falsification.
4. **The driver's own depth account is not the fix** (N5). `DEPTH_LIMIT=5` with the
   fallback arm removes the ineligible refusals almost entirely (2,585 → **236**)
   and is **4,521,984 B worse** than the same arm unlimited: it suppresses 3,745
   *good* declarations to avoid 2,349 bad ones, and `no_candidate` rises to 8,558.
   The driver's depth figure is an over-estimate by its own admission, so it cannot
   be used as the selector. **L7 therefore has no harness-side fix**, which is why
   it is listed as a product question.

## 9. The verdict

**(a) The gate is reachable, by a costed path — but not on harness changes alone.**
Steps 1–3 above: **48,372,843 B = 0.9809x**, margin **942,997 B (1.91 %)**. Ordered:
**L1 (harness, done, 0 product lines) → L4 (C1 cursor, ~180 LOC, no amendment) →
L5 (objects row grammar, amendment).**

**(b) The T1 target of 47,048,435 B is not reachable on that path.** 48,372,843 is
**1,324,408 B above it**. The only identified route is recovering the **2,055,169 B
chain-depth regression** (L7), which is a product depth-accounting question and has
no identified mechanism. With L7 recovered the Store models at **46,317,674 B =
0.9392x**, which would clear the target by 730,761 B — **but that is a hypothesis
about a product fix, not a path.**

**(c) #188 should NOT be closed as not achievable.** It should be **re-scoped**:
its gate is reachable, its target is not, and **the Stage 7 diagnosis should be
withdrawn** — it is falsified by the target's own commit count and by V1's
base-distance histogram, independently.

**(d) What the owner should rule, in order of what unblocks the most:**

1. **Keep the fallback arm and re-run it as a registered diagnostic.** It is
   harness-only, already implemented, and worth **6,402,048 B** — more than every
   other lever combined except the cursor. It should not be left as a switch.
2. **Authorise the C1 chunk cursor (L4).** V2 reads it as needing no amendment; it
   is still a `core/crates/layerfs-content/src/` change. **It is on the critical
   path: without it the Store stays 293,995 B above the gate.**
3. **Rule on L5's trade** (1,236,992 B of Store for one page read per chain edge).
   It is the lever that closes the gate.
4. **Open the chain-depth regression as its own item (L7, 2,055,169 B).** It is the
   only thing standing between the measured path and the T1 target, and it is a
   product question: 489 objects lose a base because their base became ineligible.
5. **Re-price the T1 target, or state the design that beats v0.1.6 by 1.32 MB.**
6. **Keep #185 deferred** (V2: 1.429 % measured) and **keep `history-stride1`
   unoptimised.**

**A stride3 confirmation is still required for any gate claim, and none exists.**
Nothing here is a gate claim; it is a reachability argument with one new measured
arm.
