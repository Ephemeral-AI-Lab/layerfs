## 1. The two halves, re-separated — plus a third thing the task merged

The brief asks me to separate #185's **cursor** half from its **cross-role** half.
Doing that surfaced a third item the brief merges into the cursor half, and it is
the one that decides the recommendation.

### 1.1 The paper's own labels (measured, source read)

`core/docs/architecture/deferred/01-size-transition-delta-hints.md` §3:

| # | Claim | Label |
| --- | --- | --- |
| 11 | A usable cross-role base at the transition | **deferred** |
| 12 | Core should consult the cursor per emitted chunk | **proposed** |

and §4 step 3 gates **only** the cross-role half on an owner amendment
("*For the cross-role half only: an owner amendment is required first*"), while
step 1 — *"Implement the cursor in `core/` behind the existing four-slot type,
with no storage-format change"* — carries no gate. **Confirmed: the cursor half is
proposed, not deferred. Nothing needs un-deferring; the available action is to
implement it.**

### 1.2 The cursor half is a large → large mechanism, not a transition mechanism

Confirmed independently and from the source, not from the earlier assessment:

- `core/crates/layerfs-content/src/file/view.rs:62-67` — `file_state()` returns
  `Some(FileState)` for a chunked base and `None` for a whole-file base.
- `core/crates/layerfs-content/src/file/edit/apply.rs:132-140` — dispatch is
  `Some(state) ⇒ replace_chunked`, `None ⇒ stream_combined`.
- `stream_combined` (`apply.rs:397-416`) is therefore reached **only** when the
  result is chunked and the base is a whole-file object: the `small → large`
  crossing, i.e. the cross-role half's population.

**So `build_streaming`'s hardcoded `None` serves the CROSS-ROLE half on the
`apply_edits` route.** The cursor half's `apply_edits` producer is
`replace_chunked`, and its gap is a *different* one: `apply.rs:309-314` computes
`predecessor = rightmost_payload(left)` — **one id, shared by every chunk of the
replacement** — which is exactly the gap chapter 14 §14.2 documents.

### 1.3 …but on THIS lane neither route is used, and `build_streaming` is the producer

The history driver does not call `apply_edits`. It calls `construct_bytes` for
every changed path (`core/benchmark/fs-bench-pro-storage-content/src/ops/history.rs:1479`,
`:1535`; the reason is written at `:1510-1512`). That route is
`content.rs:207 construct_bytes` → `content.rs:246-247` → `content.rs:297
construct_chunked` → `content.rs:305 build_streaming` → `build.rs:326
push_chunk(chunk, None, consumer)`.

**On this lane, therefore, `build_streaming` is the ONLY producer for all 1,098
chunk records, and it offers `None` to every one of them.** The brief's item 4 is
**correct for this lane** and wrong for the `apply_edits` route — the two are
different code paths that happen to share `build_streaming`.

### 1.4 Why R0's declaration cannot reach a chunk — measured, structural

R0 is harness-side (`ops/history.rs:1569-1648`, applied at `:1706-1718`): it
builds `bases: BTreeMap<ObjectId, Vec<ObjectId>>` keyed by `new_root =
constructed.get(&changed.path)` and attaches the previous version's root to
**that object only**.

For a chunked file, `construct_chunked` returns
`root = mapping::emit_file_state(...)` (`content.rs:316-317`) — the **FileState**
object. So on a chunked path:

1. the advisory is attached to the **FileState**, and
2. `select.rs:229-239` short-circuits every tree role (`FileState`,
   `ExtentLeaf`, …) to `encode_full` **before any candidate is read** — *"Tree
   roles are ordinary framed bytes … never choose a payload delta base."*

**The declaration on a chunked file's root is therefore inert, and the 1,098 chunk
objects are offered nothing.** This is not a coverage problem that a better
producer fixes: **even a perfect Stage 7 correspondence layer, declaring the exact
nearest previous version of every path, cannot put a candidate in front of a chunk
object.** The per-chunk correspondence is a C1 cursor, and it does not exist.

| --- | --: |
| `delta.prepared_full` | 45,239 |
| `delta.trials` | 34,488 |
| `delta.no_candidate` | 10,732 |
| `delta.work_exceeded` | 19 |
| `delta.full_losses` | 49 |

**Arithmetic (computed, residual 0):** `trials + no_candidate + work_exceeded` =
34,488 + 10,732 + 19 = **45,239 = prepared_full**. ✓

Objects: 44,141 whole-file + 1,098 chunk = 45,239. The chunk lane holds **1,098
objects, all tag 0, and 0 of 1,098 carry a `base_object_id`**. Therefore:

    whole-file: 34,488 trials + 9,634 no_candidate + 19 work_exceeded = 44,141  ✓
    chunk:           0 trials + 1,098 no_candidate                    =  1,098  ✓

`select.rs:346-357` shows `probe` is the only path that increments `trials`,

branch: not one delta trial has ever been attempted for a chunk in this Store.**

This matters for the recommendation: the chunk lane is not a lane where trials
*lose*. It is a lane where **no trial exists**, and the missing piece is a
producer, not a selector, a codec, an index or a budget.

## 5. What would the cursor buy NOW? — the bound, and which input is modelled

Frame ratios, all **measured**, headers excluded so the arithmetic is comparable:

| frame class | raw | frames | ratio |
| --- | --: | --: | --: |
| core, chunk FULL (current Store) | 22,032,441 | 5,685,272 | **3.87535x** |
| v0.1.6, chunk FULL | 8,604,206 | 2,376,287 | 3.62086x |
| v0.1.6, chunk PREFIX | 13,428,235 | 1,550,476 | **8.66072x** |

Headers are measured from the grammar: FULL = 5 B/record (tag u8 + raw_len u32);
PREFIX = 37 B/record (the same plus the 32-byte base id).

**Note a sub-result that helps us: core's FULL encoder is 7.0 % better than
v0.1.6's on the same lane** (3.87535x vs 3.62086x). Any transplant of v0.1.6's
selection must carry that across, or it understates the saving.

### 5.1 Bound A — **the measured anchor: 1,737,621 B**

Not a model. It is the byte difference between two real selections over
byte-identical raw payloads (§2). A cursor that reproduced v0.1.6's reach on this
corpus would land here.

### 5.2 Bound B — the transplant model: **1,893,759 B (est)**

v0.1.6's *selection* (650 PREFIX / 448 FULL), core's *ratios* on both classes:

    PREFIX  13,428,235 / 8.66072 + 37 × 650 = 1,550,476 + 24,050 = 1,574,526
    FULL     8,604,206 / 3.87535 +  5 × 448 = 2,220,204 +  2,240 = 2,222,444
    framing (core's 131 groups)                                  =     4,916
    lane                                                          = 3,801,919
    saving = 5,695,678 − 3,801,919                                = 1,893,759

**Modelled input:** the *assumption that core's PREFIX ratio equals v0.1.6's
8.66072x*. The selection is measured; the ratio is imported from the other tree.

### 5.3 Bound C — the unreachable ceiling: **2,576,371 B (est)**

E3's input, the 63 in-place edits, at the current Store's ratios:

    R = 18,274,423 B ;  avg chunk = 22,032,441 / 1,098 = 20,066.0 B ;  k = 910.7
    FULL   = R / 3.87535 + 5 k  = 4,715,527 + 4,554 = 4,720,103
    PREFIX = R / 8.66072 + 37 k = 2,110,041 + 33,696 = 2,143,732
    saving = 2,576,371

**Modelled inputs, all three of which favour the saving:** uniform chunk size; no
chunk-level reuse inside the class (removing that assumption gives **2,317,644 B**);
and **every one of the 911 in-place emissions winning its single trial** — which is
exactly what v0.1.6, *which had the cursor*, did **not** do (650 of 788, 82.47 %).

**So Bound C is not reachable and is reported only to show what the excess over
Bound A is:** 2,576,371 − 1,737,621 = 838,750 B is the trials a real cursor loses.
Bound A is the honest number.

### 5.4 The bound, stated once

> **The cursor is worth at most 1,737,621 B on this corpus (measured: v0.1.6's own
> selection on byte-identical raw payloads), and a core implementation with the
> same reach and core's better FULL encoder would land near 1,893,759 B (est).
> It cannot exceed ~2.58 MB, and only by winning trials v0.1.6 lost.**

## 6. Access cost — bytes per read, never time

The cursor walks the base's mapping tree forward. On the current Store, **measured**
from `canonical_by_role`:

    extent-leaf   92 objects / 53,368 canonical  =   580.1 B each
    file-state    92 objects /  9,752 canonical  =   106.0 B each
    per base file                                =   686.1 B

Each chunked content's mapping is **a single extent leaf** (92 file-states, 92
extent-leaves). So:

| | value | label |
| --- | --: | --- |
| base-mapping reads per cursor | 2 nodes = **686 B** | measured sizes |
| 63 in-place events × 686 B | **43,223 B** | est (one cursor per edit event) |
| amortised over 1,098 chunk emissions | **39.4 B / emission** | est |
| amortised over the 788 reachable records | **54.9 B / record** | est |
| share of the lane's 22,032,441 B of payload | **0.196 %** | est |

Bounds: forward-only, **≤ 4,096 descriptors** then `exhausted` (reference
`read.rs:395-455`); exhaustion is not an error. Core already has the pattern —
`RangeCursor` (`mapping/read.rs:361-428`) memoizes mapping pages in the caller's
`PageCache`, and `apply_edits` already creates **one** `PageCache` per operation
(`apply.rs:67`), so a cursor can share it. **No timing claim is made.**

## 9. Recommendation, with arithmetic

### 9.1 The deciding numbers

| number | value | what it decides |
| --- | --: | --- |
| cursor, measured anchor | **1,737,621 B = 20.603 %** of the residual | the price of the cursor half |
| #185 cross-role ceiling | **≤ 476,317 B = 5.648 %**, of which **120,490 B = 1.429 %** measured | #185 stays deferred |

| owner amendments needed | **0** | why it can start now |
| base-mapping reads | **39.4–54.9 B per chunk record**, 0.196 % of lane payload | the access cost |
| bytes bought per production line | **≈ 9,600 B/line** | the trade |

### 9.2 Answer to the question asked

**Should #185's cursor half be un-deferred and implemented NOW?**

**It cannot be "un-deferred" — it was never deferred.** Claim 12 of the paper's own
ledger labels it *proposed*; §4 step 1 requires no amendment; #185's revisit
condition 2 names the cursor landing in `core/` as the *precondition* for
revisiting #185 itself. The available action is **implement it**, and the arithmetic
says **yes**:

- it is **20.603 %** of the residual — the second-largest single lane after the
  whole-file lane's 4,890,202 B (58.0 %), and the largest item that needs **no
  owner ruling and no format change**;
- it is **producer-only**: 0 lines in C2, 0 schema lines, 0 storage-format change,
  and the consumer already exists;
- it does **not** compete with R1b or the whole-file lane — different role,
  different lane, and `Candidates` only ever indexes the whole-file lane
  (`select.rs:250-257`), so the two are additive;
- it is a change that **cannot make things worse by much**: a cursor that reaches
  nothing yields exactly today's Store.

**But three things must be said in the same breath:**

1. **It does not close the gate.** Residual after: **6,696,043 B, 1.13578x.**
   Necessary, not sufficient.
2. **Do not cite it as an #187 / #188 remedy for the whole-file lane.** It touches
   the whole-file lane for **0 B**, exactly as E3 found. The T1 report's "levers
   that remain are R1b and the `base_object_id` column" is *incomplete*, not
   wrong: it omits a 20.6 % lane that its own scope never reached.
3. **The T1 report's diagnosis — "the absence of the layer that R0's producer lives
   in, which is Stage 7 (#172), unbuilt" — is a whole-file-lane diagnosis and does
   not extend to the chunk lane.** §1.4 shows R0's declaration is *inert* on a
   chunked file: the only object it can name is the FileState root, and tree roles
   never take a payload base. **Stage 7 would not move the native lane by one
   byte.** The missing piece is a C1 cursor.

### 9.3 What I would order

1. **Implement the cursor** (chapter 14 §14.4) as a producer-only C1 change, behind
   an external test that pins the four cases §14.6 names. Then **measure** it — the
   1,737,621 B is a reference-tree number, not a `core/` number.
2. **Leave #185 deferred.** 1.429 % measured does not buy an amendment.
3. **Keep the negative arms.** Nothing here changes R1a's, R0's or the
   full-producer falsification.

## 10. Negative results, kept

- **The chunk lane has never run a delta trial.** 0 of 1,098 chunk objects carry a
  base; `trials` reconciles to the whole-file lane exactly (44,141). "The chunk
  lane's deltas lose" is false — none is attempted.
- **R0/R1a/R2/R3 moved the native lane by 0 B.** `/tmp/base187` and `/tmp/r2`
  report identical record bytes (5,690,762) and framing (4,916).
- **`build_streaming`'s `None` is not the cursor half's `apply_edits`
  producer.** On `apply_edits` it serves `small → large` — the cross-role half.
  Conflating the two would have put a cross-role fix behind a no-amendment gate.
- **Bound C is unreachable.** The 63-in-place-edit input gives 2,576,371 B only if
  all 911 emissions win; v0.1.6, with the cursor, won 650 of 788 (82.47 %).
- **The 91 changed chunked contents sum to 24,492,001 B, not 22,032,441 B.** A
  2,459,560 B (10.043 %) residual that any per-class byte model must handle; the
  exact chunk-reuse explanation is H-V2-1, not proven per object.
- **The cursor cannot reach 42 of the 105 chunked path-states** — 28 have no chunked
