## Shared constants (the scratch-ceiling arithmetic)

All four items share these figures; every path:line verified at this tree.

| Fact | Value | Citation |
| --- | --- | --- |
| Page ceiling | 8,192 B | `core/.../filesystem/limits.rs:10` |
| Operation scratch lease | 4 MiB = 4,194,304 B (caller-declared, default this) | `limits.rs:41`, `filesystem/input.rs:58,73` |
| Per-child batch reserve | `MAXIMUM_PAGE_BYTES + associations` = 8,192 + 88 = **8,280 B** (associations = `size_of::<ObjectId>()`(32) + `size_of::<(ObjectId,Vec<u8>)>()`(56)) | `sorted/page.rs:225-233` |
| One decode slot | directory ≈ 60.2 KiB (`bytes*3 + (bytes-44)/11*48`), inode ≈ 32.7 KiB | `sorted/format.rs:304-306,523-525` |
| Demand ceiling | 4,096 ids/wave (both sides) | `filesystem/objects.rs:20`, `layerfs-storage/src/policy.rs:80` |
| Directory branch fanout | (8,192−44)/(2+name+32): 1-byte names → ≤**232**; fill min 3,277 B (`limits.rs:34`) → ≥~12 at 255-byte names | `format.rs:290-298` |
| Inode branch fanout | 64–127 | `limits.rs:30-32` |

**The 4,096 demand ceiling is unreachable for in-memory page waves**: 4,096 ×
8,280 = 33.9 MiB ≈ 8.1× the whole 4 MiB lease. Full-width reserve fits only for
W ≤ (4,194,304 − 60,652)/8,280 ≈ **499**; W=512 (4,239,360 B) never fits even in
an otherwise-empty budget, so any constant above ~499 is fiction that the
narrowing loop (`page.rs:229-257`) would silently clamp every time. The largest
useful width is the widest real demand: one branch page's children ≤ 232.
**Proposed constant: `BATCH_CHILDREN` 32 → 256** (power-of-two, covers every
legal branch page in one wave; full reserve 256×8,280+60,652 ≈ **2.08 MiB**,
leaving ≥ 2 MiB for the live spine). Recursion caveat: `batch_children`'s lease
is held while the merge descends into children (`merge.rs:248-296`), so a
parent's 256-batch plus a child's own 256-batch (2×2.08 MiB) cannot coexist —
the inner call narrows. That is the honest trade: top level one wave, deep
levels narrower; the loop makes it graceful, never a refusal.
