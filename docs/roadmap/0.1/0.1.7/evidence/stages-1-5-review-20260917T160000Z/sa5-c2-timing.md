## 2. Findings, severity ordered

**F1 (High) — A persisted tree may contain direct references to objects that were never persisted, and the composition gate does not detect it.**
- Trigger: any caller-supplied `InodeUpdate` whose `content_root`/`metadata_root` was not emitted/stored (the normal "file content supplies completed roots" contract, `filesystem-tree.md:138`).
- Observed: the inode value embeds both roots (`object/inode_leaf.rs:121-140`), but a level-0 inode leaf carries no declared references (`sorted/format.rs:362-366` → `page.rs:353`), so C2's dependency check (`cas/dependencies.rs:47-70`) cannot see them; `cas/save.rs:55-73` admits the leaf, `owner.rs:875-912` acknowledges it. The product's own C2 target does exactly this: `tests/filesystem_pipeline.rs:185` (`synthetic("pipeline/root-meta")`, never emitted), and `tests/support/filesystem.rs:288-289` for 1,200 entries.
- Expected: per `stages-1-5-reviewer-handoff.md:165`, "a reported root must have its required objects persisted"; per `admission-and-persistence.md:69`, a "Stored" result means required dependencies are satisfied.
- Consequence: an acknowledged Store can hold a filesystem root whose inode table references absent objects; a later read fails with `ObjectMissing` (`cas/read.rs:74-77`) far from the save that promised success.
- Smallest remedy: either declare an inode leaf's value roots in `FinalizedObject::references` so the existing dependency check covers them, or make the caller-authorized-roots exclusion explicit in `filesystem-tree.md` and add one target that saves a tree with a dangling supplied root and asserts the documented outcome. Do not add a new validation pass.

**F2 (Medium) — `measure_filesystem`, the Stage 5 harness, does not select the operation its `--case` names.**
- Trigger: `--mode c2|pipeline|--case inode-update|hardlink-move|subtree-remove`.
- Observed: `--case` only picks `entries` ∈ {0, 32, 200} (`measure_filesystem.rs:174-179`); the C2 body saves the same fixture and the pipeline body always applies an empty change set (`:288-291`), so those cases are byte-identical work under three different labels.
- Expected: `stages-1-5-reviewer-handoff.md:470-471` — "an example's `--case/--mode` actually selects the claimed operation".
- Consequence: receipt/report rows named "C2 inode-update" and "integrated subtree-remove" (`stage-5-completion-report-20260917.md:111-112`) are mislabelled; no correctness loss (the work is real), but the case names cannot be quoted as covered workloads.
- Smallest remedy: print the same supplied-object/fixture banner `measure_edits.rs:411-422` prints, or map the case names to real change sets.

**F3 (Medium) — The integrated Stage 5 row is neither a bounded handoff nor a storage read-back.**
- Trigger: `measure_filesystem --mode pipeline`.
- Observed: all emitted objects are collected in an in-memory `Bag` before `begin_save` (`:302-317`), and `readback` reads that `Bag` (`:347-353, 361-377`); the Store is never reopened. The banner nevertheless prints "construction, bounded handoff and save acknowledgement" (`:336`).
- Expected: `stage-5-verification.md:81-82` (bounded handoff, read-back reported separately) and the handoff's "filesystem root -> C2 finish -> reopen/list/read" (`stages-1-5-reviewer-handoff.md:187`).
- Consequence: the recorded 17,534,000 ns / 90,583 ns pair does not evidence the handoff or a reopen; those proofs exist only in the C2 targets (`filesystem_pipeline.rs:268-339`, `filesystem_failure.rs:165-191`).
- Smallest remedy: route the pipeline row through `SaveHandoff` and reopen the Store for its read-back (the pattern is already written at `measure_components.rs:275-296`).

**F4 (Medium) — A trace node per accepted object contradicts the admission contract and can silently clip.**
- Trigger: a save of more than ~500 objects with a recorded scope.
- Observed: `SaveOperation::accept` always creates `storage.batch` under the caller's per-object node (`store.rs:257-263`); the C2 receipt is 19 nodes for 8 objects. `admission-and-persistence.md:538` says "Do not add a node per object, syscall or delta edge". Above `MAX_NODES = 1024` the detail is dropped and the ancestors are marked incomplete (`recording.rs:144-157`, `203-206`).
- Expected: coarse, object-count-independent detail for a persistence row.
- Consequence: large C2 rows lose their inner detail; `tests/timing.rs:163-175` asserts non-incompleteness only for one small case, so the property is not held for the workload class the C2 lane exists for.
- Smallest remedy: keep one accept-scope for the whole batch (or one per wave) instead of one per object, or amend the contract line with the owner's reason.

**F5 (Low/Medium) — The Stage 5 harness cannot report a clipped trace.**
- Trigger: any clipped report from `measure_filesystem` or `filesystem_timing_c1`.
- Observed: both print `report_nodes N` only (`measure_filesystem.rs:285`, `filesystem_timing_c1.rs:375`); `is_incomplete()` is never consulted, unlike `measure_edits.rs:299-311` and `measure_pooled.rs:193-203`, which fail the run.
- Expected: `stage-5-verification.md:85-86` — a clipping report marks itself incomplete and a clipped row is never `PASS`.
- Consequence: the two collected Stage 5 rows are honest (7 and 19 nodes, unclipped), but the harness cannot honour the rule for a bigger case.
- Smallest remedy: copy the `is_incomplete()` check into both Stage 5 examples.

**F6 (Low) — The C1 comment "A `--mode c1` row opens no database" is not true of `measure_filesystem --mode c1`.**
- Trigger: `measure_filesystem --mode c1`.
- Observed: `Store::create` runs unconditionally at `:183-191` before the mode dispatch, creating and opening a SQLite Store. The collected C1 receipt row instead used `filesystem_timing_c1` (`receipt.json`), which links no storage crate.
- Expected: the verification contract's own sentence (`stage-5-verification.md:84`).
- Consequence: wording only — the measured region is unaffected (the Store is created before `Instant::now()`); a reader who trusts the sentence about this binary is misled.
- Smallest remedy: create the Store only in the modes that use it, or correct the sentence to name `filesystem_timing_c1`.

**F7 (Low) — `LAYERFS_TRACE` remains a product-path debug branch.**
- Trigger: `LAYERFS_TRACE` set in the environment.
- Observed: four env-gated `eprintln!` sites inside the update body (`update.rs:197,215,312,332`), one per observed binding; no consumer in the repository reads the variable.
- Expected: `core/AGENTS.md:44-54` product source contains product code only; diagnostics belong in telemetry/evidence.
- Consequence: unbounded stderr work proportional to changes inside a timed operation; a second reviewer reached the same site independently (`sa3-refs-ordering.md:185`).
- Smallest remedy: delete the four branches before acceptance.

## 3. Non-findings (checked, no gap)

- Owner-declared deferrals (not findings): the complete-operation comparison stays `NOT_RUN` per `stage-5-verification-addendum-20260917.md:82-90`; no cold-cache or whole-process memory claim is made.
