## The fix, and what it deliberately does not do

An identity waiting in an unfinished group has no row yet. The owner now seals the
group holding it on demand, so the ordinary verified storage path answers for it:
the duplicate occurrence goes through the same byte comparison against stored bytes
that a cross-batch duplicate uses, and a same-save read reads the row it just
created. The alternative -- retaining the canonical bytes of every waiting member --
was implemented first and rejected: a group is bounded by its *framed* bytes, so a
record that compresses to tens of bytes can carry 32 KiB of canonical data, and a
64 KiB group could then retain tens of MiB. Sealing costs packing granularity for
the caller that needs the identity and nothing else; an identity is sealed at most
once, because afterwards its row exists and the membership lookup finds it.

## Bounds of this evidence

- Deterministic workloads, single observation per arm, no timing or memory claim.
- The harness lives outside the repository and is reproduced by the copy above.
- The F14 workload stores 3 distinct objects into 2 packs; that number is a
  property of this workload, not a packing-efficiency claim.

## Why the retain-first design was rejected, measured

The first implementation kept the canonical bytes of every member waiting in an open
group and served both the duplicate and the same-save read from that copy. A group is
bounded by its *framed* bytes, so that retention is not bounded by the group target.

Workload (harness-compressible.rs, copied here): 4 MiB of zeros with a 4-byte counter
stamp every 64 KiB, which is ordinary compressible content with distinct chunks.

```text
$ /tmp/rev-harness/target/release/compressible
file 4 MiB of zeros with a 4-byte stamp every 64 KiB
objects=130 distinct chunks=128 chunk canonical bytes 32789..32789
inserted=66 reused=64 packs_created=2 pack_appends=1
canonical bytes retained if waiting members kept their payloads: up to 4196992 bytes per group
```

64 distinct 32,789-byte payloads (4,196,992 bytes) can be waiting in one open group of
this workload, against a 64 KiB group target that bounds framed bytes only. The
retain-first design was therefore replaced by sealing the group on demand; the
fix that ships retains no payload at all.

## A failed seal inside a read is terminal

Sealing is a preparation write, so `SaveOperation::read_batch` runs it under the save's
terminal boundary: a lost write lock or a failed commit at that moment leaves an
unproven transaction state, and the one terminal boundary resolves it exactly as it
does for `accept`. The query that follows the seal is a query, and a missing object is
a caller error rather than a broken save, so it does not terminate anything. This path
is not induced: reaching it needs an engine or transport failure, which product source
cannot inject. It is a coverage gap recorded as such, not a passing test.
