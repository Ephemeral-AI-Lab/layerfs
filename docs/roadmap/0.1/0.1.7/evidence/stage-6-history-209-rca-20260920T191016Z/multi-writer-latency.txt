**Both writers completed in every round. Zero `OwnershipUnavailable`.**

Reading it. 1,290 of the 1,306 calls are sub-millisecond; the 50 that are not are the
group seals, each of which widens the step and rewrites a whole pack body. The step a
second writer cannot enter is therefore **p50 0.4 us / p95 ~4 ms / p99 ~11 ms / worst
observed 37.6 ms**. The one writer that owns no lock at that moment pays that step as
its own latency: `pair` mean 400-413 us against `solo` 120-134 us for the same calls.

## The step cannot simply be widened: it fails, it does not wait

`maybe_commit` was given an explicit, default-1 lever
(`LAYERFS_STORAGE_COMMIT_EVERY`, measurement-only, removed after this round) that
commits the save's transaction once per N steps instead of once per step. That is
exactly "hold the arbitration lock across more appends".

    COMMIT_EVERY=1        both writers finish, 0 OwnershipUnavailable, 5/5 rounds
    COMMIT_EVERY=8        FAILED in round 0
    COMMIT_EVERY=64       FAILED in round 0
    COMMIT_EVERY=100000   FAILED in round 0

    panicked: called `Result::unwrap()` on an `Err` value:
    CleanupFailed { original: OwnershipUnavailable, cleanup: OwnershipUnavailable }

The failure is `OwnershipUnavailable`, not a longer wait. SQLite admits one writer per
Store file and the product's `busy_timeout` is **zero** by declared profile, so a
second writer arriving while a transaction is still open is refused immediately; its
own cleanup then needs the lock it cannot get and the save fails as a cleanup failure.
**A widened step does not cost the second writer time, it costs the second writer the
save.** The step boundary is therefore not a tuning parameter: it is the largest unit
of work that can be serialized without destroying the capability the model bought.
