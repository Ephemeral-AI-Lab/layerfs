## Findings and design implications

Real packing improves bulk upload and sequential transfer strongly in this local
collection. Scattered pack range reads transfer far fewer bytes than whole-pack
reads, but they are slower than individual-object reads with the same128 requests.
That cost must remain visible in any architecture decision. Future locality-aware
batching/cache experiments need their own prospective cases; none was added here.

SQLite FULL/fullfsync costs about14–16ms per publication under this exact profile;
COMMIT dominates, while SQL row work is smaller. With one serialized writer gate,
adding clients increases total waiting rather than aggregate publication throughput.
This supports local runtime Workspace metadata and a short global publication
transaction for modest Commit rates, but does not establish high-rate global
catalog capacity. Durable batching/sharding or another catalog engine would be
separate design experiments, not hidden tuning of these rows.

MinIO independent upload request lifetimes overlap and aggregate throughput rises
with1/2/4 clients. Independent metadata publications all finish through the
application writer gate; same-Branch competitors yield exactly one winner; native
SQLite contention yields BUSY without retry. Indexed bounded namespace operations
keep the same statement counts at10k/100k population. Deep path resolution uses
one indexed query per component, not a repeated whole-path scan.

## 2. Metadata publication and synchronization cost

Each selection performs eight successive publication transactions. The synthetic
catalog registers an already-uploaded pack key and locator rows, inserts a Commit
row and conditionally advances the Branch generation in one transaction.
No physical MinIO upload or canonical Commit construction is part of this group.

Runtime profile: MEMORY journal/synchronous OFF/fullfsync OFF.
FULL profile: DELETE journal/synchronous FULL/fullfsync ON.
Both: cache_size=-512,mmap_size=0,busy_timeout=0,temp_store=FILE,foreign_keys=ON;
effective settings are in each raw receipt. No WAL or product-profile change.

| D-1024-runtime-v2 | 13.238 | 1.655 | 1.028 |
| D-1024-full-v2 | 127.990 | 15.999 | 113.248 |

For128 locators, FULL SQL COMMIT totals109.098ms of113.836ms overall. For1024

## 3. Concurrency, conflicts and native contention

Uploads: eight256KiB synthetic bodies per client, one producer/connection each.
First signed PUTs pause after64KiB transmission until all clients arrive, then
complete192KiB and receive successful provider acknowledgements. Recorded arrival
and ACK intervals prove incomplete request lifetimes overlap; they do not prove
simultaneous server CPU execution or distributed capacity.

owner commits once; second reads the accepted state afterward. Total phase

converted into a fallback.

## 4. Population and path-depth query laws

Prepared closed SQLite masters for each shape are integrity/count qualified,
SHA256 sealed and independently copied as bytes into writable case databases.
Setup took0.721010s once. Copy is not an APFS clone or a cold claim. Performance
uses128 indexed points (flat) or eight full path resolutions (deep), one128-row
keyset page and one rename/delete. Rename visibility has a separate untimed
SELECT before deletion; exact final rows and unchanged master seals are verified.

| Case | Point/path phase ms | Point/path statements | One page ms | Rename ms | Delete ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| S-flat-10000-v2 | 1.428 | 128 | 0.234 | 0.189 | 0.095 |
| S-flat-100000-v2 | 1.360 | 128 | 0.228 | 0.220 | 0.104 |
| S-deep-10-v2 | 0.785 | 80 | 0.194 | 0.180 | 0.109 |
| S-deep-270-v2 | 16.170 | 2160 | 0.197 | 0.174 | 0.201 |

Flat populations10,000 and100,000 each use128 point statements, one keyset statement
and three mutation/visibility statements. EXPLAIN plans use indexed SEARCH,
including parent/name and primary-key mutations, with no full nodes scan.
The fixed point keys are `(37*k) mod population`, k=0..127: both flat cases
therefore visit the first4,700 names. This is a controlled bounded lookup set,
not a uniform sample of the entire population; the keyset page covers names
5,000..5,127.

Depth10/270 each has100,000 flat entries plus its path chain. Eight resolutions
issue80/2160 actual SELECTs, exactly eight times depth. Per resolution:
0.098ms versus2.021ms; elapsed ratio20.59 for depth ratio27, while query count law
is exactly linear in components. Two observations do not prove all asymptotic
latency laws, and a candidate backend schema does not fix the existing#289 path.
Depth270 does not enlarge the current product's supported path profile.
