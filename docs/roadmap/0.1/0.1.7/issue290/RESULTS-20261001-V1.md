## Decision supported by this collection

The local observations support continuing the SQLite-metadata / grouped-MinIO-
object investigation. They expose substantial per-request cost for tiny objects
and per-transaction cost for metadata. They do not yet justify replacing the host
or selecting a global durable catalog design. This is a single observation of
small fixed workloads, not a scaling law or a stable speed guarantee.

Keep namespace listing and point lookup in indexed SQLite metadata, and evaluate
sealed immutable aggregates for small content in MinIO. Avoid treating one S3
request per 1 KiB file as an efficient bulk transport. The first pass does not
measure actual LayerFS pack construction, CAS negotiation, compression, delta
base reads or range extraction.

## MinIO observations

| Case | PUT | GET | LIST | Timed HTTP requests |
| --- | ---: | ---: | ---: | ---: |
| M-directory-10000-v1 | — | — | 496.596 ms | 11 |
| M-big-64m-v1 | 186.178 ms | 38.598 ms | 2.897 ms | 3 |
| M-tiny-1024-v1 | 844.210 ms | 393.107 ms | 39.072 ms | 2050 |
| M-grouped-1024-v1 | 13.006 ms | 4.180 ms | 2.080 ms | 9 |

The 64 MiB object uploaded at
**343.76 MiB/s** and downloaded at
**1658.10 MiB/s**. GET follows its own PUT;
the download number must not be described as cold disk throughput. Input is a
seeded synthetic memory body streamed in 64 KiB pieces, not a filesystem read.

The tiny and grouped cases both carry 1 MiB of logical content. Grouping reduced
PUT requests from 1,024 to four and observed PUT time by **64.91x**;
observed GET time fell by **94.05x**. These ratios describe this collection
only. The grouped bodies are synthetic aggregates, not valid LayerFS packs.
The request counts include LIST. Listing 10,000 keys required 11 actual page
requests and delivered **20,137 entries/s**.
S3 prefix listing is not POSIX directory behavior.

Per-object PUT/GET times for the tiny case were
824.4 / 383.9
microseconds on average over the single bulk run. These are arithmetic averages,
not sampled percentile latencies.

| Case | Insert metadata | Indexed points | Keyset listing | Insert transactions | Database size |
| --- | ---: | ---: | ---: | ---: | ---: |
| S-directory-10000-v1 | 41.684 ms | 1.262 ms | 4.271 ms | 79 | 888,832 B |
| S-tiny-1024-b1-v1 | 20.965 ms | 1.123 ms | 0.582 ms | 1024 | 110,592 B |
| S-tiny-1024-b128-v1 | 4.446 ms | 1.138 ms | 0.713 ms | 8 | 110,592 B |
| S-big-index-4096-v1 | 9.654 ms | 1.983 ms | 1.943 ms | 32 | 237,568 B |

The directory case has 10,000 name/inode pairs, 128 point lookups and 128-row
keyset pages. Its insertion rate was
239,899 metadata pairs/s;
listing rate was 2,341,600 entries/s.
Each pair requires two inserted rows. These are Python binding + SQL + fixture
identity costs under the declared runtime profile.

For 1,024 pairs, batching reduced transaction count from 1,024 to eight and
observed insertion time by **4.72x**. This does not establish individual
POSIX-call atomicity or the cost of durable global publication.

The range-index case stores 4,096 locators for one logical 64 MiB file; no file
payload BLOB is inserted. It performs 256 indexed point lookups and 33 keyset
queries, including the final empty query. File metadata cases rename 128 names
in one transaction; exact phase data is in the raw receipts. Deletion time is
separate cleanup, not credited to the operation phases. Empty database files
retain their allocated size; deleting rows does not promise filesystem shrinkage.

## Acquisition failure and correction

The original archive was truncated at 25,557,715 bytes and failed SHA256 and gzip
end-of-stream validation. It was retained, not extracted. A registry HEAD
reported 36,896,726 bytes. An explicit request for the missing byte range returned
206 with exact `Content-Range: bytes 25557715-36896725/36896726`. The repair copied
the original into a separate provider root, appended only that range and verified
the complete frozen bottle hash before extraction/startup. No automatic retry,
provider substitution or third-party modification occurred.

Evidence: [original failure](evidence-20261001-v1/provider-preparation/original-acquisition-failure.json),
[range acquisition](evidence-20261001-v1/provider-preparation/acquisition.json).
The original artifact remains under ignored local outputs. Private credentials
and startup logs were excluded from publication; public evidence was checked
against the generated access key and secret for accidental inclusion.

## Remaining questions and next stage

- Durable global catalog: freeze the actual transaction/durability policy and
  measure its publication cost separately. Runtime synchronous OFF results cannot
  answer this question. No WAL or product durability change was made here.
- Actual chunks: separately freeze 8/16/32 KiB object selections and actual sealed
  pack operations, including range reads and locator lookups, before collection.
- Scaling: this pass has one directory population and one large-file size. It
  neither proves nor refutes quadratic scaling, including the #289 workload.
- Concurrency: competing uploads, same-key conditions, SQLite writer contention,
  branch-head compare-and-swap, upload pins and cleanup races are unrun.
- Cache/resource: all numerical rows remain INELIGIBLE; native heap peaks, macOS
  file-cache residency and physical I/O are unavailable. RSS snapshots establish
  no bounded-memory or healthy-progress guarantee.
- CDC, CAS negotiation, canonical metadata, compression, delta dependencies,
  consistency/crash custody, daemon/FUSE and large-to-small transitions are
  outside this pass. #287/#288 product work and qualification are unaffected.
- Mount-stage tools (pjdfstest, smallfile, mdbench, fio, fsstress, fsx) are unrun.
