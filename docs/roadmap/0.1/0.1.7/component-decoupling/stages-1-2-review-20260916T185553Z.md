## 2. Findings

Severity: **S1** contract/data-safety, **S2** real functional or resource defect,
**S3** robustness or quality, **S4** cleanup.

### F1 — S1 (demonstrated): an unrelated reader can read unfinished-save output

*Location.* `core/crates/layerfs-storage/src/cas/store.rs:145-171`
(`Store::read_batch`), interacting with `cas/owner.rs:307-345` (`maybe_commit`).

*Behaviour.* `Store::read_batch` opens a fresh connection, captures
`ceiling = SELECT COALESCE(MAX(pack_id), 0)`, and only then applies that ceiling
to every acquired location. The ceiling therefore means "the highest pack that
existed when this read started", not "the highest pre-save retained pack". A save
that commits a bounded transaction early — `maybe_commit` fires after 8,191 rows
or 4 MiB − 1 canonical bytes — has already published those packs to any other
connection, so a read that begins afterwards observes them.

*Trigger and evidence.* Reviewer experiment
[`experiment-visibility-and-cost.txt`](../evidence/stages-1-2-review-20260916T185553Z/experiment-visibility-and-cost.txt):

```text
constructed 274 objects, root e880487484d286db017e0d4dc93d6ab61bce0b0ccf986185b44f7a4dede75490
UNRELATED READ WHILE SAVE OPEN: visible=1 ceiling=19 packs_read=1
mid-save early commit observed: true
save outcome: inserted=274 commits=6 packs=23
```

The save was still open (no `finish` had run). A second connection read a chunk
belonging to it, with that read's own ceiling (19) already above the pre-save
baseline. The existing owner-bound test
(`pack_locator.rs::same_save_reads_see_accepted_objects_before_the_finish_barrier`)
covers only the permitted direction; `grep -rn "VisibilityCeiling\|ceiling"
core/crates/layerfs-storage/tests` returns nothing, so the restriction is
untested as well as unimplemented.

*Impact.* A reader can obtain a root, or a required dependency, that belongs to a
save which later fails; `cleanup::abandon` then deletes those packs, leaving the
reader with a dangling root. Equally, "private" early output is not private, so no
later Workspace or history layer can rely on this boundary.

*Smallest recommended fix.* Make the read ceiling a save boundary rather than a
snapshot: capture the pre-save baseline in the owner, publish it inside the save's
first transaction (a one-row active-save marker holding the baseline pack id and
an owner token), remove it at acknowledgement or cleanup, and have ordinary reads
read `COALESCE(marker.baseline_pack_id, MAX(pack_id))` as the ceiling — ideally in
the same statement that already computes it, so no extra round trip is added.
*Invariant that must remain true:* the ceiling is captured once per read and never
moves mid-read, and a same-save read on the owner connection stays unrestricted.

### F2 — S1 (source-derived, not reproduced): the baseline and pack cursor are read outside the write transaction

*Location.* `core/crates/layerfs-storage/src/cas/owner.rs:97-113`
(`MutationOwner::acquire`).

*Behaviour.* `lookup::highest_pack_id(&connection)` runs **before**
`write::begin_immediate(&connection)`. Its value becomes `baseline_pack_id` (the
cleanup authority) and `next_pack_id` (the placement cursor). Between the
unlocked read and the lock another writer can commit a pack:

```text
B: MAX(pack_id) -> 4                  no lock held
A: commits pack 5, releases the lock
B: BEGIN IMMEDIATE succeeds
B: baseline = 4, next_pack_id = 5     stale
```

Two consequences follow. (a) `write::insert_pack(pack_id = 5, ..)` fails on the
primary key, so the save fails for a reason the ordering created. (b) That failure
is a definite pre-COMMIT failure, so `finish::terminate` calls `abandon`, which
runs `DELETE FROM objects WHERE pack_id > 4` and
`DELETE FROM object_packs WHERE pack_id > 4` — deleting writer A's retained packs.
The window is not negligible: `CompressionWorkspace::new()` (2 MiB) and
`DecompressionWorkspace::new()` (1 MiB) are allocated between the read and the
lock, and `storage.begin` measures 5.25–8.22 ms inclusive in the debug smoke runs.

*Evidence and honesty about it.* Reviewer experiment
[`experiment-race.txt`](../evidence/stages-1-2-review-20260916T185553Z/experiment-race.txt) ran one long writer and one
contending writer for 15 s in a release build: **45,055 successful acquisitions,
0 stale baselines, 0 accept collisions**, 3 legitimate `OwnershipUnavailable`
contentions, and all 39 of writer A's objects readable afterwards. The hazard is
therefore **source-derived with a reasoned reachability argument, not
reproduced**, and is not reported as a demonstrated defect.

*Smallest recommended fix.* Move the `highest_pack_id` read after
`write::begin_immediate`, so baseline and cursor are established under the
ownership the design requires. Two lines plus a comment.

### F3 — S2: a mid-save `maybe_commit` failure can leave the save's own committed rows behind

*Location.* `core/crates/layerfs-storage/src/cas/owner.rs:314-330`.

*Behaviour.* `maybe_commit` commits and then re-acquires:

```rust
write::commit(&self.connection)?;          // succeeds; transaction_open stays true
self.counters.commits += 1;
write::begin_immediate(&self.connection)?; // can fail if another writer took the lock
self.transaction_open = true;              // not reached on failure
```

If re-acquisition fails, `transaction_open` is stale-`true` while no transaction
exists. `abandon` then calls `write::rollback`, which fails ("no transaction is
active") and maps to `UnknownOutcome`; `cleanup_attempted` was already set, so the
deletion pass never runs. The rows acknowledged by the successful COMMIT remain in
the Store, unreferenced by any caller, and the caller sees `CleanupFailed`. No data
loss, but a definite failure leaves owned unpublished data behind.

*Reproduction.* Not reproduced; it needs the exact COMMIT→BEGIN interleaving.
*Smallest fix.* Set `transaction_open = false` immediately after a successful
`commit`, before attempting `begin_immediate`.

### F4 — S2: one full canonical-bytes copy per stored object per wave

*Location.* `core/crates/layerfs-storage/src/cas/save.rs:47` —
`let object = objects[index].clone();`

`FinalizedObject::clone` deep-copies the owned canonical `Vec<u8>`, and the
original stays alive in `objects` for the rest of the loop, so every newly stored
object is copied once before encoding. This contradicts the handoff's "Move the
existing allocation; no copy solely for the boundary".

*Fix.* Take `&FinalizedObject` in `MutationOwner::offer` (it only borrows
`canonical()`, `role()`, `id()` and `references()`) and drop the clone. The
duplicate-occurrence comparison already borrows. Saving: one canonical-bytes
memcpy per inserted object per save. *Invariant preserved:* byte comparison,
`Availability` bookkeeping and `prepared` indexing are unchanged.

### F5 — S2: the read path is a point-call loop whose fixed cost dominates

*Location.* `core/crates/layerfs-content/src/file/mapping/read.rs:175`
(`reader.read_canonical(id)` per mapping node) → `object/access.rs:23` (the
one-ID-batch default) → `cas/store.rs:145` (`Store::read_batch`: new connection,
pragma profile, 1 MiB decode workspace).

*Measured* (release, n = 1 each;
[`experiment-visibility-and-cost.txt`](../evidence/stages-1-2-review-20260916T185553Z/experiment-visibility-and-cost.txt)):

```text
read_batch(ids=1)  ->  1 value,  packs_read=1, elapsed=0.466ms  (0.466ms/call)
read_batch(ids=24) -> 24 values, packs_read=3, elapsed=1.077ms  (0.045ms/id)
8 separate single-id read_batch calls: 2.117ms total (0.265ms each)
```

A grouped call for 24 identifiers costs 1.077 ms where 24 point calls cost roughly
6.4 ms; each point call pays about 0.27–0.47 ms of fixed cost. Tree traversal
issues one such call per visited page.

*Fix.* Two independent small cuts: (a) let `descend` request all overlapping child
ids of a branch in one `read_canonical_batch` call instead of one call per child;
(b) size the decode workspace from `ZSTD_estimateDCtxSize()` (256 KiB, not 1 MiB)
and the encode workspace from the profile estimate rather than the 2 MiB maximum.
*Invariant preserved:* demand order, per-page structural validation and the wave
release rule.

### F6 — S3: the read ceiling is unreachable in single-writer use and untested

`Store::read_batch` reads the ceiling and the locators from the same connection in
immediate succession, so `pack_id > ceiling` cannot hold except under the F1 race.
`StorageError::VisibilityCeiling` is therefore effectively dead in normal
operation and has no test. This is a coverage statement; fixing F1 gives it real
meaning.

### F10 — S2 (attribution): no C2 work appears under `content.traverse` in the integrated report

*Location.* `layerfs-storage/examples/measure_components.rs:295-300`
(`StoreReader::read_canonical_batch`), interacting with
`layerfs-content/src/object/access.rs:12-29` (the provider trait takes no scope).

*Behaviour.* The provider cannot attribute work to the caller's tree, so the
example measures each provider call under its own `Timing::disabled` recording and
discards it. In the chunked pipeline run, `content.read > content.traverse`
reports **22.13 ms** with **no storage children**, although that span performs
every locator query, pack read and decode of the read: 22.13 ms of 85.22 ms (26%)
of the integrated operation is labelled as C1 traversal but is C2 work.

*Fix.* Either give the provider call a scope parameter (a real interface change)
or have the integrated caller wrap each provider call itself. Until then the
integrated tree must not be read as a C1/C2 split.

### F12 — S2, **found after the review was first written and since fixed**: the per-field envelope ceiling was missing

*Location.* `layerfs-content/src/object/codec.rs` (`canonical_len`,
`decode_bytes_object`), against `layerfs-content/src/limits.rs:5` in the reference.

*Behaviour.* The frozen format applies **two** independent size guards to a
bytes-role object. The candidate implemented only the first:

```text
payload_len <= MAX_OBJECT_BYTES - HEADER_LEN   (16 MiB - 9)   candidate: present
value_len   <= MAX_OBJECT_FIELD_BYTES          (8 MiB)        candidate: MISSING
```

*Evidence.* Two harnesses linking the real crates by path (the reference one
read-only), retained in
[`experiment-envelope-field-limit/`](../evidence/stages-1-2-review-20260916T185553Z/experiment-envelope-field-limit/README.md):

```text
value  8.0 MiB       candidate ACCEPTED        reference ACCEPTED
value  8.0 MiB + 1   candidate ACCEPTED        reference ENCODE REJECTED
value 12.0 MiB       candidate ACCEPTED        reference ENCODE REJECTED
value 16.0 MiB - 14  candidate ACCEPTED        reference ENCODE REJECTED
```

The divergence was two-sided: the candidate could *produce* a canonical object the
reference cannot produce, and *accepted* one the reference rejects. It is an
envelope and public-API contract divergence plus a foreign-bytes acceptance
difference. It was **not** a Store-corruption path: no role produces anything near
8 MiB, and a hand-built 12 MiB object is refused one step later by
`owner.record_body` (`GROUP_LIMIT` 65,536), so nothing oversized could reach a
Store through the product API.

*This was a review miss.* `object_identity.rs` asserted payload-overflow rejection
(`u32::MAX`) but never probed the 8 MiB field boundary, so criterion 1.7 below was
first recorded PASS too generously. The record has been corrected rather than
rewritten: the verdict for the reviewed tree `69d34cbe` stands as INCOMPLETE on
that criterion, and the fix is recorded separately.

*Fix (landed after the review, at the owner's request).*
`MAX_OBJECT_FIELD_BYTES = 8 MiB` was added to `layerfs-content/src/policy.rs` and
applied in `canonical_len` (covering every encoder) and `decode_bytes_object`
(covering hand-built and foreign bytes), with a boundary test at 8 MiB (accepted)
and 8 MiB + 1 (rejected on both encode and decode). The post-fix harness output is
identical to the reference on all five value sizes; see
[`output-after-fix.txt`](../evidence/stages-1-2-review-20260916T185553Z/experiment-envelope-field-limit/output-after-fix.txt).

### F11 — S4: minor accounting and reporting inaccuracies

- `owner.rs:196-230`: `PendingGroup::framed_len` accumulates
  `framed_length([record])` per record, over-counting group framing by `4n − 4`

- `SaveOperation::read_batch` clones pending bytes twice (once into `pending`,

### 7.2 Boundedness verdict: **INCOMPLETE**

Every individual owner is bounded, and C1 construction and C2 save state are
bounded by test. Three qualifications keep this from a PASS.

1. **No aggregate reservation.** Entries 1–14 are individually bounded, but
   nothing checks the sum before allocating. No code reserves the producer
   footprint plus the consumer footprint before a large object is admitted, which
   the handoff requires ("Reserve the supported producer footprint before
   allocation"; "Use the existing resource owners, count and byte limits"). The
   singleton path *works* at the largest supported size, so this is a missing
   checked total rather than a demonstrated overflow.
2. **Entry 4 is O(mapping depth), not constant.** Depth is capped at 32 by the
   frozen grammar, but calling the frontier constant would be wrong.
3. **Entry 11 is per call, not per Store.** Because C1 navigates with one provider
   call per page, reading a wide file performs one 1 MiB workspace allocation per
   page sequentially. Peak stays 1 MiB; churn is proportional to page count and
   shows up as the `storage.decode` node (1.3–1.5 ms per call in the debug smoke
   runs).

No payload spool or scratch file exists: product `src/` contains no `std::fs`,
`File::`, `OpenOptions` or temp-directory call, and
`a_complete_file_singleton_never_creates_a_payload_file` asserts that a Store
directory holds exactly the database file after a 131,071-byte singleton save.

Slow storage, many files and errors cannot accumulate one buffer per object: the
batch drains at 512 objects and 512 KiB, and
`a_late_input_failure_after_an_early_commit…` plus
`a_pipeline_input_failure_…` show that a failure releases the batch and the
operation (store counts return to their pre-failure values). The one place this is
*not* proven is F3, where a mid-save re-acquisition failure skips the deletion
pass and leaves committed rows behind.

### 7.3 Memory safety verdict: **PASS for what was inspected, with declared limits**

| Area | Finding |
| --- | --- |
| `unsafe` surface | Confined to `encoding/codec.rs`: 7 blocks plus 1 `unsafe fn`, all FFI. Both FFI wrappers own a `Vec<u64>` region and build a *static* context inside it; `Drop` clears the pointer and never calls a C free. The crate denies `unsafe_op_in_unsafe_fn`; `layerfs-content` forbids unsafe code entirely. |
| Allocation arithmetic | Every workspace and output size passes through a checked conversion plus `try_reserve_exact` and an explicit limit; `output(size, limit)` rejects zero and over-limit sizes; `canonical_len` is checked against the 16 MiB profile cap. |
| Codec input and output lengths | Compression validates the raw length against the profile limit, `ZSTD_compressBound` against the frame limit, and the produced length against both. Decompression validates the frame magic, reserved descriptor bits, `frameContentSize == raw_length`, `windowSize` against the window log (or `GROUP_LIMIT` for group bodies), `dictID == 0`, `checksumFlag == 1` and that `findFrameCompressedSize == frame.len()`, then decodes into an exactly sized buffer. |
| Malformed pack offsets | `parse_header` bounds the header, version and group count; `group_view` validates directory continuity, that each body starts where the previous ended, non-zero encoded and decoded lengths, codec tag consistency, `decoded ≤ GROUP_LIMIT`, and that the last body ends exactly at `bytes.len()`. `record_range` validates strictly increasing ends and exact area consumption. | Decompression bounds | No frame-derived growth: destination capacity is always the validated declared size. |

against the API contract, not by a sanitizer. A low RSS figure would not prove a
memory budget, and none is claimed.

## 9. Plain answers

- **Are all Stage 1 criteria met?** Yes, with two coverage gaps that are not
  defects: the declared `READ_WAVE_BYTES` ceiling is never enforced (the effective
  bound is 32 objects times the maximum chunk), and empty-file identity is
  asserted through one route rather than a second independent fixture. Stage 1 is
  **PASS**.
- **Are all Stage 2 criteria met?** **No.** The required visibility guarantee is
  violated by demonstration (F1), the ownership ordering is wrong at source level
  (F2), and a mid-save re-acquisition failure can skip cleanup (F3). Everything
  else in Stage 2 passes, including the FULL physical path, the four-table schema,
  exact CAS reuse, locator stability, the failure semantics that *were* inducible,
  and the supported incompressible singleton at C2. Stage 2 is **FAIL**, and
  neither issue should be closed yet.
- **What can be simplified now?** The per-object canonical clone (F4); sixteen
  dead API items and one unreachable guard (F7); the unused `blake3` dependency
  (F8); per-call workspace and connection churn with point-loop node reads (F5);
  the duplicated timing labels (F9); and one redundant clone in the same-save read
  (F11). Together roughly 100–130 production LOC plus one file-size-proportional
  memcpy per save.
- **What do we actually know about speed and memory?** At 16 KiB and 600 KiB
  inputs, one sample each, in a debug build, the real operations complete and
  round-trip: C1 construction 1.0 ms and 45.1 ms; C2 save-to-ack 15.1 ms and
  13.4 ms; C2 read 2.9 ms and 9.5 ms; integrated 24.1 ms and 85.2 ms. A release
  harness shows one grouped 24-identifier read (1.077 ms) costs about a sixth of
  24 point reads (0.265 ms each) and that each provider call carries roughly
  0.27–0.47 ms of fixed cost. Memory is bounded per owner and the ledger states
  each bound, but the aggregate is unchecked and there is no RSS or heap
  measurement at all.
- **What cannot yet be claimed?** Any v0.1.6 speedup or regression; any cold-cache
  latency; any compression or pack-occupancy efficiency; any total process memory
  figure; the timing overhead of enabled versus disabled recording; that private
  early output is invisible to unrelated readers (it is not); that every failure
  leaves a clean Store (F3); and anything at all about Stages 3–7. A clean
  Stage 1–2 result would still not be a v0.1.7 qualification.
