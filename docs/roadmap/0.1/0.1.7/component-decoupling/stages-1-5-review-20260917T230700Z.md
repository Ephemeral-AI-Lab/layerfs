## 1. Findings, severity ordered

### F1 - HIGH (evidence integrity): `filesystem_timing_c1 --case attributes` times nothing

**Location.** `core/crates/layerfs-content/examples/filesystem_timing_c1.rs:276`
(`"attributes" => (Vec::new(), Vec::new(), Vec::new())`) with the timed region at
`:296-309`, the row print at `:376`, and the attribute patch at `:388-440`.

**Trigger.** `--case attributes`. The change set is empty, so the timed
`update_filesystem_timed` call re-emits the base root unchanged; the attribute
patch the case is named for runs **after** the report has been printed and is not
inside any timer.

**Observed vs expected.** Reproduced
(`diagnostics/attributes-case.log`): `--case empty` prints
`directories 0 bindings +0 -0 / objects read 0 waves 0 bytes 0 emitted 1 bytes 129`;
`--case attributes` prints the *same* counters (`directories 0 bindings +0 -0`,
`objects read 0`, `emitted 1 bytes 129`) plus `elapsed_ns 45666` and six phase
rows, and only then `attribute_patch: set 1 preserved 1 base pages 1 values
emitted 1`. Expected: the case named `attributes` measures the attribute work it
advertises.

**Consequence.** A printed Stage-5 row with a nanosecond elapsed time and a phase
breakdown describes a no-op. Anyone quoting the `attributes` cases from this
example would attribute a duration to work that did not happen. The stage-5
verification contract lists a `filesystem.attributes` family
(`stage-5-verification.md:52-54`), so the name collision is reachable.

**Smallest remedy.** Move the attribute patch inside the timed closure and build
its inputs before `Timing::record`, or rename the case to `noop-with-untimed-patch`
and time the patch as its own labelled operation.

### F6 - MEDIUM (limits): the attribute-value limit is 32,768 bytes, not the 1 MiB the limits table states

**Location.** `core/crates/layerfs-content/src/filesystem/attributes/value.rs:22-56`
(`emit_value`) checks `MAXIMUM_ATTRIBUTE_VALUE_BYTES = 1 MiB` at `:26-31` and then
emits **one** `ObjectRole::Chunk` object for the whole value at `:32`; the chunk
encoder refuses anything above `cdc::MAXIMUM_CHUNK_BYTES = 32_768`.

**Trigger.** `emit_value(&mut objects, &[0x5a; n])` through the public
`FilesystemObjects` boundary at a non-default size.

**Observed vs expected.** Reproduced (`diagnostics/diag-run.log`, probe P6):
`value bytes 4 -> OK`; `value bytes 1048576 -> ERR object limit 32768 exceeded by 1048576`;
`value bytes 1048577 -> ERR object limit 1048576 exceeded by 1048577`. So the 1 MiB
branch is only reachable for a value **below** 32,769 that also exceeds 1 MiB
(impossible), i.e. the declared 1 MiB ceiling is dead code and the real ceiling is
the CDC chunk maximum. `stage-5-report.md:334` states
`Attribute value | enforced | <= 1 MiB, always extent-backed`, and
and `stage-5-matrix-remediation-20260917.md` row `AT-4` was promoted to PASS on
"the 1 MiB value bound covers the write path".

**Consequence.** A caller that reads the limits table will size attribute values
against 1 MiB and discover the real limit only at runtime, at a figure 32x smaller.
The `AT-4` PASS is not supported by its stated reason.

**Smallest remedy.** Either chunk the value across floor(n/32768) chunk objects
(which the existing mapping grammar already supports) or correct the constant and
both limits tables to 32,768 and say the bound is the chunk maximum. The first is
a behaviour change; the second is a documentation fix and is what an unqualified
review can accept today.

### F7 - MEDIUM (capacity): one whole-tree validation walk caps a single operation, so one `build_filesystem` call cannot exceed 4,095 directory bindings

**Location.** `core/crates/layerfs-content/src/filesystem/validate.rs:53`
(`MAXIMUM_CYCLE_CHECK_ENTRIES = 4_096`), enforced per walk in
`check_build_reachability` (`:591-614`), `check_parent_aliases` (`:279-346`) and
`check_effective_cycles` (`:636-668`).

**Trigger.** A single `build_filesystem` whose stated bindings exceed 4,096
entries; or, on an existing tree, any operation that rebinds a directory whose
effective subtree exceeds that many entries.

**Observed vs expected.** Reproduced through the public API
(`diagnostics/diag-run.log`, probes P2/P8):

```text
P2  files 4094 -> OK   entries_examined 8189
    files 4095 -> OK   entries_examined 8191
    files 4096 -> BUILD REFUSED invalid record: cycle check work limit
P8  base build: 4095 entries OK
    add 100 entries: OK, validation entries_examined 0     <- second operation
    rename the 4195-entry directory: REFUSED invalid record: cycle check work limit
```

Expected (and what happens): the refusal is deliberate and documented — the module
comment at `validate.rs:45-53` says a legal tree larger than the ceiling is refused
"with the same error a genuine cycle gets". What is **not** documented is the
consequence for capacity: a filesystem can only be created above 4,095 entries by
several operations, and once created, a directory whose subtree exceeds the
ceiling can never be renamed or relocated.

**Consequence.** This is a real bound on the owner's "maximum file count" question
and it is absent from `stage-5-report.md` §6 (whose "Enforced" rows stop at names,
paths, pages, keys, values, serials and scratch). It also means the "verified
measured" row "900-entry construction, 400-entry updates" understates what is
reachable and overstates what is safe: the cliff is at 4,096, not at 900.

**Smallest remedy.** Add the row to the limits table with its scope ("whole-tree
checks, per operation") and the two consequences above; optionally charge the
ceiling once per operation instead of once per walk, so an operation with many
directory rebindings cannot spend N x 4,096 entries.

### F8 - MEDIUM (work): ordering reads are still superlinear and every lookup rebuilds a reader

**Location.** `core/crates/layerfs-content/src/filesystem/references/runs.rs:307-368`
(`find`) and `:337` (`RunReader::seek_from`) with `merge.rs:84-101`
(`seek_from` allocates and zeroes a fresh `buffer_bytes` buffer on every call).

**Trigger.** More touched serials than `maximum_pending_records`, so the reducer
spills and later looks rows up in runs.

**Observed vs expected.** Measured with the reviewer's client over a 4,000-file
base, `maximum_pending_records = 64` (`diagnostics/diag-run.log` P1):

| change pairs | rows spilled | elapsed ns | `rows_read` | `rows_written` | runs | peak owned bytes |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 250 | 448 | 15,831,958 | 2,198 | 1,588 | 14 | 66,432 |
| 500 | 960 | 35,641,708 | 6,684 | 4,328 | 30 | 139,008 |
| 1,000 | 1,984 | 87,571,000 | 19,960 | 10,896 | 62 | 284,160 |
| 2,000 | 3,968 | 154,513,875 | 59,007 | 25,760 | 124 | 568,320 |

`rows_read` multiplies by 3.04 / 2.99 / 2.96 per doubling (~n^1.58); elapsed by
2.00 / 2.38 / 2.10. The round-1 review measured 3.65-3.83x per doubling and called
it quadratic; the scan cursor removed the quadratic term, but the tiered merge plus
the per-call reader remains superlinear, and the reducer reads 2.3x the bytes it
writes. Expected for a bounded tiered merge: O(n log n) reads, i.e. ~2.1x per
doubling at these sizes.

**Consequence.** An operation with a large touched set and a small pending ceiling
pays superlinear ordering work. The Stage-5 report claims no speedup
(`stage-5-report.md:355-356`), so nothing published is wrong; the cost is simply
unmeasured and larger than linear.

**Smallest remedy.** Keep the tier's `RunReader` (and its buffer) in
`LookupScan` instead of rebuilding it per call — the cursor state is already
per-tier, and this is the change that makes `find` O(1) amortized rather than
O(1) plus a 16 KiB allocation and zeroing.

### F11 - MEDIUM-LOW (bound): the declared per-transaction byte bound is a commit trigger, not a cap

**Location.** `core/crates/layerfs-storage/src/cas/owner.rs:840-844`
(`maybe_commit`) evaluated after `self.transaction.bytes += member.canonical_length`
(`:819`) and `self.transaction.bytes += write.bytes.len()` (`:835`);

### Q6 - Can later FUSE and host-only / host-remote / host-container arrangements use this core?

**Yes for the in-process arrangements; adapter work is required for the split
ones; replacing C2's SQL backend with remote SQL is a core blocker.** §8 gives the
seam-by-seam map, the three placement verdicts and a source-accurate minimal local
composition. The two facts that decide the answer:

- the dependency direction is `telemetry <- content <- storage` (C2 links C1, not
  the reverse: `core/crates/layerfs-storage/Cargo.toml:11`), so a "C1 service" and a
  "C2 service" are separable processes but share a crate graph;
- every core seam is a **synchronous borrowed trait object**
  (`StoreProvider<'a>{store: &'a Store}`, `SaveHandoff<'a>{operation: &'a mut SaveOperation}`),
  with `Store::accept` flushing synchronously. A cross-process adapter must be
  blocking; there is no async form, no `Send`/`Sync` bound anywhere in the three
  crates, and `TimingScope` is deliberately `!Send`.

## 8. Environment independence and exactly how to connect adapters

### 8.1 Dependency direction and both data paths

```text
crates (reference, frozen)        core workspace (replacement)
  layerfs-workspace   ---- no link ---->   layerfs-telemetry   (std only)
  layerfs-fuse                                ^
  layerfs-layerstack-store                    | path dep
  layerfs-daemon / cli / sdk             layerfs-content   (blake3 + telemetry)
                                              ^
                                              | path dep
                                         layerfs-storage   (rusqlite, zstd-sys)

WRITE  caller -> native C1 input (borrowed, unbounded)      content/filesystem/input.rs
              -> validated topology + final values          filesystem/validate.rs, sorted/
              -> finalized owned objects                    object/output.rs:FinalizedObject
              -> bounded C2 save (512 obj / 512 KiB batch)  storage/cas/batch.rs
              -> one acknowledged finish (COMMIT)           storage/cas/store.rs:314
READ   caller <- logical C1 reader (sorted pages)           content/filesystem/read.rs
              <- authenticated object batches               storage/cas/provider.rs
              <- C2 locators under the visibility ceiling   storage/sqlite/lookup.rs
```

The two paths cross exactly two seams: `FinalizedConsumer` on the way out and
`AuthenticatedObjects` on the way in. Everything else is internal to a crate.

### 8.2 Seam map

| caller/owner | actual API (verified) | bytes | preconditions | batch bounds | backpressure | errors / cancellation | process-local assumptions | future adapter work |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| any producer -> C2 | `SaveOperation::accept(&mut self, FinalizedObject) -> StorageResult<()>` (`cas/store.rs:291`) | **owned** by value; ownership moves at `object/output.rs:165` | declared role must match the bytes; framed roles are re-checked at admission | 512 objects / 512 KiB pending, flushed synchronously (`cas/batch.rs:48-69`) | **synchronous**: `accept` flushes when the bound is reached, so a transport-backed consumer must block | typed `StorageError`; `Aborted` after `finish`; no retry | the batch and its `Connection` are per-operation | a blocking consumer that preserves order, cardinality and one attempt |

Process-local assumptions found: hardcoded filesystem paths — **none in the
algorithm**; the only `PathBuf` is the optional `FileBacking` directory and the

assumptions — none in product source (zero `Send`/`Sync` bounds; `TimingScope` is

(`to_ne_bytes`/`from_ne_bytes` appear **zero** times; C1 is big-endian throughout and

### 8.3 Placement verdicts

| arrangement | verdict | evidence and minimum work |
| --- | --- | --- |
| **A. one process / host only** — app or FUSE adapter -> C1 -> C2 -> local SQLite | **READY TODAY** | C1 opens no database, pack or file; the composition already runs and is tested (`storage/tests/core_pipeline.rs:21-61`, `filesystem_pipeline.rs:330`). Minimum work: none beyond wiring. Caveats: every entry point needs a `TimingScope` and it is `!Send`; a reader that runs while a save is open uses a second connection, which is safe because the watermark hides unpublished packs |
| **B. Workspace elsewhere, core together** — host/container/remote Workspace or FUSE -> bounded operation data -> C1+C2+storage service | **ADAPTER WORK REQUIRED**, no core blocker | the adapter must (1) bound `FilesystemInput` itself, (2) bound its own response byte budget, (3) decide where ordering runs (keep it local, or implement `OrderingBacking` over its own storage — passing `None` fails explicitly at the first spill, which is correct below the in-memory budget), (4) supply an `AuthenticatedObjects` over the service's Store (`StoreProvider` already is one), (5) attach completed timing reports rather than sharing a tree. An oversize request has **no** refusal today, so the adapter must add one |
| **C. C1 and storage separated** — C1 caller <-> bounded output/read batches <-> C2 service + storage | **ADAPTER WORK REQUIRED**; the in-process shim already exists | both seams are synchronous borrowed trait objects (`StoreProvider<'a>`, `SaveHandoff<'a>`), `accept` flushes synchronously, and there are no `Send`/`Sync` bounds. Minimum work: a blocking `FinalizedConsumer` client, a blocking `AuthenticatedObjects` client with exact cardinality and its own byte ceiling, an identity story (C1 trusts the provider, so the proof must stay on the C2 side), and timing attachment. **Batch order and cardinality are already contractual** (`BatchCardinality` is checked on both sides) |
| **C-SQL. replace C2's SQL backend with remote SQL** (same C2 code) | **CORE BLOCKER — needs C2 changes, not a shim** | `Store::open` accepts a **path only** (`sqlite/connection.rs:17-26`); the session PRAGMAs are read back and *enforced*, so an incompatible endpoint fails explicitly (correct); the schema is created and validated through SQLite-specific `STRICT`/`WITHOUT ROWID` DDL plus `sqlite_master` text and `PRAGMA table_info` (`schema.rs:99-205`); one transaction spans many statements (`owner.rs:176,840-857`); and **all object bytes live in the database** (`schema.sql:34-37`, `write.rs:76-97`), with a pack append rewriting the whole `BLOB`. Minimum C2 changes: a non-path connection target, server-side equivalents for the verified PRAGMAs, a catalogue check that is not `sqlite_master` text, transaction affinity across requests, an explicit per-statement byte bound, and payload moved out of the table. Moving the whole embedded C2 service (option C) is the smaller change |

**A URL or one trait does not make an arbitrary provider compatible.** Nothing in
C2 today would accept a DSN, and every unsupported required capability fails
explicitly rather than falling back — which is the correct behaviour and is what
this review verified.

### 8.4 The smallest integration recipe

The future adapter, in the order it must do the work:

1. **Capture and normalize (adapter cost, not free).** Produce stable native
   changes: final bindings per directory, strictly sorted and unique; typed final
   values; serials the adapter's allocator just created. This is the same shape the
   reference `CandidateInputs::build` produced, and its cost belongs to the
   adapter's own budget — it is **not** preparation that an end-to-end claim may
   treat as free. The adapter also owns the request ceiling C1 does not declare
   (N-14).
2. **Supply the capabilities and start the timer.** One `AuthenticatedObjects`
   (in-process: `StoreProvider`; remote: a blocking client), one
   `FinalizedConsumer`, and optionally one `OrderingBacking`. C1 then runs with
   **no FUSE paths, no daemon identities, no history**: `update_filesystem(&mut
   objects, &input, Some(backing))` is the whole call.
3. **Connect finalized output to the same C2 save.** In process:
   `SaveHandoff::new(&mut operation)`. The adapter must distinguish **construction
   completion** (the returned `FilesystemResult`) from **acknowledged persistence**
   (`SaveOutcome` after `finish`); publishing a workspace/history root is a later
   owner's act after a successful finish, never before.
4. **Serve FUSE reads with bounded logical reads.** `FilesystemRead::new(provider,
   root)` plus `resolve`/`stat`/`list`/`readlink`; page with the caller-declared
   count and byte bounds. Live write state, locking, permissions, errno mapping and
   open-handle lifecycle remain adapter/Workspace responsibilities — the core has
   no concept of any of them.
5. **Across a process boundary**, the transport must preserve batch order and
   cardinality (already checked), byte and count bounds (the adapter must add the
   byte one), identity checks (C2 side), cancellation, and single-attempt errors.
   A full output queue stops production — `accept` is synchronous by contract.
   A logical operation costs **one** navigation wave per level plus one payload
   wave per bounded group plus one save batch per 512 objects; there is no
   per-node RPC left in C1 (the mapping navigation was batched in `ab17a6958`).
6. **A lost acknowledgement is failure/unknown, never a retry.** `StorageError`
   already models `UnknownOutcome`; the adapter must not resend, guess success or
   delete possibly-successful output. Cross-host monotonic timestamps are not
   directly subtractable; remote elapsed times may overlap and must be attached as
   completed reports, not merged as live spans.

## 11. Final answers

**Can Stage 5 be accepted under its current scope?**

**No.** The scope says acceptance requires the stage's applicable criteria *and*
its evidence obligations. The correctness core of Stage 5 (identity and codec
unification, scoped identity and its range, sorted copy-on-write with exact
partitions, whole-tree validity, reference accounting, bounded reads, portable and
generic attributes, real C2 composition, ordered final values) is implemented,
tested and — where this review could reproduce it — reproduced. But:

- two measurement harnesses print rows naming work they did not perform (F1, F2),
  and a third times work it says it excludes (F3);
- the limits evidence contains a factually wrong bound (F6: 32,768 bytes, not
  1 MiB) and omits a real one (F7: the 4,096-entry operation ceiling);
- six per-commit LOC disclosures do not reproduce (F4);
- the governing measurement document cites an invalidated receipt (F5);
- the required comparison and the simultaneous-memory row are not satisfied
  (VF-5 partial, TR-5 incomplete), and the complete-operation comparison is
  declared NOT_RUN.

None of those is a product-behaviour defect, and the first four are cheap to fix.
Stage 5 can be accepted after actions 1-5, with 6-9 as follow-ups.

**Is the whole C1/C2 core feature-complete?**

**Yes, at the implemented scope, with three named qualifications.** Every stage
0-5 obligation is implemented and exercised by passing external tests; the
composed routes are traced end to end; C1 runs with no storage dependency and C2
runs with no construction. The qualifications are: non-compact profiles are
refused by design; the 4,096-entry whole-tree operation ceiling and the 32,768-byte
attribute-value ceiling are real capacity limits a Workspace must design around;
and revision/payload reclamation does not exist by design, so retention is a later
owner's problem. "Feature-complete" is not "qualified": the performance,
cold-cache, footprint and process-memory rows are unmeasured, and three limit rows
have no boundary test at all.

**Is existing-or-better performance demonstrated, waived or still unknown?**

**Unknown, and the only comparative evidence is weaker than the documents imply.**
No complete-operation comparison exists and none is possible against the pinned
reference for the composed operation. The component comparison has two
collections: the eligible one at `eb42c1347` (0.653 / 0.272 / 0.480
candidate/reference on three primitive cases, identity MATCH) and the ineligible
one the governing addendum still publishes (0.324 / 0.347 / 1.100). They disagree
by up to 2.3x on the candidate arm and 1.85x on the reference arm, so neither is a
stable absolute and neither supports "as fast as v0.1.6". The Stages 3-4 waivers
remain waivers; they do not reach Stage 5. What the source *does* reduce is
reproducible: one grouped navigation call per level instead of one per page, one
inline leaf grammar, and a single ordering byte owner with honest counters — and
what this review *measured* is that ordering reads still grow ~3x per doubling of
the change count.

**Can Stage 6 qualify this artifact, and what must a later Stage 7 adapter supply?**

**Stage 6 can qualify it, but not with the artifacts that exist today.** Stage 6
needs: a frozen complete-operation comparator (or an explicit owner decision that
none will exist and the claim is withdrawn), numerical gates, an enforced cache
contract, declared resource limits, and one identified build per row. The core is
otherwise a sound qualification target: it is deterministic, single-threaded by
policy, has no I/O of its own in C1, and reports its own work counters.

A **Stage 7 adapter** must supply, in this order: bounded native changes with
authorized scoped identities and an explicit request ceiling; a provider and a
consumer (and optionally an ordering backing) at the existing seams; the
distinction between construction completion and acknowledged persistence; bounded
listing/read serving with its own byte ceiling; and — across a process boundary —
a blocking transport that preserves batch order and cardinality, identity proof on
the C2 side, cancellation, and single-attempt error semantics with no retry. Live
write state, locking, permissions, errno mapping, open-handle lifecycle, history
naming and all reclamation remain the adapter's.

**No issue was closed, no release decision was taken and no runtime was
implemented by this review.**
