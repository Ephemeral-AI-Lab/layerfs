### 0.1 The four blocking findings, in full

**R1 - a Directory or Symlink inode can acquire a second parent (correctness).**
`validate.rs:150-159` counts only the additions *this batch* makes; the base
binding is consulted solely for the child's *kind* (`:143-148`). Binding an
existing directory under a second name therefore never trips the `added > 1`
rule, and `reduce.rs:509-543` stores `base_count + delta = 2`. The record
invariant that forbids this already exists and is never called on this path:
`InodeValue::validate` (`object/inode_leaf.rs:101-113`, rule at `:106`).
*Reproduced* (`diagnostics/topology.log`):
`T2.dir_second_parent=ACCEPTED root=ff1be089...`,
`stat d/e=Ok((2, 2))`, `stat d/e2=Ok((2, 2))`,
`lookup_serial_3=Ok(Some(2))`; the symlink case
`T3.symlink_second_parent=ACCEPTED`, `lookup_serial_4=Ok(Some(2))`; and the
same-batch control `T4.same_batch_duplicate=REFUSED "multiple parents"`.
*Consequence:* the namespace becomes a DAG, the stored inode value violates the
component's own invariant, and the reference cannot produce it. This is exactly
the case `stage-5-handoff.md:140-142` and `filesystem-tree.md:206-211` forbid.
*Smallest remedy:* when the base record's kind is not `RegularFile`, require
`previous.namespace_ref_count + added == 1`; one test in `filesystem_topology`.

**R2 - an acknowledged save can hold a root whose required objects are absent.**
`InodeValue` embeds `content_root` and `metadata_root`
(`object/inode_leaf.rs:117-140`), but a level-0 leaf row carries `child: None`
(`sorted/format.rs:362-366`), so `sorted/page.rs:353` collects no reference
for it, and `cas/dependencies.rs:47-70` validates only
`FinalizedObject::references()`. Nothing therefore relates an inode value's
roots to the saved object set. *Reproduced*
(`diagnostics/dangling-reference.log`): two arms differing in exactly one thing,
whether the object the file inode names was emitted.

    arm=dangling         emitted_objects=3 acknowledged=true inserted=3 packs=2 commits=1
    arm=dangling         file_value_roots_present_in_store=0 (of 2)
    arm=dangling         read_of_file_content_root=Err(ObjectMissing(1a07bee6...))
    arm=control-emitted  emitted_objects=4 acknowledged=true inserted=4 packs=2 commits=1
    arm=control-emitted  file_value_roots_present_in_store=1 (of 2)
    arm=control-emitted  read_of_file_content_root=Ok(bytes=55)

The save path accepts both identically and acknowledges both. The product's own
C2 target already persists a dangling synthetic root
(`layerfs-storage/tests/filesystem_pipeline.rs:185` with
`tests/support/filesystem.rs:288-289`) and still asserts a successful reopen.
This contradicts the review obligation that a reported root must have its required
objects persisted, and `admission-and-persistence.md:69`.
*Consequence:* an acknowledged, published Store can serve a root that fails on the
first read of a file's content or attribute root, with no earlier detection.
*Smallest remedy:* declare a leaf's value roots in its `references()` so the
existing dependency check covers them, **or** document the caller-authorized-roots
exclusion and add one target that saves a dangling supplied root and asserts the
documented outcome.

**R3 - the record-backed ordering path is quadratic and under-reports its work.**
`RunStore::find` (`runs.rs:236-252`) builds a fresh `RunReader` and scans
from offset 0 on every call; it is called once per touched serial
(`reduce.rs:154-163`), once per not-yet-pending serial inside `entry`
(`reduce.rs:218-233`) and once per released child (`release.rs:67,133`),
after `touched_serials` has consolidated everything into **one** run
(`reduce.rs:170-171`). `find` takes `&self`, so those reads can never be
counted: `rows_read` is incremented only by `merge_runs` (`merge.rs:116`)
and `copy_run` (`runs.rs:409`). *Measured*
(`diagnostics/ordering-growth.log`): one logical operation - rename every entry
to a freshly allocated serial - at four sizes, one sample per case per arm, warm
in-process fixtures, identical inputs, debug profile.

| entries | rows_touched | no-spill elapsed ns | spilling elapsed ns | spilling rows_read | runs_created |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 200 | 801 | 10,868,042 | 145,656,500 | 2,866 | 24 |
| 400 | 1,601 | 23,285,041 | 530,958,375 | 7,394 | 50 |
| 800 | 3,201 | 50,355,250 | 1,988,077,958 | 17,986 | 100 |
| 1600 | 6,401 | 119,691,125 | 7,604,108,916 | 42,370 | 200 |

Per doubling the spilling arm costs **3.65x, 3.74x and 3.83x** (trending to 4x =
quadratic) while the no-spill control costs 2.14x, 2.16x and 2.38x (linear), and
the *reported* `rows_read` grows only 2.58x, 2.43x and 2.36x (linear). The
reported work counter is therefore not a bound on the work done; it grows like the
square root of it. Arithmetic check: 3,201 `find` calls over a ~3,200-row run of
96-byte rows is about 3.1e8 row decodes; at the observed 7.60 s that is about
40 MB/s of decoded run bytes, so the elapsed time is explained by the scan alone.
The largest input any in-tree target exercises is 303 inodes / 31 touched
(`filesystem_bounds.rs:528`), so no collected case can see this.
*Consequence:* an operation over a large touched-inode set degrades quadratically
on the path the handoff calls the record-backed workload, and the evidence
gathered for that path is misleading. *Smallest remedy:* advance a monotonic
per-tier cursor (the touched-serial sweep is already ascending) or index the run;
count those reads in `rows_read`; add one bound test.

**R4 - the Stage 5 harness does not select or compose what its rows claim.**
(a) `--case` chooses only a fixture *size*: `examples/measure_filesystem.rs:174-179`
maps `directory-update | inode-update | hardlink-move | subtree-remove` to the
same `entries = 200`, `--mode pipeline` always applies an empty change set
(`:288-291`) and `--mode c2` always saves the same fixture bag.
*Reproduced:* the four pipeline cases print the **identical root**
`d5f91c977e13df...` and identical counters, differing only in `elapsed_ns`
noise; the two C2 cases likewise differ only in `elapsed_ns`.
(b) The integrated row is named "construction, bounded handoff and save
acknowledgement" (`:336`) but `:309-317` buffers every emitted object in an
in-memory `Bag` before `begin_save`, and `readback` (`:347-353,361-377`)
reads that same `Bag` - no `SaveHandoff`, no Store reopen, no storage read.
*Consequence:* the collected rows C2 `inode-update` (14,604,375 ns) and
integrated `subtree-remove` (17,534,000 ns) with read-back 90,583 ns are
mislabelled and do not evidence a handoff or a reopen; the corresponding
verification-contract clauses (`stage-5-verification.md:81-82`) are unmet.
*Smallest remedy:* map each `--case` to a real change set (or print the banner
`measure_edits.rs:411-422` prints and rename the rows), and route the pipeline
row through `SaveHandoff` plus a reopened Store read-back (the pattern already
exists at `examples/measure_components.rs:275-296`).

## 1. Executive answers to the six owner questions

### Q1 - resulting structure and LOC
The complete C1/C2 implementation is 3 crates, 115 production files, **17,905
production LOC** (core), with the reference tree unchanged at **65,417** (ten
crates). No production file exceeds the 999-physical-line ceiling (largest 949)
and no `lib.rs`/`mod.rs` exceeds 190 (limit 200). Stage 5 added **+6,745 core
LOC** (C1 +6,722, C2 +23, telemetry 0); Stages 1-5 cumulatively added **+17,173**
over the 732-line telemetry-only pre-Stage-1 tree, and the reference tree has not
moved by a single line since v0.1.6. Full tree, per-file and recursive tables,
plan deviations and the per-commit audit are in section 3.

### Q2 - are the criteria met?
No. **Stage 5, 71 rows: 50 PASS, 15 FAIL, 5 INCOMPLETE, 1 NOT_RUN. Cumulative
Stages 0-4 plus telemetry and the reachable-settings audit, 31 rows: 27 PASS,
1 FAIL, 1 INCOMPLETE, 2 owner-WAIVED. Combined 102 rows: 77 PASS, 16 FAIL,
6 INCOMPLETE, 1 NOT_RUN, 2 owner-WAIVED.** Four Stage 5 acceptance areas fail
outright: canonical identity is *correct but duplicated* (R11), whole-tree
validity fails on second parents and cycles (R1, R8), ordering fails its resource
and work-accounting obligations (R3, R5), and verification fails its
selection/composition obligations (R4, R17) and its LOC/plan accounting (R16).
Per stage: Stage 0-1 PASS; Stage 2 PASS with two carried open items; Stage 3 PASS
on behaviour with the frozen-partition criterion INCOMPLETE; Stage 4 PASS; Stage 5
**FAIL**; shared telemetry PASS with one carried open item.

### Q3 - what can be deleted, merged or simplified?
Twenty-one material opportunities in section 5, four of them high value: delete the
duplicate leaf-page codec (R11, about 90-150 LOC), delete four dead exported
functions and five dead fields or methods (R21, about 60-90 LOC), remove the five
`LAYERFS_TRACE` branches (R15, about 12 LOC plus a per-binding environment read
on the timed path), and give `RunStore` a monotonic cursor (R3, about 25-40 LOC)
which also removes the quadratic term. Nothing in the reference tree may be
deleted: this review authorizes no reference retirement.

### Q4 - speed, efficiency, bounded memory and memory safety
**Speed.** Two component cases are faster and one is 10% slower, and that receipt
is **not identity-matched to this tree** (R17); the complete-operation comparison
is `NOT_RUN` with a source-backed reason; the Stages 3-4 waivers remain
owner-waived and unmeasured and do not waive Stage 5. So "existing-or-better
performance" is **not demonstrated**, is **not waived** for Stage 5, and is
**unknown**. New here: this review measured a **quadratic** regression on the
record-backed path (R3) that no prior row covered. **Storage.** On the smoke
fixture: 8 objects / 19,970 canonical bytes became 9,966 pack payload bytes
(0.499, compressed) in 2 packs, with 4 value groups and 202 pooled values, in a
45,056-byte SQLite file; no pack-slack, cold-cache or whole-tree footprint row
exists. **Memory.** Section 6 gives a 22-owner ledger built from allocation and
release sites. Every owner the operation *reports* is bounded by a declared
ceiling, but the touched-serial vector is bounded by **no** ceiling (8 bytes per
touched inode) and no whole-process RSS, cgroup, file-cache or allocator
measurement exists anywhere in Stage 5 - a source-derived budget is not measured
RSS. **Memory safety is a separate verdict: PASS for the reviewed scope, with an
explicitly unrun tooling gap.** `layerfs-content` and `layerfs-telemetry` are
`#![forbid(unsafe_code)]`; all `unsafe` is 11 zstd-sys FFI blocks plus one `unsafe fn`, all confined
to `layerfs-storage/src/encoding/codec.rs`, `unsafe_op_in_unsafe_fn` is
denied, decompression is bounded before allocation, and no sanitizer or Miri run
exists for this artifact - so this is a code audit plus dependency guarantees, not
a proof.

### Q5 - enforced, configurable, theoretical and verified limits
Section 7 answers all eight rows. Headline: **revisions** - no retained-root,
version-count or history limit exists at all, because C1/C2 own no naming, no
retention and no GC; the depth bounds are whole-file <= 50, chunk <= 50 and pooled
metadata <= 50, persisted separately and checked. **Maximum file size** - no single
enforced maximum; the binding bounds are `u32` extents per mapping page, depth
31, 8,192-byte pages and a 16,777,216-byte canonical-length ceiling on a *page*
object; the largest real payload verified in this review is small, and no
large-payload case was collected. **File count** - one *operation* is bounded by
`MAXIMUM_CYCLE_CHECK_ENTRIES` (4,096) in validation and by supplied memory
otherwise; the *stored* filesystem has no count limit, only 2^63-1 serials per
scope and available storage. **Directory length** - 255-byte names, 4,096-byte
paths, 256 components, 8,192-byte pages, 2/5 fill; the listing page is bounded by
the caller. **Filesystem size** - C1/C2 provide filesystem roots, not a Workspace
quota or lifecycle; no workspace maximum exists or is implied.
**Attributes/symlinks** - domain <= 64 B, key <= 255 B, value <= 1 MiB *on read
only* (R10), symlink target <= 4,096 B verified at the boundary.

### Q6 - can later FUSE and host/remote/container Workspaces use this core?
Architecturally yes, with adapter work and **one core blocker**. Dependency
direction is correct (`layerfs-telemetry` to nothing; `layerfs-content` to
blake3 plus telemetry; `layerfs-storage` to those plus rusqlite and zstd-sys),
so C1 runs with no SQLite and no Workspace, and every seam is a caller-supplied
trait or value rather than a filesystem path: `AuthenticatedObjects`
(borrowed provider), `FinalizedConsumer`/`FinalizedObject` (owned bytes moved
to the consumer), `FilesystemInput`/`FilesystemResources`,
`OrderingBacking`/`OrderingRun`, `Store`/`SaveOperation`/`SaveHandoff`,
`TimingScope`/`TimingReport`. There is no transport, URL, plugin registry,
network stack or FUSE code in `core/` (grep clean). Placement A (one process,
host-only) is **READY TODAY as public seams and INCOMPLETE as a shipped composition**: the adapter must still write the product composition and the Store-to-C1 provider itself, because no `impl AuthenticatedObjects` exists in product source (R41). Placement B (core in another process, container or
host) is **ADAPTER WORK REQUIRED**: the algorithms are provider-neutral, but
ordering backing currently needs a local directory and a transport must preserve
batch order and cardinality, byte and count bounds, identity checks, cancellation
and single-attempt errors. Placement C read as "replace C2's SQL backend with
remote SQL" is a **CORE BLOCKER**: C2 uses embedded rusqlite with
`journal_mode = MEMORY`, `synchronous = OFF`, a zero busy timeout,
`BEGIN IMMEDIATE` write ownership, in-transaction watermark advances and
`pack_id`-ranged deletes, none of which a generic remote SQL endpoint provides
unchanged. Moving the *whole embedded C2 service* is adapter work, not a blocker.
Details, the seam table, the smallest integration recipe and clearly labelled
pseudocode are in section 8.

### 3.6 Counter audit and counter defects

The counter is `tools/production_loc.py` (407 lines, sha256 recorded in the

`cfg(not(test))` and `cfg(any(test, feature))` stay), same runtime-SQL
treatment (`--` comments removed, code lines counted), and the same
`#[cfg(test)] mod x;` transitive file exclusion. Audit performed for this review:

- **Physical-line ceilings** counted independently of the production counter:
  largest production file `C2/src/cas/owner.rs` at 949 physical lines (cap 999);
  115 files scanned, none above the cap; every `lib.rs`/`mod.rs` below 190
  (cap 200). Consistent with the boundary guard, which passes over 115 files.

  silently reclassified; the only relocation risk is the reference-to-core
  boundary, and the reference totals are identical at every snapshot, so no
  reference line entered a core total.
- **Shipped SQL**: `C2/sql/schema.sql` is counted (48 LOC) and is the only SQL
  in the product. Comment lines were verified to be excluded (the role-ceiling
  line is code and is counted once).
- **Counter defect found**: none that changes a total. Two limits are worth
  recording. (1) The counter counts `src/`-and-`sql`-only, so a future
  production `build.rs` or a non-`src` shipped asset would be missed silently;
  today neither exists for `core` (the two `build.rs` files are ordinary
  modules under `src/`). (2) With the `src`/`sql` scope, a production file
  placed under a directory named `tests`/`examples`/`benches` anywhere in the
  crate path is excluded; no such path exists today, but the guard and the counter
  share the same blind spot, so a future move could evade both.

  prohibited test markers and common implementation constructs in entry files, and

### 5.2 Asymptotics: what the source reduces and what it does not

Work is derived in terms of the real inputs. **Construction** consumes the caller's
binding input once: `O(changes * log pages)` merge work plus one provider wave per
in-page group; it is not `O(changes)` alone because each affected directory's page
walk is proportional to the pages it touches. **A localized edit** is
`O(changed bytes + affected pages)` with a bounded decoded frontier, but CDC
resynchronization has a real worst case at a shifted boundary that the edit tests
measure rather than assume away. **Subtree deletion** visits every released entry:
`O(released entries)` provider reads, and the release frontier currently issues
one serial per demand (S11). **Ordering** is `O(rows log rows)` when it does not
spill and, on the spilling path, `Theta(rows^2)` until S2 lands - the one genuine
asymptotic regression in the tree, flagged even though the small fixture is fast.
**Reads** are `O(depth + page group)` with caller-declared bounds; `attribute_keys`
is the one exception (unbounded collect). No constant-RSS, zero-disk or universal
`O(changes)` claim is made anywhere in this review.

### 6.6 Memory safety - separate verdict

**PASS for the reviewed scope, with two explicit limits.**

- `layerfs-content` (`lib.rs:16`) and `layerfs-telemetry` (`lib.rs:13`) are
  `#![forbid(unsafe_code)]`.
- All `unsafe` in the product is 11 blocks plus one function in
  `layerfs-storage/src/encoding/codec.rs` calling zstd-sys FFI, plus one
  `unsafe fn` (`parse_frame_header`, `codec.rs:581`);
  `lib.rs:19` denies `unsafe_op_in_unsafe_fn`, and the crate is otherwise safe
  Rust over rusqlite (whose own API is safe).
- Decompression is bounded before allocation: the raw length comes from the frame
  header and is checked against `GROUP_LIMIT` (`codec.rs:326,535-556,618`), the
  window size is checked against `GROUP_LIMIT` (`:546`), and the workspace is
  bounded to 1 MiB. Corrupted locators, ordinals and digests are checked at the
  schema and index layers (`sqlite/pool.rs:71,116`;
  `encoding/pool/index.rs:231`); `record_number` and `group_number` have SQL
  CHECKs.
- What Rust itself guarantees: no out-of-bounds access, no use-after-free, no data
  race in the safe code; and the checked arithmetic (`checked_*` throughout) turns
  overflow into an explicit error rather than a wrap in the paths reviewed.
- What a dependency guarantees: rusqlite and zstd-sys are safe/FFI wrappers pinned
  by `--locked`; their own soundness is not re-established here.
- What tests exercise: malformed canonical objects, wrong roles and levels, wrong
  lengths, a corrupted group body, and the frame-boundary refusals. They do **not**
  exercise the FFI sites under a sanitizer.
- **Unrun tooling, reported honestly:** no Miri run (the storage crate has FFI and
  a C dependency, so Miri is not applicable without patching a dependency, which
  the rules forbid), and no ASan/TSan run exists for this artifact. Clippy, a green
  test suite and low observed RSS are **not** a memory-safety proof, and no such
  claim is made here.

supply its own bound for caller input vectors and the touched-serial collection.


## 8. Environment independence and how adapters connect

### 8.1 Actual dependency direction and the two data paths

    layerfs-telemetry   (no dependencies)
          ^     ^
          |     |
    layerfs-content ---- blake3
          ^
          |
    layerfs-storage ---- rusqlite, zstd-sys

Dependency direction is one-way and correct: C1 depends on telemetry and blake3

                    <- AuthenticatedObjects::read_canonical_batch (owned Vec<u8>)

### 8.4 What a remote SQL backend would actually have to satisfy

Inspected in this tree, not assumed:

| requirement | actual code | consequence for a remote/cloud SQL endpoint |

A URL, a connection string or a single trait does **not** make an arbitrary
provider compatible: the requirements above are semantic, and an unsupported one
must fail explicitly rather than silently degrade - which the current code already
does for the embedded profile.

### 8.5 Smallest integration recipe for a later adapter (no core change)

1. **Capture.** Produce normalized, strictly sorted `DirectoryUpdate` /
   `InodeUpdate` sets plus typed final values, and allocate scoped serials
   yourself (the allocator owns uniqueness across its lifetime; C1 checks only that
   a declared-new serial has no base record). The ordering and validation cost of
   this normalization is the adapter's and must not be presented as free.
2. **Run.** Build an `AuthenticatedObjects` provider and a `FinalizedConsumer`,
   start the operation's `TimingScope`, and call `build_filesystem` /
   `update_filesystem` (or the `_timed` variants with `FilesystemPhases`).
   C1 needs no FUSE path, daemon identity or history entity.
3. **Persist.** Connect the consumer to `SaveHandoff` and the same bounded save;
   keep "construction complete" distinct from "acknowledged persistence" and
   publish a Workspace or history root only after `finish` returns
   `SaveOutcome { acknowledged: true, .. }`.
4. **Serve.** Answer lookup/readdir/getattr/read with bounded logical reads
   (`FilesystemRead::resolve/stat/list/readlink/read_attribute`) while live write
   state, locking, permissions, errno mapping and open-handle lifetime remain in
   the adapter.
5. **Across a process boundary**, add the transport for 8.3 B and quantify the
   exchange count per logical operation: today one filesystem operation is one
   save, a bounded number of read waves per level, and one `finish`; a transport
   that turns each node or each inode into its own round trip is an accidental
   per-node RPC and must be rejected by design.
6. **On a lost acknowledgement**, report the operation as failed with an unknown
   outcome; never retry, resend, guess success or clean up output that may have
   been persisted.

A source-accurate minimal local composition exists today and is retained as
external evidence: `diagnostics/stage5-diagnostics/src/bin/dangling.rs` (build ->
read -> `Store::create` -> `begin_save` -> `accept` -> `finish` ->
`contains` -> `read_batch`) and `src/bin/ordering.rs` (the same operation with
a real `FileBacking`, both arms). Both use public APIs only, and neither adds a
product hook.

### 8.6 Pseudocode for the unimplemented connections (illustrative, not callable)

    // FUSE/host adapter - the parts that do NOT exist today.
    on_write(path, offset, data):
        live.insert(path, offset, data)                // adapter-owned live state
    on_commit(path):
        changes = normalize_live_changes(path)         // adapter: sorted, unique, bounded
        serials = allocator.allocate(len(changes))     // adapter: durable burn, scoped
        provider  = StoreProvider(store)               // adapter glue (see 8.2 gap)
        consumer  = SaveHandoff(store.begin_save(scope))
        scope     = timing.child("workspace.commit")
        result    = update_filesystem_timed(objects(provider, consumer), input, None, phases)
        // C1 is done; persistence is NOT yet acknowledged.
        outcome   = consumer.finish(...)               // exactly one attempt
        if outcome.acknowledged: publish_workspace_root(result.root)
        else: return EIO                               // never retry, never guess

    // Remote placement - a transport carrying the SAME batch contract.
    send_read_wave(ids):        // identical cardinality and order, bounded bytes
        reply = rpc("read_canonical_batch", ids)       // one attempt, cancellable
        assert len(reply.values) == len(ids)           // BatchCardinality otherwise
        return reply.values                            // owned bytes on this side
    send_finalized(object):     // role + canonical bytes + references + predecessors
        rpc("accept", object)                          // backpressure: block when full
    ack():                      // a lost ack is an unknown outcome, not a success
        return UNKNOWN                                 // caller reports failure; no resend

`allocator -> InodeIdentity/InodeScope`; `read cache + Store -> AuthenticatedObjects`;
`SaveHandoff -> FinalizedConsumer`; `spill directory -> OrderingBacking`;
`workspace commit timer -> TimingScope`; `Store -> persistence owner`;
`published root -> Workspace/history owner`.

## 11. Closing answers

**Can Stage 5 be accepted under its current scope? No.** The implemented scope is
substantially present and 50 of 71 Stage 5 rows pass, including the hard parts
(canonical byte identity against a sealed independent oracle, the sorted COW engine
with exact partitions and untouched-subtree sharing, reference accounting,
96-byte ordering grammar with checked cleanup, real C2 save/finish/reopen for the
new roles, and the attribute grammar). Four obligations nevertheless fail on the
frozen tree with reproduced evidence: single-parent whole-tree validity (R1),
persistence completeness of a reported root (R2), ordering resource and work
accounting (R3, R5), and the verification row that the Stage 5 harness claims to
have produced (R4), plus an evidence-integrity failure (R17) and stale accounting
(R16). Three of these are small, bounded fixes; none is architectural. The correct
disposition is a scoped remediation round followed by re-review of the affected
rows, not a waiver and not a closure on the current evidence.

**Is the whole C1/C2 core feature-complete? Yes, at the declared component
scope.** All five stages have their implemented surfaces: C1 constructs complete
files and filesystem trees with attributes and symlinks and serves bounded logical
reads; C2 stores, pools, packs and reopens them with exact reuse; the composition
issues one COMMIT and one watermark advance per save; C1 has no SQLite or Workspace
dependency and C2 has no construction dependency. "Feature-complete" is not
"qualified": the correctness and resource rows above are open, and no history,
retention, GC, quota or runtime exists - which the contracts deliberately place
outside C1/C2.

**Is existing-or-better performance demonstrated, waived or still unknown?
Unknown, and now partly disproved for one path.** The only matched component
comparison is not identity-matched to this tree (R17); the complete-operation
comparison is NOT_RUN; the Stages 3-4 waivers remain unmeasured and do not cover
Stage 5. This review additionally measured a quadratic regression on the
record-backed ordering path (R3) that no prior row covered, so the honest status is
"unknown, with one known regression" rather than "equal or better".

**Can Stage 6 qualify this artifact?** Not as it stands. Stage 6 can begin on the
parts that are unaffected (canonical content, physical encoding, pooling, packs,
file edits, C1-only reads), but a whole-core qualification that includes the
filesystem tree would inherit R1, R2, R3 and R4 and would be qualifying a root the
Store cannot fully serve. Actions 1-4 in section 10 are prerequisites for
qualifying the composed artifact; with them done, Stage 6 is the right owner for the
complete-operation comparison, cold-cache rows and measured memory.

**What must a later Stage 7 adapter supply?** A live-operation capture that
produces stable native change sets and authorized scoped identities; the input,
read, output and ordering capabilities (all of which exist as public traits today);
the operation timer start; the link from finalized output to the same bounded save
and backpressure contract, with construction completion kept distinct from
acknowledged persistence; bounded logical reads for FUSE lookup, readdir, getattr
and read, while live write state, locking, permissions, errno mapping and
open-handle lifecycle stay in the adapter; and, across a process boundary, a
transport that preserves batch order and cardinality, byte and count bounds,
identity checks, cancellation and single-attempt errors, with a lost acknowledgement
reported as an unknown outcome rather than retried. It must also add the workspace
quota, retention and GC that C1/C2 deliberately do not provide.
