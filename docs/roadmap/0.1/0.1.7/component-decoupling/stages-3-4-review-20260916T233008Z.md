### 2.1 F1 (S1) - CHUNK delta candidates skip the eligibility check; an absent predecessor fails the save

* **Location.** `core/crates/layerfs-storage/src/encoding/delta/select.rs:209-210`
  (`ObjectRole::Chunk => advisory.first().copied()`), flowing into `:232-243`
  (`let Some(base_id) = candidate else { ... FULL ... }` then `acquire(input, base_id)?`),
  and `core/crates/layerfs-storage/src/encoding/delta/read.rs:82-86` (`resolve_dependency`
  -> `ObjectMissing`).
* **What the contract requires.** `stages-3-4-handoff.md:119-121`: *"A missing/ineligible
  advisory candidate or a successful losing delta trial may select FULL by policy. Failed
  acquisition, corruption, codec reset/encode/decode, allocation, SQL or ownership fails the
  operation."* The required `delta_payload` cases name "explicit/cache candidates; native
  first-only; **absent/ineligible optional candidates**". The report claims
  (`stages-3-4-report.md:49`) that `CHUNK` "considers the first supplied **eligible**
  candidate".
* **Actual behaviour.** The `WHOLE_FILE` path calls `acquisition()` (`select.rs:295-311`),
  which probes every advisory id through `eligible()` and *counts* an absent candidate
  (`:319-322`, `absent_candidates`) before returning `None`, so an absent predecessor
  selects FULL. The `CHUNK` path takes `advisory.first()` with no probe at all, and
  `acquire` then resolves that id directly; an id with no committed row is
  `StorageError::ObjectMissing`, which propagates out of the save.
* **Reference behaviour (read independently).** The pinned v0.1.6 native lane treats the
  same situation as a policy fallback, not an error:
  `crates/layerfs-layerstack-store/src/objects/admission.rs:676-680` maps
  `read::NativePriorOutcome::Unavailable` to `NativeFallback::Unavailable`, which stores the
  FULL record. The candidate therefore deviates from the reference's actual first-candidate
  rule, not merely from the handoff prose.
* **Reachable trigger (source-derived).** The only producer of a `Chunk` advisory is
  `core/crates/layerfs-content/src/file/edit/apply.rs:238-243` plus `:255-267`:
  `predecessor = rightmost_payload(left)` for each edit in a multi-edit stream. For edit
  *N* > 1, `left` may end in a payload created by edit *N*-1 in the same operation. That id
  has no `objects` row until its lane seals: the Native lane seals at `GROUP_TARGET =
  48 KiB` (`cas/owner.rs:27`, `:349-357`) or at `finish` (`:818-820`). A multi-edit chunked
  stream whose second edit follows an earlier replacement therefore supplies an uncommitted
  predecessor and the save fails, where the reference stores FULL. `build_streaming` always
  passes `None` (`file/mapping/build.rs:303`), which is why complete-file construction is
  unaffected.
* **Coverage.** `tests/delta_payload.rs` has no CHUNK-absent case (its native case at
  `:101` supplies two *stored* candidates); `tests/edit_pipeline.rs:151-192` is named
  "multi-edit transition" but loops over three **single-edit** vectors (`:156`, `:162`,
  `:165`), so no integrated multi-edit stream exists anywhere. The defect is both
  unexercised and unasserted.
* **Smallest fix.** Run `advisory.first()` through `eligible()` exactly as the WHOLE_FILE
  path does (counting `absent_candidates` / `ineligible_candidates`), so an absent or
  ineligible native predecessor selects FULL by policy; add the missing `delta_payload`
  CHUNK-absent case and one integrated multi-edit chunked pipeline case.

### 2.2 F1b (S2) - the pooled lane reads above the publication watermark

* **Location.** `core/crates/layerfs-storage/src/cas/owner.rs:459` (`index.find(...,
  i64::MAX, ...)`), `:544` (`index.sync(..., i64::MAX, ...)`), `:658`
  (`lookup::location(..., i64::MAX)`), `:685` (`reader.leaf_body(..., i64::MAX, ...)`).
* **Claimed behaviour.** `stages-3-4-report.md:112` asserts "Read ceiling | the publication
  watermark, applied to every dependency and cache read"; the handoff (`:202`, `:124`)
  requires the captured ceiling to be enforced through dependency and cache reads.
* **Actual behaviour.** Every pooled-lane read passes `i64::MAX`, that is, no ceiling. This is
  currently equivalent to the watermark only because `MutationOwner::acquire`
  (`owner.rs:162-171`) refuses to start a save whenever `retained_pack_ceiling !=
  highest_pack_id`. That precondition, in a different module, is what keeps uninspected packs
  unreachable - not the pooled read path.
* **Impact.** No reachable failure was found at this snapshot. The impact is contract-level:
  the stated invariant rests on one precondition rather than at the read sites, so relaxing
  it (or adding a second reader path) silently exposes unpublished value groups and pooled
  leaves. `encoding/pool/read.rs:75-80` already returns `VisibilityCeiling` when a real
  ceiling is supplied; the writer simply never supplies one, while ordinary reads do
  (`cas/read.rs:41-68`, `cas/store.rs:202-246`).
* **Smallest fix.** Thread the owner's own `self.ceiling` (which already includes its own
  early-committed packs) into those four call sites; add a test that a pooled read refuses a
  catalogue row whose pack is above the captured ceiling.

### 2.2b F1c (S2) - cold-start index replay materialises the whole catalogue

* **Location.** `core/crates/layerfs-storage/src/encoding/pool/index.rs:224-246`
  (`retained_start` calls `pool::catalogue(connection, None)`), with
  `core/crates/layerfs-storage/src/sqlite/pool.rs:123-151` building a
  `Vec<ValueGroupRow>` of every catalogue row.
* **Trigger.** The first synchronisation of a cold `PoolIndex` on a Store holding more
  than `1 + METADATA_INDEX_VALUES` ordinals (`index.rs:116`).
* **Impact.** Live transient memory proportional to the number of catalogue rows - up to one row
  per pooled value in the worst case - while the reference performs the identical recurrence by
  *streaming* the statement
  (`crates/layerfs-layerstack-store/src/objects/metadata.rs:252-281`). The handoff
  forbids size-proportional hidden collectors (`stages-3-4-handoff.md:130`). The
  implementation's comment is right that the *payload* of evicted groups is never read; the
  header vector still is, and nothing bounds it to the 131 072-entry window.
* **Evidence.** Source above; `stages-3-4-report.md` §7.5 concedes that the
  131 072-entry window is crossed but never filled with distinct identity-recorded rows.
* **Smallest fix.** Stream the statement (or page it by `LOOKUP_PAGE_IDS`) instead of
  collecting it. Verification: `metadata_window` plus a transient-row accounting
  assertion.

### 2.3 F2 (S1) - checkpoint D's decoded frontier is not implemented; drafts are encoded and hashed eagerly

* **Location.** `core/crates/layerfs-content/src/file/edit/tree.rs:52-58`
  (`deferred: BTreeMap<ObjectId, Vec<u8>>`), `:105-139` (`hold_node` encodes and hashes on
  every creation), `:112-132` (charge only ever grows), `:82-101` (`load_node` clones and
  re-decodes on each visit).
* **Required behaviour.** `stages-3-4-handoff.md:235-256` (checkpoint D) and its improvement
  row at `:417` require one **owned decoded unfinished representation**: "Owned decoded
  frontier; drop overwritten drafts and encode/hash only final nodes".
  `stages-3-4-completion-handoff.md:134-145` names the two states explicitly - *Stored
  subtree: ObjectId + checked summary* and *Unfinished subtree: owned decoded entries +
  checked summary*.
* **Actual behaviour.** `hold_node` receives a decoded `ExtentNode` and immediately calls
  `encode_node` and `ObjectId::for_bytes` (`:106-107`), so every intermediate draft pays a
  full canonical encode plus a BLAKE3 hash even when a later split or join overwrites it and
  it is never emitted. `commit_node` (`:167-202`) then *re-decodes* each reached node from
  the stored canonical bytes (`:185`) before encoding it again into a `FinalizedObject`.
  Superseded drafts stay in the map and keep charging the deferred ceiling (`:31`,
  `:112-122`) for the whole operation, because nothing removes or refunds an entry.
* **Impact.** Work and memory, not correctness: the handoff's named improvement is not
  delivered, and the live bound is "monotone in edit count up to 8 MiB - 1" (`tree.rs:31`,
  `:116-122`) against an API that accepts 4 096 edits (`file/edit/input.rs:21-22`), not a
  function of supported height and fanout (`stages-3-4-handoff.md:251-256`).
* **Reference contrast (read independently).** v0.1.6 `crates/layerfs-content/src/file/rope/
  edit.rs` emits a node by encoding it once and storing those bytes, taking the summary from
  the in-memory node - there is no decode step. The candidate both re-decodes an emitted
  node (`tree.rs:185`) and re-encodes a node the builder already encoded
  (`DeferredSink::accept` at `tree.rs:225` -> `hold_node` -> `encode_node`).
* **Evidence.** Source above; `grep -rn peak_deferred core/crates/layerfs-content/tests`
  returns nothing, so the counter that would show the difference is unasserted.
* **Smallest fix.** Hold decoded entries plus a checked summary; encode and hash only inside
  `commit_node` once a node is proven final; release a draft when `split`/`concat`
  supersedes it. Verification: `edit_reference`, `edit_localized`, `edit_bounds`,
  `edit_batch`, plus a counter assertion that `nodes_created` equals the number of emitted
  mapping objects.

### 2.4 F4 (S2) - oracles that do not test what their names and comments claim

* **`core/crates/layerfs-content/tests/edit_bounds.rs:240-273`,
  `the_retained_frontier_does_not_grow_with_the_file`.** The body applies
  `Edit::delete(0, 0)`, which `file/edit/apply.rs:62-74` resolves through the no-op
  comparison pass and returns the base root **without running the builder**. `peaks`
  (`:266`) is the *unmodified base's* extent count (40 and 400); the assertion at `:272` is
  vacuous with respect to any frontier, and `:268` asserts the opposite of the test name.
  This is the only target the implementation's tables cite for the frontier bound, and
  `EDIT_DEFERRED_LIMIT` has zero references outside `src/`.
* **`core/crates/layerfs-storage/tests/policy_capacity.rs:146-158`** is named and worded as
  cutoff-versus-budget independence but compares two *cutoffs* (128 KiB vs 1 MiB) at
  identical depths (8/4). No oracle compares depth 4 with depth 50 budgets, so "raising a
  depth never raises a budget" is source-derived only.
* **`core/crates/layerfs-content/tests/object_identity.rs:250-251`** asserts the 8 MiB and
  16 MiB constants equal themselves; no object at either magnitude is encoded, stored, or
  rejected at plus or minus one.
* **`core/crates/layerfs-content/tests/streaming.rs:80-84`** computes a peak pending count
  and then discards it (`let _ = peak;`); `:30-37` builds a `CountingSource` and never reads
  it. Both bound names are unasserted.
* **`assert_children_precede_parents`**
  (`core/crates/layerfs-content/tests/support/mod.rs:175-195`) is the only
  child-before-parent assertion in the tree and is used exclusively by `streaming.rs:55,98`
  (complete construction). No `edit_*` target asserts child-first emission although the
  handoff's test table requires it for `edit_batch` and `edit_model`. The property does hold
  by construction (`tree.rs:186-200`), but it is unasserted for edits.
* **Also uncovered:** no slow bounded sink (only a rejecting consumer,
  `edit_bounds.rs:319-361`); no transition read-amplification accounting; no boundary test at
  the 4 096-edit ceiling, the 8 MiB deferred ceiling, the CHUNK depth ceiling, depth 50, the
  131 072-entry pooled window filled with distinct rows, or the 8 MiB / 16 MiB envelope
  bounds.
* **Smallest fix.** Assert on the counters the product already exposes
  (`EditCounters::peak_deferred_bytes`, `nodes_created`, `MappingBuild::peak_pending`)
  instead of on a base's extent count; add the missing depth, envelope and integrated
  multi-edit cases.

### 2.6 F6 (S2) - a full canonical clone per object survives on the prepared-save path

* **Location.** `core/crates/layerfs-storage/src/cas/save.rs:50`
  (`let object = objects[index].clone();`), inherited verbatim from `5e8b8cbc2`.
* **Required.** `stages-3-4-handoff.md:286-289` lists "per-object clone in cas/save.rs"
  among the hot paths this batch must remove, and the file plan's own row for that file is
  "Batched membership/bases and **moved input; no per-object clone**"
  (`stages-3-4-file-plan.md:196`).
* **Impact.** One deep copy of the canonical bytes (up to `MAX_OBJECT_FIELD_BYTES` = 8 MiB,
  envelope limit 16 MiB) plus predecessors for *every* distinct object of every preparation
  wave: a save copies its own content once before doing any work. `save.rs` is 52 production
  LOC against a recommended 90-170.
* **Smallest fix.** Take `&FinalizedObject` in `owner.offer` (it reads only id, role,
  canonical and length) and drop the clone. Verification: `cas_reuse`, `cas_roundtrip`,
  `core_pipeline`, `memory_bounds`.

### 2.7 F7 (S2) - pack placement deep-clones the open pack on every fit probe

* **Location.** `core/crates/layerfs-storage/src/pack/placement.rs:84-86`
  (`let mut candidate = open.groups.clone(); candidate.push(group.clone());`).
  `EncodedGroup` owns `bytes: Vec<u8>` (`pack/layout.rs:151-161`), so this is a deep copy of
  every group body already in the open pack plus the incoming group, once per placed group.
* **Impact.** Bounded but real: on the order of `group_count_limit x pack_limit` bytes copied
  per pack per lane with an allocation per probe, up to roughly 16.8 MiB per probe in the
  Singleton lane (`layout.rs:110`). The same shape appears at `pack/assemble.rs:187` and
  `cas/owner.rs:589-590`. Provenance: the same clone exists in v0.1.6
  (`crates/layerfs-layerstack-store/src/objects.rs:2390`), so it is not a regression this
  batch introduced - but the batch extended the function for the v6/v7 lanes and claims
  "Assembly/copy counts, bytes rewritten" evidence (`stages-3-4-handoff.md:422`) without
  measuring them. `pack/layout.rs:210 fits` is the canonical predicate and has no caller.
* **Smallest fix.** Compute the fit from `assembled_length(lane, &open.groups)` plus the
  incoming group's framed length instead of materialising a candidate vector.

### 2.8 F8 (S2) - unbounded owners that the design's allocation ledger does not carry

* **`ExtentBuilder` levels at or above 1 grow with file length.**
  `file/mapping/build.rs:187-199` flushes one fixed level and only ever pushes into
  `level + 1`; its sole call site is `flush_streaming(consumer, 0)` (`:165`), and
  `finish_levels` (`:201-232`) runs only at the end. Level-1 entries are therefore
  approximately `(chunks - 193) / 128`, uncapped - directly contradicting `build.rs:60-62`
  ("bounded by the height and the page capacity rather than by the file length").
  `peak_pending()` (`:103-110`) exists and is referenced by no test. **Scale of the claim:**
  a scalability gap, not an observed regression; the largest retained fixture is 3.3 MB,
  about 200 chunks.
* **The dependency pack cache is operation-lifetime with no eviction.** `cas/owner.rs:111`
  holds `BTreeMap<i64, Vec<u8>>`, filled per distinct pack by `delta/read.rs:216-229` and
  never cleared (not at `maybe_commit` `owner.rs:773-790`, not in `finish_inner`
  `:816-853`); the per-entry cap is the lane limit (256 KiB, or `SINGLETON_PACK_LIMIT` =
  16 MiB + 4 096, `policy.rs:47,78-80`). The doc at `select.rs:162-163` calls it "inside
  this wave", which is wrong. A second copy exists at `encoding/pool/read.rs:32`.
* **Bounded cleanup can run one very large transaction.** `sqlite/cleanup.rs:31-75` opens one
  transaction, loops deletes and commits once; the only budget is `pages > 1_000_000`
  (`:66-68`) times `CLEANUP_PAGE_ROWS` 128 = up to about 128 M row deletes, under
  `journal_mode = MEMORY` (`connection.rs:33`), so modified-page pre-images are held in RAM
  until COMMIT. The transaction row/byte limits the owner enforces (`owner.rs:774-777`) are
  not consulted on this path.
* **Declared-but-dead budgets.** `METADATA_INDEX_BYTES` (32 MiB, `storage/policy.rs:118`) has
  no readers; the real index bound is the entry count 131 072 times a 24-byte charge
  (`pool/index.rs:80,131,151-158,236`), about 3.0 MiB derived. `candidates.rs:104-106` takes
  `size_of_val` of a boxed slice, so `candidate_index_bytes()` (`owner.rs:418`) reports the
  fat-pointer size rather than the declared index bytes.
* **Stale ledger text.** `content-io-memory-audit.md:144` declares a "requested 32-MiB
  cache/connection, mmap0"; no `cache_size` or `mmap_size` pragma exists anywhere in `core/`
  (`connection.rs:29-45` is the entire profile). The engine's page cache and MEMORY journal
  are therefore charged to no budget, and connection multiplicity is unbounded
  (`cas/store.rs:91` clones the handle).

### 2.9 F9 (S3) - latent traps in the extended code

* `pack/placement.rs:83,86` uses the constants `GROUP_COUNT_LIMIT` and `PACK_LIMIT` where
  `lane.group_count_limit()` and `lane.pack_limit()` exist (`pack/layout.rs:108-137`).
  Unreachable today, because a Singleton record is planned only when its contribution already
  exceeds `pack_limit` (`encoding/full.rs:189-201`), so the probe can never accept a second
  Singleton group. It becomes a hard `Integrity("pack group count")` failure the moment those
  two limits move apart.
* `encoding/delta/select.rs:186-194` returns `encode_full` for `InodeLeaf`, but
  `cas/owner.rs:385-387` already intercepts `InodeLeaf` before `select` is reached, so the
  branch is dead. It is also why `StorageCapacities::delta_depth_for_role`
  (`storage/policy.rs:315-320`), which maps every non-`Chunk` role to the **whole-file**
  depth, is harmless today: a future caller that routes `InodeLeaf` through `select` would
  silently use depth 8 instead of the persisted `metadata_delta_max_depth`.
* `StorageCapacities::chunk_canonical_limit` and `chunk_frame_limit`
  (`storage/policy.rs:245,247`) have **no readers** in product code or tests. The former is
  computed as `chunk_raw + 21` while the canonical bytes-role envelope is
  `HEADER_LEN + VALUE_LEN_BYTES = 13` (`content/object/codec.rs:18,23`); the true value is
  32 781, not 32 789.
* `content/file/mapping/codec.rs:96-97` encodes with `node.validate(true)`, so the
  `MIN_ENTRIES` (64) rule for non-root pages (`mapping/types.rs:156-160`) is enforced only on
  **decode**. `file/edit/tree.rs` accordingly passes `root = true` at ten call sites where
  the node is not the tree root (`:402,403,429,438,449,461,475,484,495,507`). The final
  `commit_node` pass re-decodes every reached child with `root = false` (`tree.rs:185-192`),
  so a non-canonical page is caught before emission; the invariant holds, but only through
  the emission path, and unreached drafts are never validated.
* `content/policy.rs:183` (`OBJECT_ENVELOPE_BYTES = 23`) and `storage/policy.rs:75`
  (`OBJECT_ENVELOPE_OVERHEAD = 23`) both name a 23-byte envelope that is 13 bytes.
  `whole_file_canonical_limit` is therefore 10 bytes generous, and `encoding/codec.rs:71`
  lands on the correct raw limit only because it subtracts the same wrong constant. No
  reachable over-acceptance was found.
* `cas/owner.rs:673-674` charges `(depth + 2) * METADATA_RECORD_LIMIT (8192)` against the
  fixed `METADATA_CHAIN_ENCODED_LIMIT` 139 281 (`policy.rs:108`), so an accepted metadata
  depth above 15 can never be used even though the policy accepts up to 50 and persists it
  (`policy_capacity.rs:241-245` asserts persistence only). The handoff says "accepting a
  field never used is failure" (`:157`).
* `delta/read.rs:103` resets the shared `ChainCounters` on every resolution, so
  `SaveOutcome.chain` (`owner.rs:805`) reports the last chain, not the save total.
* `pool/value_group.rs:50-53` compression and its reader `pool/read.rs:121` are unreachable
  from every test: fixtures are BLAKE3-derived and `fresh` is deduplicated, so group bodies
  are incompressible and the `Zstandard` branch never executes, although E1 names
  "body/digest/compression".
* `metadata_pool.rs:136` never holds more than 100 values in one group (the leaf cap is 100,
  `inode_leaf.rs:24`), so the multi-group branch at `owner.rs:576` is not exercised;
  `delta_chains.rs:166` injects a non-existent id, leaving the role check at
  `delta/read.rs:140-142` unexercised.

### 2.10 F10 (S2) - documented format/design deviations to confirm with the owner

Read against `physical-encoding-and-packing.md:270-284`:

* The table names **v6 = "Active pooled physical inode metadata"**. The implementation writes
  pooled **value groups** in v6 (`cas/owner.rs:588`, `encoding/pool/value_group.rs:102`) but
  writes pooled **leaf** records in the v1 Ordinary lane (`cas/owner.rs:492,505,515,524`;
  read back at `encoding/pool/read.rs:228`), distinguishing them by the `objects.object_role`
  column. It is self-consistent and tested (`physical_formats`), but it is not what the design
  table describes.
* The table names **v5 = "Supported older unpooled metadata reader"**. The candidate rejects
  v5 explicitly and by design (`stages-3-4-report.md:104`). It could not act on such a pack
  anyway: its schema identity is `application_id = 1279677261`, `user_version = 4`
  (`sql/schema.sql:10-11`), deliberately not the reference's. This is a scope statement, not a
  defect - but it is a deviation from the design table that should be recorded explicitly
  rather than left as "unknown version rejected".

### 6.7 Memory safety

* The only `unsafe` in `core/` is `core/crates/layerfs-storage/src/encoding/codec.rs`
  (12 sites, each with a SAFETY comment, no `unsafe impl Send/Sync`).
  `layerfs-content/src/lib.rs:16` and `layerfs-telemetry/src/lib.rs:13` are
  `#![forbid(unsafe_code)]`.
* Decompression-length handling is correct: the destination is sized from the caller's
  `raw_length`, the frame's `frameContentSize` is compared before the call and the return
  value after it (`codec.rs:428-451,486-515,544-562`); no allocation is derived from an
  untrusted frame field.
* The two zstd FFI questions raised by the raw-sys usage were resolved against the pinned
  vendored C source: an undersized static `CCtx` is a detected error
  (`zstd_compress.c:2168`), and the `assume_init` at `codec.rs:605` is sound
  (`zstd_decompress.c:479,486`). A natural misreading was also corrected:
  `ZSTD_d_windowLogMax` is not the enforcement point (zstd consults `maxWindowSize` only on
  the streaming path); the crate's own `header.windowSize` test is.
* Residual, not a use-after-free: if the prefix-clear call fails, its `?` skips the reset
  that follows (`codec.rs:310-314,521-525`); every public entry point resets first, so the
  next call is clean.
* One uncharged allocation exists: `ZSTD_DCtx_refPrefix` allocates a dictionary context per
  prefix decode, which the module doc's "every allocation is charged before the call" does
  not cover.
* `StorageCapacities` has no `#[non_exhaustive]` and all fields are public
  (`storage/policy.rs:233-277`), so any crate can forge one and reach the unchecked
  `codec.rs:71` subtraction and the `1_u64 << window_log()` shifts.
* **Coverage limits.** No public-input test feeds a hostile frame to the zstd decoder or the
  prefix codec (0 hits for `decompress`, `compress_prefix`, `parse_frame_header`, `zstd` in

* **No heap/RSS/allocation measurement exists in any of the seven evidence generations.**
  Both required memory conclusions therefore rest on declared capacities plus external
  test accounting (`edit_bounds`, `edit_localized`, `memory_bounds`). That is a coverage
  limit, not a safety claim.

### 7.2 Direct answers

**File revisions.** No revision-count cap exists in reviewed C1/C2 code, and no history,
branch, checkpoint or revision entity exists at all - not a crate, not a table, not a type
(the schema declares exactly four tables, `sql/schema.sql:13-69`, and nothing counts or
references file roots). Retaining a root and its dependencies is different from computing it:
construction emits each object once and retains no whole-mapping state, so computing a root
is O(height) memory. Verified: **16 distinct file roots in one save**
(`core_pipeline.rs:189-223`); more than 256 objects streamed in one save; 1 312 distinct root
objects persisted across 1 312 saves (`metadata_window.rs:130-166`, inode leaves - the
file-root count itself was not driven beyond 16). No successful-version rollback: cleanup
deletes only packs above the baseline captured under exclusive ownership
(`cas/owner.rs:856-888`, `sqlite/cleanup.rs:30-76`). A history/revision *service* is outside
Stages 3-4.

**File size.** T is a routing threshold, not a maximum. The whole-file representation is
capped at T - 1 raw (1 048 575 B at the largest accepted T); a chunked file has **no
enforced maximum**. The binding format field is the `u64` logical length, 2^64 - 1 B
(approximately 16 EiB) - derived-theoretical, not a support promise; the extent-side capacity
(2^224 extents at 32 768 B) does not bind first. Largest actually verified: **24 MiB edited
through real public C1 APIs** (`edit_localized.rs:276,423,475`), **5 MiB constructed and
stored in SQLite and read back** (`visibility.rs:54`, `pack_locator.rs:163-201`), and
**2 097 151 B end-to-end through a real Store** in this batch's smoke round (earlier commit
identity). Nothing above those sizes is qualified.

**Files per workspace.** There is no filesystem or Workspace owner in this tree: `core/Cargo.toml`
declares only `layerfs-content`, `layerfs-storage` and `layerfs-telemetry`. Stage 3-4 stores
independent roots and implements **no workspace membership, count or enforcement**. The
workspace cap is deferred to Stages 5/7. Underlying verified scale instead: 16 file roots in
one save; more than 256 objects in one save; 512 pooled leaves (1 024 packs) in one Store.
A 512-object batch or a 128-id query page is a working-set bound, not a limit on how many
files may exist.

**Directory dimensions.** Name-component length (bytes and character rules), full path length,
nesting depth and entries per directory are **all unestablished**; no code implements them
(`object/inode_leaf.rs:1-8` explicitly disclaims directory traversal, inode allocation,
hardlink updates and filesystem-tree construction). The 100-row inode-leaf cap and the
128-entry mapping-page cap are page capacities, **not** directory limits, and host
`PATH_MAX`/`NAME_MAX` are not imported as a core contract anywhere. Stage 5/7 review is
required.

**Workspace size.** The core cannot promise a workspace maximum. There is no owner, no quota
and no aggregate of logical, retained-history, unique-canonical or physical bytes. The largest
retained Store in evidence is 323 584 B (512 pooled leaves whose 51 200 rows would be
4 169 728 canonical bytes unframed - a ~12.9x deduplication effect in that fixture). A
deduplicating store's logical size can differ greatly from its physical size; both are
unbounded here.

**Store/database.** Object ids are 32-byte BLAKE3 (2^256). Pack ids are `i64`, checked.
At most 256 groups per pack and 8 191 records per group. `objects.canonical_length <=
16 777 216`. Metadata ordinals are hard-capped at 2^32 by the schema CHECK
(`sql/schema.sql:40-46`), verified to 131 400. The pack BLOB's only DDL bound is a lower
bound (`length(data) >= 32`); the real bound is the assembly limit (16 781 312 B singleton).
**SQLite engine maxima are environment-dependent and not qualified**: the product sets only
journal, synchronous, temp_store, foreign_keys and busy_timeout; `page_size`, `cache_size`,
`max_page_count` and `sqlite3_limit` are never set, and the build links a system
`libsqlite3`. A database-file maximum is in any case **not** a maximum single file or
workspace. Unimplemented cloud/remote providers are unqualified by definition.

**Edits and concurrency.** At most 4 096 edits per operation, rejected before mutation;
overlap, inversion, out-of-range and reach-into-an-earlier-replacement are rejected with
`InvalidEdit` before any read or emit; the largest exercised stream is 200 edits. Deferred
state is capped at 8 MiB - 1 and is never approached. One writer per Store via a single
`BEGIN IMMEDIATE` with a zero busy timeout - a lost lock is a definite failure, not a wait;
readers are unbounded and never blocked. C1 and C2 contain **no worker pool or thread at
all**, so a fixed-worker limit is not a capacity of this tree.

engine maximum, and every workspace and directory dimension. No multi-terabyte maximum was
allocated, no disk was exhausted, no endurance campaign was started.
