# Deduplication across retained history on one Branch

> **Status:** Draft family `dedup_branch_history`: 20 new timed cases and no
> proof-only cases. Depth 500 belongs to extended qualification; it is not a
> promise of a 1–5 second execution.

## Question and scope

Does retaining many exact Workspace states cost only their unique content and
required metadata? Measure accumulated storage, per-Commit latency/resources,
and exact historical readability for localized, repeated, metadata-only, and
unrelated whole-Workspace changes.

This family explicitly permits **one Branch with repeated successful Commits**
in v0.1.3. It supersedes the old single-Commit draft restriction for these
cases only. Branch fan-out, competing writers, Add, conflicts, and multi-Branch
deduplication remain v0.1.4. The [shared testing rules](testing-rules.md) and
[parent inventory](README.md) own common requirements and release boundaries.

## Fixed Workspace and exact membership

Use exactly one deterministic **1 MiB, 200-file Workspace shard** from the
[shared fixture](testing-rules.md#shared-workspace-fixture), including its wide
directory, regular directory, deep spine, paths, generator, and metadata:

```text
128 files × 1 KiB + 64 files × 8 KiB + 8 files × 48 KiB = 1 MiB
```

Files have unique independently generated bytes and frozen paths/metadata.
Qualify chunk intersections rather than assume small files contain no repeats.
Use one Store, LayerStack, genesis Layer, Branch, and real-FUSE Workspace for
the complete history. N is the number of **successful retained `Created`
Commits**, with tiers `1, 10, 100, 500`. Each row expands to four scenario IDs
using those suffixes.

| Scenario prefix | Work before each Commit | Public surface |
| --- | --- | --- |
| `dedup-history-distributed` | One 64-byte same-length replacement, cycling a seeded permutation of all 200 files; replacement changes on later visits | One singular SDK file-range edit |
| `dedup-history-hotset` | One 64-byte replacement cycling the fixed eight 48 KiB files; later visits receive new bytes | One singular SDK file-range edit |
| `dedup-history-recurring` | Replace one fixed 48 KiB file in full, alternating exact deterministic B and its original A | One singular SDK full-range replacement |
| `dedup-history-metadata` | Toggle one file's mode between 0600 and 0640; preserve payload and all other metadata | Ordinary FUSE `chmod` in one completed public Exec |
| `dedup-history-unrelated` | Rewrite **all 200 files** with unrelated deterministic bytes of their original lengths, close/sync, then Commit | One public Exec running one compiled ordinary filesystem workload |

There are **20 timed IDs and 60 timed samples**. A fresh tier sample executes
its entire N-Commit history; its schedule is an exact prefix of the same
500-Commit seed/profile schedule, not a resumed Store from a smaller timed
tier. Generated replacements always differ from the current bytes; mode
toggles differ from the current mode. The SDK batch API is same-file only,
so it cannot replace the stated multi-file call count.

Use zero-based Commit ordinal `k`. Distributed edits choose the `k mod 200`
member of a seed-ranked permutation of shard file ordinals; hotset edits choose
the `k mod 8` member of the seed-ranked ordinals 192..199. Both replace the
64 bytes centered at `file_length / 2`, using distinct replacement bytes
generated from family/profile/seed/k before the operation timer. Recurring
targets file ordinal 192: even k installs B and odd k restores A, using
`WorkspaceFileReplacement::Inline` for the complete 48 KiB range. Metadata
targets ordinal 0: even k sets 0600 and odd k restores 0640. Unrelated rewrites
generate all 200 replacement files from profile/seed/k/file ordinal. Bind the
permutations, exact replacement hashes, modes, and manifests to the source
seal; no current result or clock chooses the next operation.

The unrelated profile is the necessary negative control for storing new
complete snapshots, not a latency peer for a single 64-byte edit. At depth
500 it performs **500 public Exec calls and 500 Commits**, rewriting 100,000
files and 500 MiB in total. This preregistered POSIX/FUSE tool operation is not
an emulation or timing of an SDK edit. Compare each profile only against the
same declared profile/surface. Its actual work and wall belong in the extended
lane; do not substitute one edited file, skip intermediate publications, or
claim a few-second full history.

## Byte ceilings and retention denominators

Every visible Workspace state is exactly 1 MiB; the largest file is 48 KiB.
Count genesis plus N retained states, including repeated content roots as
distinct committed snapshots with distinct Commit identities:

```text
retained logical snapshot bytes = (N + 1) × 1,048,576
maximum at N=500 = 525,336,576 bytes = 501 MiB
```

No-op attempts, failed attempts, verifier reopenings, and `UpToDate` results
do not add a snapshot or increase the denominator. Report attempted, Created,
and UpToDate counts separately and fail membership if fewer than N Created
Commits result. Do not deduplicate repeated snapshot identities out of the
logical denominator, or include them more than once.

Stream replacement generation and historical verification; at most one bounded
replacement/verification buffer is live, and at most one historical projection
is mounted at a time. Do not materialize all historical snapshots as ordinary
files alongside the live Workspace. Retained logical snapshots, current files,
temporary logical artifacts each receive explicit ledgers under the shared
<1 GiB total and <=500 MiB per-file rules. Actual Store/spool allocation has
its separate physical disk budget, as the shared rules require. This fixture
leaves headroom even when a current state is counted separately.

## Operation and timing

Prepare and seal the genesis outside the history timer, using the existing
fixture/custody infrastructure. On the same Workspace, execute the declared
mutation, wait for any Exec to terminate, and call
`Client::commit_workspace_session_with_status`. Require `Created`; record
Commit ID, parent, root, head, call counts, phase durations, and available
product counters after acknowledgement. The next mutation follows that
acknowledgement. Do not Add the Commit as another Layer.

The distributed, hotset, and recurring profiles use exactly the stated public
SDK content-edit route, with an attached real FUSE projection and no
edit-caused FUSE payload writes. Metadata and unrelated whole-tree rewriting
use their declared native operations and are not called SDK range edits.
The unrelated process independently regenerates bytes, opens each existing
file, writes its complete declared new contents, closes it, restores the frozen
mtime, and performs its declared sync before exit. No per-file process launch
or cached completed snapshot replaces this work. Active processes or pinned
handles cannot be silently bypassed to make owner-side edits work.

Record per-edit aggregate, per-Commit, history-construction, Workspace Create,
and End walls separately. Do not put transcript construction, historical
queries, complete Store scans, digesting, resource sampling not permitted by
the shared contract, reconnect, or FUSE verification inside operation timers.
Cheap acknowledgements/counters must obey the declared collection boundary.

## Payload, metadata, and physical accounting

Use the [exact transcript model](dedup-cross-file.md#exact-payload-and-storage-accounting)
for every retained regular-file root. Maintain distinct sets for genesis,
previously retained history before each Commit, the current state, and the
union of all retained states. The union includes chunks no longer referenced
by the latest state but still required by an older Commit.

Report for every step and cumulative history:

- attempted/created Commit counts, roots, changed file counts and bytes;
- regular-file payload occurrences, referenced extent bytes/source offsets,
  distinct chunk payload and canonical bytes, newly inserted bytes, emitted
  preexisting CAS reuse, and borrowed unchanged extents;
- distinct namespace/metadata canonical objects and actual inserted/reused
  bytes, even when file payload is unchanged;
- retained logical snapshot bytes versus distinct retained payload bytes,
  current-state logical bytes, and unique bytes introduced by this step; and
- actual SQLite length/allocated blocks/live pages, canonical bytes by role,
  transaction maxima, spool and temporary peaks, CPU, RSS/cgroup memory,
  swaps/OOM, I/O, and execution/output/lease retention.

Savings against retained logical snapshots is an honest **history-sharing**
measure, not proof that the same quantity was newly emitted and CAS-deduplicated.
Borrowed unchanged extents and emitted CAS hits remain separate. Actual Store
growth also includes Commit records and metadata; monitor `saved_fraction` and
`physical_bytes` alone cannot establish retained-history disk cost.

For metadata-only histories require zero new **regular-file payload** chunks,
not zero total objects or zero database growth. For unrelated rewrites require
the sealed new payload set each step and preserve every older set. For local
edits retain the exact oracle-defined extents and chunk sets rather than
requiring a fresh whole-file CDC transcript that the incremental representation
does not promise.

For recurring A/B, full-file replacement makes the input content relationship
explicit. Seal the canonical transcript expected for that operation before
admission and compare each recurrence with the earlier state. A zero-new-chunk
gate is justified only when the expected transcript is the earlier transcript.
Do not generalize it to arbitrary SDK partial reversion: equal visible bytes
can be represented by different valid borrowed extents, and unchanged extent
borrowing is not an emitted CAS hit. Exact byte reappearance and retention are
mandatory regardless of that distinction.

## Historical verification and completion

In a separate verification run, reconstruct the deterministic schedule and
verify **every retained Commit**, not only earliest/middle/latest examples.
After fresh Store reconnect, enumerate Commit records using
`Client::query(Query::new(QueryKind::Commits))`, including continuation pages.
The current implementation enumerates the Store; it does not apply the
LayerStack filter to Commit queries. Match the exact Commit IDs retained in
this trajectory's receipts and check parent/head/root topology. Do not invent
a Branch-scoped historical query or file-read API. Reuse the
existing read-only canonical verifier to authenticate each root's complete
file-payload/metadata graph and stream all expected bytes. Query returns Commit
records, not a new historical file-read API.

For real-FUSE historical readback, use the existing public
`Client::fork_branch(name, LocalForkSource::Branch { branch_id, commit_id })`
route and create/end one
historical Workspace at a time. Verification-only Branches/projections are not
timed history members or a Branch fan-out claim; their allocation and readback
walls stay in verification receipts. Freeze the original one-Branch storage
measurements before these verifier-created Branches, never include them in
history-sharing denominators, and clean up their runtime resources. Do not add
a product API solely for the verifier.

The final state, all historical states, recurrent A/B bytes, untouched paths,
canonical roots, metadata, and released cleanup behavior must be exact. No
GC or compaction may remove history to improve this family's growth metric.
No additional persistent index, sidecar, format, or benchmark-only API is
authorized.

Run three fresh seed samples per ID. Reuse pristine genesis preparation and
existing family selection, source sealing, result reports, and SDK runner
adapters; extend their operation-count schema for this declared repeated-Commit
family rather than weakening inherited one-edit admission. Small selected
histories may target the shared fast loop. Freeze realistic extended budgets
for depth 500, retain all valid samples, and report baseline limitations without
silently truncating the retained history.
