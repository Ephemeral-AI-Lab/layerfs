# Reuse of content already stored before Workspace additions

> **Status:** Draft family `dedup_workspace_reuse`: 12 new timed cases and no
> proof-only cases. No implementation or evidence is admitted by this document.

## Question and scope

When an agent independently writes new files, does Commit reuse content already
durable in its base, and what additional payload, metadata, CPU, and storage does
it require? This is an ordinary file-creation workflow followed by public
Commit, not an SDK range-edit or cross-file import claim.

The [shared testing rules](testing-rules.md) own common requirements. Reuse
[cross-file deduplication's](dedup-cross-file.md) exact payload/Store accounting,
but take the preexisting chunk set from the prepared base. Importing the base
is outside the measured addition; a matching pristine prepared Store may be
reused as an independently writable sample input under custody.

## Exact membership

The genesis contains **128 independently generated, unique 1 MiB files**.
Every case adds `N = 1, 10, 100, 500` new files, each exactly 1 MiB. Each row
expands to suffixes `-1`, `-10`, `-100`, and `-500`.

| Scenario prefix | New file i | Required payload result |
| --- | --- | --- |
| `dedup-workspace-exact` | Exact regenerated bytes of base file `i mod 128` | No new regular-file payload chunk bytes; existing content root reused |
| `dedup-workspace-local` | Same selected base with a distinct 64-byte interior XOR change | Exact frozen local sharing and incremental insertion |
| `dedup-workspace-unique` | Unrelated deterministic 1 MiB stream | Exact new payload set with no unintended base/new intersection |

There are **12 timed IDs and 36 timed samples**. Profile/seed schedules are
fixed 500-file sequences with nested prefixes. Exact and local profiles share
the declared base-index schedule; the local profile rejects duplicate complete
output digests. Unique fixtures are qualified against the whole base payload
set, not only the particular file selected by another profile.

At N=500, base plus additions contains **628 MiB = 658,505,728 bytes**. There
is no temporary full-size copy of the additions inside the Workspace. Each
file is opened, streamed, and closed sequentially with a bounded buffer. Any
runtime spool is separately accounted for under its physical disk budget;
workload artifacts remain subject to the shared logical size rules. No cap is
inferred merely from a dedup ratio.

## Authentic operation and phases

Prepare one Store, LayerStack, genesis Layer, and Branch. The measured product
workflow creates a real-FUSE Workspace, invokes one fresh process using
`Client::exec_workspace_session`, and creates/writes/closes the N files through
ordinary filesystem calls. Regenerate deterministic bytes without reading or
cloning the base file. Do not use a hard link, reflink, sparse file, direct
Store insertion, borrowed-range API, or precomputed root as a substitute for
independent writes.

The process uses the family's declared final sync and exits; observe its
receipt, then call `Client::commit_workspace_session` exactly once and require
`Created`, followed by End. Report create, Exec/workload, sync, Commit, and End
separately. Neither process launch nor output polling is reported as Commit
latency. Separate verification reconnects and reads the exact committed root
through canonical traversal and real FUSE; it is not in performance timers.

Normalize modes and mtimes from the sealed manifest, setting parent times
after children. Preserve all base file bytes and metadata. New names and
namespace objects are expected, so "zero inserted payload" must not be
misreported as "zero Store growth."

## Oracle and metrics

Before Create, seal the complete base regular-file payload-ID set `P`, path
manifest, canonical metadata, and actual Store state. For each new file seal
expected bytes and full independent CDC transcript. After verification,
partition final regular-file payload chunks into `P` and new IDs and compare
the complete per-file extent transcript, including source offsets where the
representation requires them.

For exact copies require the selected base content root and zero insertion of
regular-file payload chunks. For local variants require the exact expected
intersection and inserted set; do not import the old unqualified 90% floor.
For unrelated files require the qualified unique set. Every preexisting reused
ID must have existed before this operation, and every new ID must be accounted
for once, even if several additions reuse it within the same Commit.

Report separately:

- all new logical bytes written through FUSE and all bytes captured/scanned;
- within-addition duplicate occurrences, emitted preexisting CAS hits, and
  unchanged base extents borrowed without emission;
- the **addition-only** payload denominator and the final Workspace logical
  size; an unchanged 128 MiB base must not inflate the addition savings rate;
- canonical payload, namespace, and metadata insertion/reuse, actual SQLite
  length/allocation/live-page growth, and transaction/candidate maxima; and
- phase walls, CPU, RSS/cgroup memory, swap/OOM, logical/physical I/O,
  spool/temporary peaks and passes, process/output retention, and cleanup.

The monitor's `saved_fraction` and `physical_bytes` remain supplementary. Exact
path count, names, bytes, modes/mtimes, unchanged base manifest, Branch head,
Commit outcome, canonical root, fresh reopen, and no leaked resources are
required independently of the dedup percentage.

## Execution and completion

Use three shared seed samples per timed ID, separate verification, and the
existing namespace/SDK fixture generator, pristine-Store custody, runner,
source seals, report machinery, and public runtime. Adapt only family-specific
operation/result handling; do not introduce another framework or bypass
measured source writes/capture with cached post-workload results.

Selected development cases aim at the shared 1–5 second loop after prepared
inputs; all 500 MiB of additions still belong to the largest workload. Freeze
resource/correctness gates before baseline and honest performance budgets
before candidate optimization. Complete the exact family; no invented target
or reduced prefix can stand in for a failed large case.
