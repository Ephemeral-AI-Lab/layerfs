# Sandbox runtime providers

Status: Current general guide. Native macOS is implemented and host-verified; H21 adds Linux native support, pending Linux host qualification. Docker provider adaptation remains deferred.

`layerfs-sandbox::provider` defines object-safe `SandboxProvider` and `SandboxInstance` ports, capabilities, launch inputs, exact partial launch ownership and non-HTTP error construction. `ExecRequest` lives in the shared types layer; its Docker re-export remains compatible. `SandboxId` aliases the existing `ContainerId`, preserving encoded identities and records. The runtime layer has no daemon control dependency.

`NativeMacosProvider::new(root)` and `NativeLinuxProvider::new(root)` are two aliases of the same local provider implementation, with their corresponding instance aliases sharing the existing local runtime owner. Each refuses the wrong platform before root access. macOS uses Darwin process facts; Linux uses the retained #402 `/proc` PID/start/boot checks, process groups and lazy FUSE detach. Linux requires a root daemon and a root directory traversable by command users; ordinary commands keep #402’s nonroot identity (Node selects 501:20) and fixed container PATH. macOS keeps the caller identity, inherited PATH and loopback NFS. The provider explicitly selects `LAYERFS_KERNEL=fuse` on Linux and `nfs` on macOS and rejects conflicting launch overrides. Launch preserves the original single-attempt process lifecycle, native identity, inherited PATH, NFS environment and partial owner on failure. `inspect` reports exact process liveness; unknown exit/storage facts stay absent. Records remain the Node binding’s responsibility; providers neither scan directories nor infer project ownership. B8 list aggregation and doctor remain future work.

`SandboxApi::with_provider(Arc<dyn SandboxProvider>)` and `create_provider_file(ProviderCreate, store, manifest)` launch a provider and return `ProviderSandbox`. Before launch, API validates authentication identities, selected Store, command identity and local resource ownership: overlay and mount home must belong to the instance, Store must live outside it, and native listen uses dynamic loopback. API encodes daemon configuration, then uses the shared TCP/Noise/Hello and Store-install pipeline in `sandbox/connection.rs`. Failures retain their phase, original cause, runtime, control, observed status, installation acknowledgement and handshake work. No automatic retry or cleanup occurs in API.

Both Linux and macOS Node bindings select the provider with `deploy.sandbox: "native"` / `LAYERFS_SANDBOX=native` (the current #427 name), `deploy.localDir` / `LAYERFS_LOCAL_DIR` and `deploy.daemon` / `LAYERFS_DAEMON`. Docker remains the default and the former `local` selector/records remain refused. Linux opens its Store directly in the caller process without a worker. The Node binding uses this path, transfers the original control owner with `internal::split_provider`, and retains its existing native records and explicit cleanup policy. Local command execution delegates through `Box<dyn SandboxInstance>`; record reopen still validates the existing directory/PID/start/boot/port fields and wraps the same local instance. No record migration is required.

For compatibility, Docker callers retain `SandboxApi::new(Docker)`, `SandboxCreate`, `ManagedSandbox`, `internal::split/parts/exec` and ordinary streaming Exec handles. This thin legacy path shares authentication, Hello and install with providers. `internal::split_provider/provider_parts` provide the equivalent instance/control access for providers. Fully adapting Docker and unifying its public runtime/Exec handles is deferred; there is no new Docker launch option pretending to implement it.

The Store remains explicitly Disposable/WAL/OFF. Native macOS keeps #427’s direct Store access without a worker; this refactor does not change persistence authorization or filesystem semantics.
