# Legacy transport comparison and the smallest useful next design

> **Status:** Research; informative and not a product contract.

Source review dated 2026-09-20. Legacy baseline is tag `v0.1.6`, peeled commit
`44cf748486863ab7c21ca47e731bd88e2b9a7b4a`. At review HEAD
`795fb1a2f792742a2b19fdb82d98e6fd8a8b0470`, the root `crates/` changes since that

The v0.1.7 side is the proposed [design packet](README.md), not an implemented
replacement transport. Counts below are source-derived application exchanges,

Three parallel source reviews covered host/daemon transport, FUSE/Workspace
behavior, and dependency/minimality. No production changes, builds, tests,
benchmarks or issue updates were performed for this comparison.

## 1. What v0.1.6 actually does

There are two communication planes, and their logical directions differ:

```text
 HOST                                                 LINUX CONTAINER
 +--------------------------------------+             +-----------------------+
 | SDK -> Workspaces / Docker lifecycle |-- control ->| layerfs-daemon        |
 |                                      |             | mount / exec / close  |
 | RemoteWorkspace                      |             |          |            |
 |   BackingOwner + BackingServer        |<-- reads ---| FUSE + LiveOwner      |
 |   workspace, branch, head, base,      |             | namespace + handles   |
 |   pending snapshot/completion state  |-- capture ->| pending local edits   |
 |                                      |-- pull ---->| frozen records/spool  |
 |   construct + Store + history        |<- payload --|                       |
 |                                      |-- complete->| rebase local state    |
 +--------------------------------------+             +-----------------------+
```

The host starts/mounts/stops execution through the daemon control protocol. The
container connects back to the host backing server for immutable-base access and
establishes reverse-control lanes for host-driven snapshot work. The actual
daemon mount uses `LiveOwner`; the generic proxy client is not a substitute for
tracing that production route.

Sources: [daemon mount assembly](../../../../../crates/layerfs-daemon/src/main.rs),
[host remote backing owner](../../../../../crates/layerfs-workspace/src/live_backing.rs),
[live owner](../../../../../crates/layerfs-fuse/src/live_owner.rs),
[live transport](../../../../../crates/layerfs-fuse/src/live_transport.rs).

Important existing optimizations must be credited:

- Writes accumulate in a sandbox-local piece tree and spool; a FUSE write is not
  automatically a host RPC. Overlay reads and immutable-cache hits can also be local.
- A cold base read requests a logical range, not one RPC per canonical object.
- Lookup can return sibling metadata and small-file prefetch; directory requests
  are paged. Avoid replacing this with mandatory resolve-then-stat network calls.
- Data, control, observation and snapshot lanes are persistent and have isolation
  purposes. Execution stdout/stderr is pushed rather than polled per output chunk.
- Payload acquisition already uses a shared bounded segment cache: up to 1 MiB
  per fetch and an 8 MiB operation cache. Multiple pieces can share a fetch.
- Direct local backing dispatch, bounded framing, vectored writes and authentication
  bound to the initial request already exist.
- The daemon already has no native Store/SQLite dependency. C1/C2 object work is
  already host-local on this route.

Sources: [live owner and local writes](../../../../../crates/layerfs-fuse/src/live_owner.rs),
[snapshot segment input](../../../../../crates/layerfs-workspace/src/snapshot_input.rs),
[daemon client authentication/output](../../../../../crates/layerfs-daemon/src/lib.rs),
[daemon dependencies](../../../../../crates/layerfs-daemon/Cargo.toml).

The principal complexity is the host's knowledge of Workspace/snapshot lifecycle
and the FUSE package's ownership of transport/runtime behavior. It is not an
absence of streaming, batching or platform separation.

## 2. Where the serial network waits are

For a normal successful nonempty remote Commit, after setup:

```text
 host                                                daemon / LiveOwner
   | CAPTURE -------------------------------------------->|
   |<-------------------------------------- frozen result |
   | SNAP_RECORDS(page) --------------------------------->| repeated P times
   |<--------------------------------------------- records|
   | SNAP_READ(segment/range) --------------------------->| S cache misses
   |<----------------------------------------------- bytes|
   | [local construction + conditional Store publication] |
   | COMPLETE_BEGIN ------------------------------------->|
   |<-------------------------------------------------- OK|
   | COMPLETE_NODE(page) -------------------------------->| ceil(R/128) times
   |<-------------------------------------------------- OK|
   | COMPLETE_END --------------------------------------->|
   |<-------------------------------------------------- OK|
```

Let P be frozen-record page requests, S actual payload-fetch cache misses, and R
completion records. The established-lane exchange count is:

```text
 E_legacy = P + S + ceil(R / 128) + 3

 P >= 1; R is completion-node count, not necessarily file count.
 S is actual cache misses, including any refetch; not simply file/piece count.
 Example P=1, S=1, R=1: 6 request/reply exchanges.
 Empty frontier: CAPTURE + one records page + SNAP_CANCEL = 3 exchanges.
```

The group helper holds a lane but awaits each exchange in sequence. Its name
does not mean the requests are pipelined. A response already contains status and
body together: there is no additional mandatory poll/ACK/fetch-body triplet.

## 3. What the current v0.1.7 proposal improves, and what it does not

| Area | v0.1.6 source | v0.1.7 proposed direction | Assessment |
| --- | --- | --- | --- |
| Service ownership | Host BackingOwner carries Workspace/branch/head/base/snapshot state | Authorized explicit-root operations; Workspace state stays caller-side | A clearer boundary with less host coupling, once implemented |
| Transport placement | FUSE package contains live transport, wire, owner and projection behavior | Neutral bridge, service library/binary, execution daemon | Allows headless and future FUSE callers to share operation handlers |
| Native dependency isolation | Linux daemon already excludes Store/SQLite | Default remote daemon still excludes service/C2/SQLite | Preserve an existing strength; not a new saving |
| Direct path | Local backing dispatch already exists | Same authorized logical service handler through direct and streamed delivery | Broader semantic consistency, not invention of direct calls |
| FUSE writes | Local accumulation already avoids per-write RPC | Preserve bounded Workspace accumulation in pair 1 | No automatic roundtrip reduction on this path |
| Cold reads | Logical range RPC with caching/prefetch | Logical ReadFile plus bounded metadata queries | Often the same request count; avoid metadata-query regressions |
| Save payload | Host pulls segment misses with serial replies | Daemon pushes stable bounded input without per-frame application ACK | Removes payload-dependent request/response barriers for supported input routes |
| Multi-file update | One captured changed frontier, paged transfer/completion | Initial N file operations plus one tree update | N+1 exchanges can be worse for many small files; not yet a batch win |
| Lane isolation | Separate data/control/observer/snapshot lanes | Initial single active operation per connection | Simpler prototype, but pair 1 must address read/control head-of-line blocking |
| Failure recovery | Pending completion and retained-attempt redelivery exist | Explicit failure/unknown outcome; no automatic resend | Fewer recovery states, with an intentionally different caller contract |
| Cloud portability | Native host owner and native storage | Neutral operation surface; later C2 provider/lifecycle adaptation | Better preparation, not managed-runtime support or durability |

Legacy host coupling is visible in
[BackingOwner/RemoteWorkspace](../../../../../crates/layerfs-workspace/src/live_backing.rs)
(950-1022); the broad SDK assembly in
[client.rs](../../../../../crates/layerfs-sdk/src/client.rs) (27-30, 76-103).
The proposed replacement boundaries are in [document 02](02-file-layout-and-boundaries.md).

## 4. Recommended refinement: bundle network work without requiring atomic storage

Keep the five initial operations for the pair 3 foundation. Before claiming an
efficient pair 1 multi-file path, design one bounded **SubmitChanges** operation
(name provisional). This is a recommendation, not an added frozen opcode.

```text
 daemon / Workspace                              common service handler
 freeze a bounded generation locally
 BEGIN(changes, limits, base root) ----------------------> validate / admit
 metadata + file1 bytes + file2 bytes + ... ------------> save files locally
 END_INPUT --------------------------------------------> update filesystem
 <---------------- streamed bounded reconciliation result + terminal outcome

 No READY per file. No pull request per segment. No ACK per result page.
 File roots, record counts, replay and total input/output remain capped.
```

Two storage implementations have different contracts:

1. **Sequential existing saves:** save each file through existing C1/C2, retain a
   bounded operation-local input-ID-to-root map, then save the filesystem update.
   Already retained roots are readable by its ordinary provider. This can be one
   network operation while still performing N+1 local save operations. Earlier
   saves may remain unreferenced if input or a later step fails; do not claim
   all-or-nothing storage, guess cleanup, or automatically replay. Validate the
   required pair 1 semantics before choosing this route.
2. **One atomic combined save:** content and filesystem update share a save with
   authenticated visibility of its unpublished outputs. That needs an explicit
   reader/consumer ownership proof; it is not available merely because
   `SaveOperation::read_batch` exists. Implement only if the required semantics
   justify it, separately from the network bundling decision.

Thus a single network exchange does not depend on first rewriting C2 for atomic
composition. Conversely, bundling alone does not eliminate N+1 local save
operations, each of which may use multiple bounded SQL transactions, or guarantee
lower CPU. The initial five-op surface remains N+1 exchanges; this
recommendation must not be advertised as already implemented.

The result must preserve the information Workspace needs to rebase: saved roots,
input-generation identity and bounded inode/content reconciliation where required.
Legacy completion supplies such mappings. One streamed response can replace
page-by-page acknowledgements, but cannot simply discard that semantic work.
Old roots, open handles and later writes must remain correct after completion.

Existing C2 [same-save read](../../../../crates/layerfs-storage/src/cas/store.rs)
and C1 [reader/consumer composition](../../../../crates/layerfs-content/src/filesystem/objects.rs)
are separate capabilities; [document 03](03-operations-and-transport.md) states
the current supported composition limit.

## 5. Prepare pair 1 without rebuilding the old coupling

- **Retain local write/read-your-write behavior.** Pair 1 owns freeze generations,
  overlays, handles and bounded backing. These belong in a reusable Workspace
  layer, with a thin FUSE adapter; service handlers stay independent of mounts.
- **Use logical metadata queries.** A lookup response should contain the identity
  and attributes the caller needs. Do not require resolve followed by a second
  remote stat; C1 already returns a resolved inode value. Preserve useful bounded
  sibling/small-file prefetch only with explicit cache/work accounting.
- **Keep directory consumption incremental.** The legacy live owner refreshes all
  backing directory pages into local state before serving paged results. A new
  bounded page/cookie design could avoid acquiring an entire directory just to
  return its beginning; concurrent mutation/cookie semantics must be specified.
- **Advance a frozen-frontier cursor instead of rebuilding its ID list per page.**
  Legacy `SNAP_RECORDS` collects frontier IDs and scans past `after` again for each
  page ([live_owner.rs](../../../../../crates/layerfs-fuse/src/live_owner.rs),
  2781-2857; [frozen.rs](../../../../../crates/layerfs-workspace-core/src/frozen.rs),
  65-71). For M frontier entries and P pages, that can repeat O(M * P) traversal
  and temporary-ID work. A single ordered traversal with a retained position can
  remove that repetition while preserving generation checks. Streaming frames
  alone do not fix this algorithm or the whole-frontier metadata budget.
- **Preserve responsiveness with the smallest justified lane policy.** Qualify the
  single-operation connection first. If a bulk save blocks required reads/control,
  consider a small fixed number of bounded connections before a general multiplexed
  scheduler. Enforce aggregate caps and the existing single construction producer.
- **Keep execution control separate in meaning.** Mount/exec/stop and process output
  are real legacy capabilities. The pair 3 headless operation client does not
  replace them. Pair 1 must decide which process/lifecycle controls it needs and
  how they are delivered; do not embed Docker orchestration into core or claim
  equivalent scope merely because the new wire has fewer opcodes.
- **Reuse behavior, not reference-crate dependencies.** Preserve checked framing,
  partial-write handling, auth, bounded buffers and direct dispatch. Do not import
  the legacy FUSE owner/protocol wholesale into the neutral bridge.

The current C1 [resolve/stat/list APIs](../../../../crates/layerfs-content/src/filesystem/read.rs)
support the metadata direction above. Kernel/FUSE semantics and callback fairness
remain pair 1 design and test work, not properties proved by those APIs.

## 6. Close real boundary gaps before claiming equivalence

The proposed wire error taxonomy must match what local APIs preserve. Current
[StoreProvider error mapping](../../../../crates/layerfs-storage/src/cas/provider.rs)
(31-52) distinguishes missing objects from provider failures but maps several
storage causes, including capacity and engine errors, to `ProviderFailure`.
A service must not recover lost structured categories by parsing message strings.
Keep those reads in the preserved provider-failure class, or review an explicit
error-preservation correction if the operation contract needs finer detail.
Bridge admission errors, direct C1 errors and save errors can retain their own
available typed distinctions.

The new transport is better prepared for deployment changes because its caller
does not require the legacy host SDK/Workspace assembly. It still needs real
authentication, fairness, error, managed-provider and resource qualification.
Native SQLite/zstd dependencies and runtime scratch/lifetime needs remain; no
cloud execution or crash durability follows from this review.

Use the [verification plan](04-resource-and-verification-plan.md) for future
evidence. Add matched pair 1 cases for local writes, cold/cache-hit reads, lookup
prefetch, partial directory consumption, N-file saves, slow receivers and reads
during a save. Count serial request barriers separately from frames, bytes, local
save calls and history publication. All execution and performance results from
this review are **NOT_RUN**.
