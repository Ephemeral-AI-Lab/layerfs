# Family 3 cold-source/direct-backing qualification profile

> **Status:** Prospective method and gate for the next #286 Family 3 selection. It does not reclassify r043 or historical #273/#248 rows. The nine case IDs, workload, oracle, order, 15/25 s complete-command limits and separate 9 s verifier are unchanged.

Profile ID: `darwin-zero-source-residency-linux-direct-backing-v1`. It applies only to the public `WorkspaceApi` full-lifecycle write matrix on a Darwin host with the Linux aarch64 Docker daemon. A different host requires a separately frozen cache instrument; the LayerFS product/API is not made host-specific by this benchmark profile.

Each cell gets an independently copied, writable C2 Store and C5 history from the sealed #271 master. Copying, SHA-256 validation and closing happen outside the measured child. The harness then flushes those **setup copies** (not Workspace private backing), invokes the already tested `core/benchmark/fs-bench-pro-storage-content/shared/residency.py` de-warm sequence on both files, and checks every source page with `mincore` immediately before launch. Its self-check must detect and evict a known-warm scratch file. Both copies must have zero resident pages, and the check-to-launch gap must be 0–1,000,000,000 ns. No fixture payload is read after de-warming. The de-warm report, allocated `st_blocks*512`, final residency and gap are recorded per cell. Failure prevents or disqualifies that cell; there is no warm fallback.

The Linux product path is pinned to `core/crates/layerfs-workspace/src/backing/segments.rs` SHA-256 `dd2286500231693d0498379f7825af3314cc902f65bdc0b27c122b74b24c735d` and `core/crates/layerfs-fuse/src/adapter.rs` SHA-256 `e361037d9c87ac42dda651e06a708053b999bfa54a69a7e5038a3e1398380fa7`. The former opens Workspace private segment files with `O_DIRECT` and requires aligned reads/writes on ext4; the latter opens writable FUSE handles with `FOPEN_DIRECT_IO` and refuses `FUSE_WRITE_CACHE`. The exact source hashes are enforced before building. Bounded, charged product memory remains part of the product; OS page-cache transfer from Exec's private backing into Commit is not credited.

The host SDK driver's Darwin `proc_pid_rusage(RUSAGE_INFO_V2)` reading reports its own device-read byte delta from the beginning of `main` through completion/cleanup. The frozen corroboration floor is **90% of the sum of the two cloned files' allocated bytes**, integer floor. Null, negative or below-floor readings make the numeric cell `INELIGIBLE`; this is an intentionally conservative whole-source floor. The per-process observation excludes Docker child-process reads and is paired with the zero-residency checks. The driver does not add its verifier to the performance clock.

An eligible cell must also have one completed SDK run, exact expected write callbacks, a known parented Commit, independent complete old/new byte oracle, cleanup PASS, separate verifier ≤9 s, and external launch-to-exit ≤15 s for 100/512 writes or ≤25 s for 4,097. Only then is its numeric status `PASS`. A cache failure is `INELIGIBLE`; an eligible command over its unchanged limit is `TARGET_MISS`/functional FAIL. No average, speedup denominator, resampling or timeout increase applies.

The source method is committed before any selection. Its retained receipt must pin the source/tree, product/harness/dependency seals, helper SHA-256, direct-I/O source hashes, release driver/verifier/daemon hashes, image ID, closed master and independent manifest hashes, copy method, per-cell source residency/device reads, command and verifier walls, functional and cleanup statuses. The previous r043 matrix remains functional PASS/numeric INELIGIBLE under its original uncontrolled-cache profile.
