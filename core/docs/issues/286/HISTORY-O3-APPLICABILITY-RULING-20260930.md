# #286 family-2 O3 method-applicability ruling

> **Decision, 2026-09-30:** The original v0.1.6 canonical pins remain immutable historical FUSE-importer results and remain enforced in the already frozen v1/v2 compound profiles. Their v2 stride3/stride1 FAIL receipts remain FAIL. They are **not an applicable equality oracle** for the fixed-corpus component producer. A separately registered v3 profile uses independent canonical pins generated by the corrected older-Core implementation of that same producer. This is a prospective change of the compared operation, not a retrospective PASS or a storage/timeout relaxation.

The v0.1.6 source `benchmark/fs-bench-pro/shared/deepseek_ten.py` seals source **file bytes** but no mode/mtime vector. Its public Docker/FUSE importer passes file attributes into the old Workspace. In `crates/layerfs-workspace/src/changes.rs`, the persisted metadata root depends on `permission_mode`, `mtime_seconds` and `mtime_nanoseconds`, and Workspace assigns its own inode serials. The fixed `deepseek-history-data` manifest and `oracles/<sha>.json` contain path, kind, mode, size and digest but no mtime; `core/benchmark/fs-bench-pro-storage-content/src/ops/history.rs` explicitly supplies one synthetic metadata root and a deterministic path-serial producer. An equality check of canonical object counts/bytes across those two producers therefore asks unlike input graphs to have identical identities. The absent mtime input cannot be reconstructed or sealed retroactively from the old receipt.

The v2 corrected independent older-Core producer at `6b22835dd57d76ea53bd44561a68f50e0aab756f` yielded stride10 **380,559,460 B/51,689 objects** and stride3 **589,480,854 B/73,447 objects**. A read-only query of that sealed reference Store gives **871,337,620 B/104,618 objects**. This continuation is a functional canonical reference, **not** an uninterrupted speed/command-budget arm. The candidate's complete v2 receipts match these independent canonical counts and all157 sealed roots and fixed-corpus tree/content oracles. Original v0.1.6 pins **589,423,458 B/73,476** and **871,588,115 B/104,705** stay published and failing in v2; no source file, pin, receipt or status is edited to disguise the discrepancy.

The prospective `c1-c2-c5-retained-history-v3` cases keep the exact 17/53/157 state schedule, fixed corpus, C1/C2/C5 operation, one construction worker, complete path/kind/size plus deterministic selected-content oracle, independent [v2 root vectors](oracles/history-reference-v2/manifest.json), C5 public reopen and cleanup rules, exclusive at-run C2+C5 `st_blocks*512` ceilings **<49,344,512 / <64,024,576 / <83,947,520 B**, complete-driver bounds **60/170/170 s**, and separate verifier bounds **10/20/30 s**. V3 uses a new case/profile/receipt/gate and C5 binding/incarnation; its receipts explicitly carry both the applicable reference pin and the original historical pin. It is not pooled with v1/v2. A family-2 checkpoint requires all three new v3 cases to pass at the eventual frozen product source; r008's v2 stride10 PASS and later v2 failures are historical evidence, not a substitute. Numeric time without symmetric cold proof remains INELIGIBLE even if absolute command budgets pass.
