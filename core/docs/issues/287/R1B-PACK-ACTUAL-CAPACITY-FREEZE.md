# Pack loader and actual-capacity cache repair freeze

Prospective source freeze,2026-10-01 after published b98 control. This refines the owned-canonical freeze's deliberately deferred pack repair; no test/build/measurement result is claimed. Existing v1 canonical formats, publication ceilings and all pack versions/limits remain.

The concrete defect is sqlite/lookup.rs::pack_bytes: row.get<Vec<u8>> copies the full allocated BLOB (up to16MiB+4KiB), then truncate changes len but keeps capacity. Ordinary dependency and pooled pack caches charged len, so spare-capacity entries could exceed their4MiB class. The replacement keeps the same SQL primary-key/row-length/publication guards, borrows ValueRef::Blob inside the row callback, validates declared_length against the full borrowed row and format bounds BEFORE a Rust buffer allocation, checks used<=SINGLETON_PACK_LIMIT, requests exactly used with try_reserve_exact, verifies actual Vec capacity<=used, and copies only the validated used slice. Borrowed SQLite native materialization/engine/pager memory is separately unqualified; this repairs first-party Rust capacity only.

The4MiB pack-cache and512KiB decoded-group/value-cache ceilings do not grow. Cached Vecs charge capacity, value cells charge capacity*INODE_VALUE_BYTES, incoming capacity is validated before map retention, and wholesale release remains the crossing policy. Group replacement credits the removed key before admitting its replacement. A single oversized incoming owner cannot remain inside one of those caches.

Compatibility legitimately permits a used singleton body up to16MiB+4KiB. It moves into one explicitly separate current-body slot, never the4MiB cache. Resolver/ChainBases/PoolReader own that slot; account/base/decode reads of the same current body reuse it. Changing pack drops the old current owner before allocating another; the next cache-crossing operation clears retained bodies using actual incoming capacity. A slot has zero allocation while empty, owns exactly one immutable Vec, yields only scoped slices, and data is destroyed when replaced/dropped. Existing public stored_base keeps its signature with a local explicit current slot; wider resolver/bases owners retain their slot across their real traversal. The existing BodyCaches BTreeMap API stays compatible. No native/resource lease or canonical32MiB credit is invented for these packs.

Actual overlap is prior retained pack capacity<=4MiB plus incoming/current used capacity<=16MiB+4KiB (prior current dropped before allocation), ordinary decoded groups<=512KiB, pooled pack cache<=4MiB plus its one current-body slot if demanded, pooled value capacity<=512KiB, existing codec workspace/decoded temporary, current canonical/base/result owners and metadata descriptors. Their simultaneous global8/96/176/process/physical fit is NOT established by these per-owner bounds. The32MiB returned-canonical compatibility grant stays unchanged; no strict8 provider, Store grant/worker/deadline/native-guard change occurs.

Owned edits: sqlite/lookup.rs; encoding/delta/read.rs,pool/read.rs,decode.rs; NEW encoding/pack_cache.rs and encoding/mod.rs declaration. cas/store,lifecycle,provider/read,owner/working/codec remain with their assigned owners. External tests must construct real padded16MiB pack rows, observe requested/live Rust allocation while used bodies are held, validate exact independent bytes/publication/declared-width refusal, cross4MiB caches and512KiB group capacities, cover legal oversized used bodies in the separate current slot, and assert owner lifetime/refund through real allocator observation. Canonical bytes/root/role and existing counters remain owning compatibility checks. No source-only arithmetic establishes a PASS.
