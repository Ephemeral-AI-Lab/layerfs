Status: one model in the API

Every machine, Store, project, Sandbox and Workspace answers one of six states. Each state has the companion fields in this table and no others. The companion says why as a code, never as a sentence. The UI maps the code to a signal; an agent reads the code and the fix.

Companions
op is the recorded operation: {name, phase, started_at}. blocked_by is {<machine|store|sandbox>, reason}. reason is a code from the closed list below. fix is one runnable shell line; two commands are joined with &&. observed_at is when LayerFS last knew the state: the last live read that answered, else when the record was last written. In the short form a state carries its companions and nothing from another state; in the long form every key is present and the others are null.
Reason codes
A closed list: . In blocked_by the reason is the blocker's own state (stopped, busy) or its broken reason. A broken thing's reason is one of . The sentence stays in the long form's message.
One cause, named once
blocked_by names the thing at the root, with that thing's own state or reason: a Workspace in a Sandbox on a stopped machine answers {"machine":"docker","reason":"stopped"}, not its Sandbox. A UI can then show the cause once and fold everything it blocks under it.
Docker not running
The docker machine is broken with reason: engine_down and a fix that starts the engine. stopped means a person stopped the machine, and nothing else.
Records first
A state comes from the home's records and costs no probe. --with live probes and stamps observed_at; only then can a state be unknown. A UI probes machines only; what lives on them inherits.
Where Workspaces are recorded
The home's records hold Workspaces only for a Sandbox on native and for a Sandbox reached directly. Elsewhere the machine's worker keeps them. So home get --with tree, sandbox list and workspace list cannot list those Workspaces from records: a Sandbox row answers workspaces_not_listed:true while its machine is ready, and workspace list --sandbox S asks the machine. A stopped machine's Workspaces are not listed; its Sandboxes answer blocked.
Blocked things stay listed
project.list keeps the recorded projects of a Store it cannot open and marks them blocked; project.get answers the same instead of refusing. Today the all-Stores listing drops that Store's projects, so the UI keeps its own catalog to show them.
Every operation is recorded
machine.start and machine.stop record an op, as create and remove do today, so every client sees busy, not only the tab that pressed the button. This is new work.
A lost reply
When the reply to machine start or machine stop is lost, the recorded op stays with its outcome not known: the machine is broken with reason: unresolved and fix: layerfs machine get <machine> --with live. That live read settles it: it sees whether the machine runs and clears the op. Today the only call that clears an uncertain machine operation is machine remove, which deletes the VM and its disk.
Short form
A get always answers state. A list row leaves it out when it is ready: no news is good news, the same rule the UI follows.
One counter
home.get answers generation, a number that moves when any record in the home changes. A UI polls that one number and re-reads only when it moves, in place of the 15 s and 60 s polls per page. It does not move for a Workspace the home does not record.

  • "Stopped" has four looks: a grey chip on Machines, an amber row and tab, red on the Store page, a grey dot on the Store card.

  • A Sandbox on a stopped machine reads "Running"; lost and unsupported are shown as raw words.

  • Projects have ten UI-made labels and the Storage pages use a second set; a Sandbox is "Running/Stopped", "Active/Not created" or "closed" depending on the page.
  • A failed status read becomes a state: "Not answering" for a machine, the red box for a Store, "closed" for every Sandbox card.

Doctor: a thing and what is on it

Every thing has one owner, and the doctors and the page follow that one relationship. A doctor checks its own thing, then gives a shallow check to each thing directly on it; a project and a bucket also have a Full check. A shallow check is that thing's own checks and nothing beneath it. No option controls depth, no doctor has a records-only mode, and opening the page runs no doctor.

Six doctors, one shape
home.doctor, machine.doctor, store.doctor, project.doctor, sandbox.doctor, backup.doctor. A Workspace has no doctor of its own: sandbox doctor checks it from the daemon's list. Today the whole-home sweep and the per-target checks answer two different reports, and rate the same outdated worker as a warning in one and an error in the other.
Depth
A doctor checks its own thing, then gives a shallow check to each thing directly on it; a project and a bucket also have a Full check, project doctor --full and backup doctor --full. There is no other depth and no option for it. --with never changes what a doctor checks.
Short form
{"ok":true} only when every check was made and nothing was found. Otherwise findings and not_checked, each present only when it has entries. A notice is a finding, so an answer with only a notice has no ok.
Severity
error: the thing does not work until it is fixed. warning: it works and something is wrong (a disk nearly full, a backup behind). notice: a normal state worth saying, which blocks nothing. A check's outcome is pass, its finding's severity, or not_checked. A thing's status is ok when every check passed, else the worst outcome among them; the answer's status is the worst thing in it.
A failed parent
Live checks beneath a stopped, outdated or unreachable parent are not attempted: one not_checked entry each, with blocked_by naming the root cause, no severity. Today the same case is "skipped", "unknown" or a silent return, depending on the check.
Could not check
A check that was tried and gave no verdict is a not_checked entry with reason: timeout (the thing's time budget ran out), busy (an operation holds the thing) or lost (the probe's reply did not arrive). It is never a finding and never ok. A check that does not apply to the thing is left out. Today's unknown and skipped outcomes go away.
Budgets
Each thing has its own time budget; no doctor takes --timeout. A Full check has no budget and runs until it finishes or the caller stops it. Today one 30 s budget covers a whole call.
Progress
--progress sends one event per finished thing: {"phase","done","total","node"}. phase is : self is the named thing, the others are the kind being checked. done and total count things; the total is known from records before the first check. node is that thing's node as in tree, without child lists, so a row's marks can land together. This is new work: today target checks, the records sweep and a worker-run Sandbox report take three different routes, and one call is one target.
Records
One of home doctor's own checks reads every record in the home: references between records, file modes, leases, half-finished operations. A finding from it names the thing it is about, at any depth, and the page shows it on that thing's row. Live checks still go one level only. No doctor takes --offline.
The Store doctor
Checks the Store (its record, the id in its data against the record, its schema, that it can be reached where it lives, no half-finished move or stale lease), then gives each project the shallow check. It stops after the schema check and reads no data; that cut is new work, since today's cheapest mode still scans the file, and it needs a new argument on the worker's Store diagnosis that an older worker will not know. On a PostgreSQL Store it also probes from each machine that has a Sandbox of that Store, and each probe is one check entry with from naming the machine. Without that, Check all could read "All clear" while a Sandbox's machine cannot reach its Store. --machine M adds a probe from one more machine and is for the command line only.
The project doctor
Shallow: the project's record against the Store's own list. This check exists today in project.get and project.list. A project on record that the Store does not list is a normal state after a delete that kept the home entry, so its finding is a notice with a fix, not an error. --full: also reads everything reachable from the head of each of the project's Branches, which is what a mount can reach. It is streamed with bounded memory, writes nothing and changes no format; an object shared by two projects is read once per project. That walk is new work on both engines and through the worker. The whole-Store scan is dropped from the doctors, so nothing checks the database file's structure or data that no Branch head reaches.
Exit code
A doctor exits 0 once its report is made, whatever it found. A doctor that cannot make a report at all (no such thing, a home it cannot read) is a refusal and exits 125.
A doctor never repairs
fix is a runnable command, or null when no command helps. The fix for an outdated worker is layerfs machine stop <machine> && layerfs machine start <machine>; machine start keeps refusing a mismatched worker, and machine stop is refused while Sandboxes run. Today a Sandbox whose machine's worker is down is offered a forced Close.
Leftovers
No doctor walks for them, and home get does not list them: a leftover is disk to reclaim, not a fault. layerfs home leftovers [--machine M] lists what interrupted operations left on each running machine, and layerfs home prune <leftover> removes one it listed, under its guard.

The page

Five status words cover every row, with the reason in the tip:

OK Checking Not checked Notice Problem

From the report: ok is OK, notice is Notice, warning and error are Problem, not_checked is Not checked. "Not checked" carries its reason in the tip: never, stopped, or waiting on a named thing. A finding keeps its own word, such as Outdated.

  • Opening the page runs no doctor. It reads home get --with tree and shows each thing as Not checked. Workspaces appear where the home records them; the others appear when their Sandbox is checked.
  • Head: one headline ("2 problems", "All clear", "Checking… 31 of 38"), one line of counts, and Check all. No problem list and no "needs attention" list.
  • Home chip: this install as one chip with its own Check. Clicking it opens its checks.
  • Tabs per kind: Machines, Stores, Projects, Sandboxes, Backups, each with a count and a mark. A mark counts only trouble that starts in that tab. The mark's slot is reserved, so the bar does not shift.
  • Every row is a folder. Closed, it shows what it has: "4 Stores · 1 Sandbox" on a machine, "2 projects" on a Store. Opened, it lists those things, and each opens the same way, down to projects and Workspaces. Going deeper is opening a folder, not an option.
  • Buttons on every row: Check where the thing has a doctor, and Full check beside it on a project and a bucket. A Workspace has none. While a call runs its buttons stay in place, disabled and marked busy, and the column keeps its width, so focus is kept and nothing jumps.
  • Marks land per finished thing. Each row shows one small mark per check. A row's marks land together when the progress event for its thing arrives, never one by one. A failed mark differs by shape as well as colour, there is one hollow mark for "not checked", and the mark group is one focusable signal whose accessible name says the state.
  • Full check shows a spinner and the elapsed time, with Stop. No percentage: the walk does not know its total. Stop ends the call; it wrote nothing, so the row returns to its last result.
  • Check all is disabled while a fix or a Full check runs, and a row's Check, Full check and fix are disabled while Check all runs. Its tip counts the calls it will make: store doctor <store> ×7.
  • Could not check: one signal, with Check as its action, for a not_checked entry that carries a reason, and for a doctor call that was refused, lost or stopped. The tip says which.
  • A thing whose own check fails shows what is on it as Not checked, with no buttons, and the tip "waiting on" its root cause. That name is a link that opens and focuses the root cause's row. Under a machine stopped on purpose the tip says "stopped", not waiting.
  • The fix button is on the root cause only, in the primary style, with the command in its tip. If the fix is refused the row returns to its previous state with the refusal in its tip, and pressing again is a new call. If its reply is lost the row shows Could not check.
  • An outdated worker's fix runs machine stop then machine start behind one button. The button is off while Sandboxes run on the machine, with their count in its tip.
  • A closed folder with trouble inside keeps its own dot and adds a mark with a count; its accessible name says "1 problem inside".
  • Clicking a row with nothing in it, or a folder with trouble of its own, shows the call, its check list and the fix line with Copy. Nothing there repeats the row as a sentence.
  • Every troubled row has an action or a tip, "Not in the Store" and "Backup behind" included.
  • Tips hang off the dot, open after 120 ms, and say something the row does not.
  • At phone width the status word comes first and is never cut; the reason is in the tip. The tab bar's edge fades where it scrolls.
  • An icon per kind, the plugin's own glyphs: a machine by platform, a Store by engine, the LayerFS mark for a project, the box for a Sandbox, a branch for a Workspace, a bucket by provider. Brand marks draw in the text colour, so colour means state only.
  • Not on the page: a Store's check from one more machine (store doctor --machine), and leftovers, which no doctor reports.
