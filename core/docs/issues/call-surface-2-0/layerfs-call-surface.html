Short form and long form

Short form · default · agents

Only what the call produced: the content asked for, the id or handle the next call takes, and anything that changed. No result tag, no echoed inputs, no revision on reads. Fields that are null, false or empty are left out. An action with nothing to return answers {"ok":true}, and ok never appears beside another key.

$ layerfs file write shop/api agent /src/app.ts < app.ts
{"commit":"12d1c0ff"}
$ layerfs file stat shop/api agent /src/app.ts
{"type":"file","size":4870,"mode":"0644"}
Long form · --detail · UI

Every short key, with the same name and type, plus flat extra keys. Every key of the row's long list is always present, nulls and empty lists included, so a UI reads one stable shape. It adds no I/O; it shows what was already read.

$ layerfs file stat shop/api agent /src/app.ts --detail
{"type":"file","size":4870,"mode":"0644","commit":"7a0b11c2","root":"9f3c0b7a","path":"/src/app.ts","inode":1042,"modified_at":"2026-11-17T09:16:59Z"}
Sections · --with

--with adds one named section to an answer, in either form. It never changes what a call does. The values are live, stats, space, docker, platforms, tree, patch; 10 calls take one or more, and each row lists its own. Anything that probes a machine, walks a disk or reads more of the Store is behind it, so neither form is slow by surprise.

layerfs store get <store> [--with live,stats]
layerfs machine list [--with live]
layerfs commit diff <project> <ref> [--from R] [--path P] [--with patch] [--limit 100] [--cursor C]

In Node the long form is { detail: true } and a section is { with: ["live"] }. In Python they are detail=True and with_=["live"]: a name that is a Python keyword takes a trailing underscore. A UI asks for --detail once, in its client; agents get the short form without asking.

Why this shape

Agents pay for every byte

An agent reads every result into its context, on every call. The short form carries one id for a write, and exit code and output for a command.

mirage, drive9 and cloudflare/computer all answer writes with the path or one id, and command runs with exit code and output.

A read answers what was asked

file stat answers type, size and mode, not the Commit it read. The revision is the caller's to choose (--at) or the long form's to show. A write answers its new Commit, because that is new information.

Carrying the revision on every read invited guards nobody set.

A result feeds the next call

The id a call returns is named like the argument the next call takes: commit out, --at and --expected in; workspace from mount, workspace into exec.

Today workspace.mount answers a 32-hex token in workspace, which exec does not accept; the handle is in ws.

The UI reads one stable shape

The long form keeps every short key and type and always sends every key, nulls included, so a UI can render without guessing. Agents never pay for it.

Results are untyped maps today; each row's long list is the schema.

A screen gets what it needs in one call

Every UI call is a CLI process. List rows carry what a row shows, and probes are named in --with.

Today the UI calls sandbox.get for every Sandbox only to show Workspace names.

Simple, but not by dropping history

LayerFS keeps Branches, Commits, shared Stores and several machines. It hides them behind defaults, short ids and the long form, not by removing them.

Automatic retries, idle shutdown and output files inside the workspace break LayerFS rules and are not copied.

Rules for every call

Call form
layerfs <family> <call> <positionals> [--options]. Two levels only. Positionals go from the outside in: owner, Branch, path or new name. Anything optional is an option, except 6 trailing positionals with an obvious default: file.glob [path], file.grep [path], sandbox.files [path], branch.fork [from], machine.prune [image], machine.files [path]. A shell option is the option's name with - for _. No old call or option name keeps an alias (R1).
Short form
The default, for agents. No echo of inputs, no result tag, no revision on reads, no null, false or empty field. A boolean is named so that true is the news. Each row lists the keys that are always there and the keys that appear only when they are news. ok appears only alone: {"ok":true} is the whole answer when there is nothing else to say, and ok is dropped when any other key remains. The short form is the long form projected onto the row's short keys, with null, false and empty values dropped, then ok dropped if anything is left beside it.
Long form
--detail, for the UI. Every short key with the same name and type, plus flat extra keys. Every key of the row's long list is always present. Where a row has ok, the long form keeps it and it is true; only a doctor's ok can be false, when it has findings or things it could not check. It adds no I/O.
Sections
--with adds one named section to an answer and nothing else. Values: live, stats, space, docker, platforms, tree, patch. A section answers under its own key ("live": {…}), except where a row adds its keys flat to each item or to the top level (live on machine.list; patch on commit.diff; stats on project.list; stats on store.list).
Commits in
--at C pins a read: a full id or a prefix of 8 or more characters, resolved by the Store (12 calls). --expected C guards a write: Conflict if the head moved (10 calls). -m gives the message on every call that makes a Commit (9 calls). A prefix that matches more than one Commit is refused InvalidInput with matches, a count. A <ref> or --from R is a Branch name first; when no such Branch exists it is a Commit id or prefix. commit diff <ref> of a Commit with no parent compares with its Branch's base, and with the empty tree when there is none.
Commits out
A write answers the new commit, a plain id, the same word --at and --expected take. Reads answer none in the short form. History calls answer Commits because Commits are what they list. An answer always carries the full id, 66 hex characters; the examples on this page cut each id to 8 characters and an ellipsis.
Paging
One convention. In: --limit N --cursor C; the default limit is 100 for a list and 200 for a log, at most 1000. Out: {"items":[…],"next_cursor":"…"}; next_cursor is left out at the end. A page ends early at 64 KiB with a cursor, never Capacity. 15 calls page this way, the log calls among them (sandbox.log, home.log, machine.log), newest first. 5 list calls take no cursor because they are bounded, and each row says why: machine.list, machine.images, store.list, store.auths, backup.list.
Cursors
A cursor carries its call's filters and, where the call pins a Commit, the pin; project list and branch list cursors carry filters only. A cursor given with different filters or another pin, or to another call, is refused InvalidInput. A cursor whose pinned Commit is gone is refused NotFound.
Partial lists
A list that could not include everything still answers, and names what is missing in not_listed: [{<thing>, blocked_by | reason, message}], one entry per thing it could not ask, with blocked_by as in a state or reason one of timeout, busy, lost, refused (workspace.list, backup.list). refused is a thing that answered and refused, such as a bucket that rejects its key; message carries the refusal; where one runnable line honestly fixes it, the entry also carries fix (backup list: a missing or refused bucket key). It is never a refusal of the whole call. A doctor's not_checked entry takes timeout, busy, lost only.
Windows
Text by lines: --line N (1-based) and --limit N (default 2000), answering next_line when more remains (file.read, file.blame).
Inline lists
A list inside a result (conflicts, overwritten paths, changes) shows its first 20 entries; only then does <list>_count appear. The rest comes from the call that owns the list. A field never changes type when cut.
Names
Each thing by its own word (project, branch, workspace, sandbox, machine, store, bucket, commit), never name except for what a call creates. engine is sqlite or postgresql; type is file, dir or symlink only. Enum values are lowercase.
Fields
Byte totals end in _bytes; one object's length is size. *_at is ISO-8601 UTC; *_ms is a duration. A plural noun is always a list, never a number. A count is <thing>_count (file_count); the count of a list that was cut is <list>_count and appears only beside that list. counts in a doctor's answer is the one plural that is a map, from each status to a number of things. op is only ever the state companion object; a log row names its call as call.
State
One of six words on every machine, Store, project, Sandbox and Workspace, each with the companion below and no other. A get always answers state; a list row leaves it out when it is ready. A state's reason is one of the reason codes; the reason of a doctor's not_checked entry (timeout, busy, lost) and of a not_listed entry (timeout, busy, lost, refused) are separate lists. The reasons and rules are under Status.

PostgreSQL: one Store, many routes

A machine can use any number of PostgreSQL Stores, and a Store can be used from any number of machines, each reaching it its own way: directly, through a proxy, through a tunnel. So nothing is configured per pair. The connection a machine uses is put together from three parts that vary independently.

Identity and ownership

A Store is its data
A Store is identified only by the id LayerFS writes into the database at first connect (the branch calls it the binding). Never by its address, which differs per machine and per proxy; never by its login, which is shared and rotates; never by its name, which is a label in one home.
Every route is proven
Each connect is checked from the machine that will dial, and must read the same id. That is what makes two addresses "the same Store". This check exists on the branch today.
The server owns the data
LayerFS connects to a database it did not make and never deletes it. disconnect forgets the home's records; the data stays. That is why the verbs differ from sqlite's create and remove.
The home owns the records
The Store's name, its saved login, its connections and a local copy of its project list. The project list is checked against the live Store on each read, so it can be shown, marked blocked, when the Store cannot be reached.
No machine owns a Store
A machine owns only its own connection and its Sandboxes. Any connected machine reads and writes; the database arbitrates writers. Removing a machine removes its own address from every PostgreSQL Store that has one, and never touches a Store. That removal is new work of machine remove: today the call deletes only the machine's folder, so a Store's record keeps the removed machine's address, which nothing then uses or cleans.
No default machine
A PostgreSQL Store records no machine: no "runs on" and no default for its Sandboxes. The machine is chosen when a Sandbox is created, with sandbox create --machine; without it the Sandbox runs on this computer, as today.
A Sandbox keeps its route
A running Sandbox keeps the connection it started with. Editing a connection affects new Sandboxes only.
Two homes, one database
Allowed. Each home has its own name, login and connections for it; the id in the data is the same.

URL is where, auth is who
The URL holds host, port, database and TLS options. A URL with a user or a password in it is refused. The saved login holds the user and password and no address, so one login covers every database and every route.
First connect
store connect <store> <url> --auth A. It names the Store's saved login, sets the connection every machine uses, and is made from this computer, which reads or writes the id and the project list. --auth is required here and only here. A Store with a different login is changed with store update --auth.
A machine's own address
store connect <store> <url> --machine M, on a Store that is already connected. It sets the address that one machine dials and is proven from that machine. It refuses --auth: a machine never has its own login. A Store has at most one default connection and one per machine. Without its own, a machine dials the default by itself (localhost is rewritten to the machine's name for this computer, as today).
Rotation
save-auth again under the same name. Every Store and machine using it picks it up; running Sandboxes keep their session.
Reach is observed
Whether a machine reaches a Store is never configured. store doctor <store> probes from each machine that has a Sandbox of that Store, so the Doctor page's Check all sees a Sandbox whose machine cannot reach its Store. --machine M probes from one more machine and stays a command-line option. sandbox create on a machine that can't reach refuses with the one address to set.
This computer needs a route
File, Branch and Commit calls on a PostgreSQL Store run in the caller's process on this computer. There is no worker route for browsing a Store this computer cannot reach.
Proxies
A pass-through proxy (a tunnel, a TCP forwarder, a pooler in session mode) is fine. A pooler in transaction mode is not supported, because compaction relies on session-level locks. This is documented, not detected.

Companions
op is the recorded operation: {name, phase, started_at}. blocked_by is {<machine|store|sandbox>, reason}. reason is a code from the closed list below. fix is one runnable shell line; two commands are joined with &&. observed_at is when LayerFS last knew the state: the last live read that answered, else when the record was last written. It is kept beside the record, in an observation file that generation does not cover. In the short form a state carries its companions and nothing from another state; in the long form every key is present and the others are null.
Reason codes
A closed list: stopped, busy, engine_down, not_answering, outdated, unreachable, missing, failed, unresolved, lost, unsupported, partial. In blocked_by the reason is the blocker's own state (stopped, busy) or its broken reason. A broken thing's reason is one of engine_down, not_answering, outdated, unreachable, missing, failed, unresolved, lost, unsupported, partial. The sentence stays in the long form's message. This list is not the reason of a doctor's not_checked entry or of a not_listed entry (timeout, busy, lost): that one says why a check or a read that was tried gave no answer, and the two lists are separate.
One cause, named once
blocked_by names the thing at the root, with that thing's own state or reason: a Workspace in a Sandbox on a stopped machine answers {"machine":"docker","reason":"stopped"}, not its Sandbox. A UI can then show the cause once and fold everything it blocks under it.
Docker not running
The docker machine is broken with reason: engine_down and a fix that starts the engine. stopped means a person stopped the machine, and nothing else.
Records first
A state comes from the home's records and costs no probe. --with live probes and stamps observed_at; only then can a state be unknown. A UI probes machines only; what lives on them inherits.
What a live read writes
A --with live read writes the record only when the state word or its reason changes. A read that finds the same state writes observed_at to the observation file and nothing else. A records-only read answers the last state word and reason that were written, so engine_down, not_answering, missing and unreachable can appear in a records-only answer, and in a records-only blocked_by, after a live read saw them.
Where Workspaces are recorded
The home's records hold Workspaces only for a Sandbox on native and for a Sandbox reached directly. Elsewhere the machine's worker keeps them. So home get --with tree, sandbox list and workspace list cannot list those Workspaces from records: a Sandbox row answers workspaces_not_listed:true while its machine is ready, and workspace list --sandbox S asks the machine. A stopped machine's Workspaces are not listed; its Sandboxes answer blocked.
Blocked things stay listed
project.list keeps the recorded projects of a Store it cannot open and marks them blocked; project.get answers the same instead of refusing. Today the all-Stores listing drops that Store's projects, so the UI keeps its own catalog to show them.
Every operation is recorded
machine.start and machine.stop record an op, as create and remove do today, so every client sees busy, not only the tab that pressed the button. This is new work.

When the reply to machine start or machine stop is lost, the recorded op stays with its outcome not known: the machine is broken with reason: unresolved and fix: layerfs machine get <machine> --with live. That live read settles it: it sees whether the machine runs and clears the op. Today the only call that clears an uncertain machine operation is machine remove, which deletes the VM and its disk.
Short form
A get always answers state. A list row leaves it out when it is ready: no news is good news, the same rule the UI follows.

A live read moves it only when it changes a state word or a reason; a new observed_at alone does not. It does not move for a Workspace the home does not record. Six doctors, one shape
home.doctor, machine.doctor, store.doctor, project.doctor, sandbox.doctor, backup.doctor. A Workspace has no doctor of its own: sandbox doctor checks it from the daemon's list. Today the whole-home sweep and the per-target checks answer two different reports, and rate the same outdated worker as a warning in one and an error in the other.
Depth
A doctor checks its own thing, then gives a shallow check to each thing directly on it; a project and a bucket also have a Full check, project doctor --full and backup doctor --full. There is no other depth and no option for it. --with never changes what a doctor checks.
Short form
{"ok":true} only when every check was made and nothing was found. Otherwise findings and not_checked, each present only when it has entries. A notice is a finding, so an answer with only a notice has no ok.
Severity
error: the thing does not work until it is fixed. warning: it works and something is wrong (a disk nearly full, a backup behind). notice: a normal state worth saying, which blocks nothing. A check's outcome is pass, its finding's severity, or not_checked. A thing's status is ok when every check passed, else the worst outcome among them; the answer's status is the worst thing in it.
A failed parent
Live checks beneath a stopped, outdated or unreachable parent are not attempted: one not_checked entry each, with blocked_by naming the root cause, no severity. Today the same case is "skipped", "unknown" or a silent return, depending on the check.
Could not check
A check that was tried and gave no verdict is a not_checked entry with reason: timeout (the thing's time budget ran out), busy (an operation holds the thing) or lost (the probe's reply did not arrive). These three are their own list, separate from a state's reason codes; a state's code appears in a report only inside blocked_by. It is never a finding and never ok. A check that does not apply to the thing is left out. Today's unknown and skipped outcomes go away.
Budgets
Each thing has its own time budget; no doctor takes --timeout. A Full check has no budget and runs until it finishes or the caller stops it. Today one 30 s budget covers a whole call.
Progress
--progress sends one event per finished thing: {"phase","done","total","node"}. phase is self, machines, stores, projects, sandboxes, workspaces, buckets: self is the named thing, the others are the kind being checked. done and total count things; the total is known from records before the first check. node is that thing's node as in tree, without child lists, so a row's marks can land together. This is new work: today target checks, the records sweep and a worker-run Sandbox report take three different routes, and one call is one target.
Records
One of home doctor's own checks reads every record in the home: references between records, file modes, leases, half-finished operations. A finding from it names the thing it is about, at any depth, and the page shows it on that thing's row. Live checks still go one level only. No doctor takes --offline.
The Store doctor
Checks the Store (its record, the id in its data against the record, its schema, that it can be reached where it lives, no half-finished move or stale lease), then gives each project the shallow check. It stops after the schema check and reads no data; that cut is new work, since today's cheapest mode still scans the file, and it needs a new argument on the worker's Store diagnosis that an older worker will not know. On a PostgreSQL Store it also probes from each machine that has a Sandbox of that Store, and each probe is one check entry with from naming the machine. Without that, Check all could read "All clear" while a Sandbox's machine cannot reach its Store. --machine M adds a probe from one more machine and is for the command line only.
The project doctor
Shallow: the project's record against the Store's own list. This check exists today in project.get and project.list. A project on record that the Store does not list is a normal state after a delete that kept the home entry, so its finding is a notice with a fix, not an error; store doctor reports the same notice, and project list leaves the project out, as today. --full: also reads everything reachable from the head of each of the project's Branches, which is what a mount can reach. It is streamed with bounded memory, writes nothing to the Store and changes no format; it may keep its visited set in a scratch file outside the Store, as today's integrity scan does, removed when the call ends. An object shared by two projects is read once per project. That walk is new work on both engines and through the worker. The whole-Store scan is dropped from the doctors, so nothing checks the database file's structure or data that no Branch head reaches.
Exit code
A doctor exits 0 once its report is made, whatever it found. A doctor that cannot make a report at all (no such thing, a home it cannot read) is a refusal and exits 125.
A doctor never repairs
fix is a runnable command, or null when no command helps. The fix for an outdated worker has two forms. With no Sandbox recorded on the machine it is layerfs machine stop <machine> && layerfs machine start <machine>. With Sandboxes recorded on it, it is layerfs machine stop <machine> --force && layerfs machine start <machine>, and the finding's message names their count: machine stop without --force is refused while Sandboxes are on the machine, and they cannot be closed first, because calls through a mismatched worker are not sent. machine start keeps refusing a mismatched worker. Today a Sandbox whose machine's worker is down is offered a forced Close.
Leftovers
No doctor walks for them, and home get does not list them: a leftover is disk to reclaim, not a fault. LayerFS removes what interrupted operations left itself, where it can prove nothing owns it (v20): there is no call that lists or removes them.

Backup status

Today the host keeps each bucket's last backup.list in memory and lists again only on List, on opening the Backups dialog, or at the end of a backup or restore. So "up to date" means "as of the last listing", which can be any age.

  • Commits after a backup leave the badge and the Store's Health row on "up to date" until someone lists again. The Health row also turns green when nothing was checked.
  • A failed listing keeps the old rows but resets the time, so it reads "listed just now". Only the bucket page shows the error.
  • A lost reply on an upload that landed reads "Bucket changed… another Store or home". Every later backup to that file is Conflict, because the link was never saved.
  • Reconnecting a bucket suggests the old file name, and that backup is refused every time. A restore is counted as a backup in coverage.
  • A VM Store costs 1 + 2N CLI calls per listing, because backup.list reads heads on native only. The host's own fingerprint is wrong both ways.

Cache and freshness

The host and client have 17 cache layers, lasting from 2 s up to forever. They fail both ways: one failed read becomes a state, two slow reads turn every project in the sidebar to "Machine unavailable", a Sandbox recreated under the same name inherits old history and metrics, and other clients' changes arrive only by polling or not at all.

Freshness envelope
Every cached value is {value, observed_at, failure: {code, since, count}}; observed_at is when the read began.
Bounded keep
Keep the last good answer for about 60 s or 3 failures, labelled "unreachable since T"; then show Unknown. A failure never becomes Down, Stopped, Removed, empty or 0.
Errors are not state
A failed read goes in its own field; only LayerFS's answer sets the label. Remove the 30 s Busy cache, or tie it to the op id.
Key by identity
Name plus created (Sandboxes: id), so a recreated thing never inherits old data.
Invalidate on change
Bump a write generation when a write finishes and drop results read under an older one. Clear caches on call-log events, which see every writer.
Show the age
Every view that can be stale shows how old it is.
LayerFS asks
[API] observed_at on every live read; reason codes on down_reason; one home-wide counter (generation on home.get); "observed down" distinct from "could not observe"; a created id on machine records.

LF13 (follow-up round, 2026-11-20): a silent PostgreSQL server is unreachable within 5 s

LF13(area 4) Every new PostgreSQL connection is made and logged in within 5 s, or within the URL's connect_timeout when it sets one; the driver bounds only the socket, so a server that accepts it and then says nothing (a paused container, a stopped process behind a live port) held the call until the host stopped it and the Store read unknown. One attempt, no retry. A status read past the limit is unreachable ("the server did not answer within 5 s (connect and login)"), so store get --with live reads broken unreachable, a reach check is refused Unavailable, and a Store open has no session (Unavailable, "no connection to the server was made"). The diagnostic driver's connect and login get the same 5 s under a longer deadline, half a Store doctor's 10 s budget: store doctor's store.connection fails ("did not answer within 5 s", evidence step: handshake) instead of reading not_checked, this computer's reach is recorded failed from that answer, and the server is not dialled a second time. A dial left waiting past the limit ends on its own thread when the server answers or the socket closes.

LF14 (follow-up round, 2026-11-20): a machine whose VM is gone lets what is on it go

LF14(area 10; extends LF10 and UI2-8 to missing) A machine whose record says a live read found its provider holding no VM of its name (broken missing) is treated as a record with no vm_name is: nothing on it can be reached again. Before, its fix machine remove was refused InUse for the Stores and Sandboxes on it, store remove said "start it", and machine start could not start it: a dead loop. Now: - every view of its state (machine get, machine list, with and without --with live, the home's tree, machine doctor's machine.provider) and its remove's InUse refusal show the chain layerfs sandbox remove … && layerfs store remove … && layerfs machine remove <m>; - a call on a Store on it is refused Unavailable with blocked_by {machine, reason: missing} (what store get shows) and that chain, nothing dialled; - machine start is refused Failed ("its VM is gone"), with that chain; - store remove and sandbox remove of what is on it go by their records alone, saying in left that the file or daemon went with the VM; - machine remove itself still asks the provider to delete the VM (a VM back under that name is not leaked); a live read still probes the machine and mends the record if the VM is back. A machine whose records say only stopped has to be read live first (the plugin's machine pages do), since nothing short of the provider says the VM is gone.
