Verdict

The shape holds. The spec is not ready to build from.

  • What holds: today's table has 84 calls in 12 families, every old call maps to a new row, and the new total is 84. Each doctor's own checks already exist in the code under today's check ids, the bucket write test included. The handle chain between calls is consistent.
  • What does not: 7 statements about today's code are wrong, 9 cases an implementer will hit in the first week are undefined, and the doctor answer has no outcome for a check that could not be made.
  • The largest hidden cost: nothing exists to build the short and long forms on. Results are untyped maps today, so "every key always present" means declaring a schema for all 84 calls.
  • The riskiest new piece: project doctor --full. The integrity check has no scope smaller than a Store.
  • The mock: the tree and the failure path read well. Two interactions are broken, one state is missing, and the progress it draws is finer than the calls report.

Recommendation: one phase with no code first, to settle the rulings and apply the corrections, then a mechanism phase that proves itself on one family before ten agents build on it.

What decides the order

  • The mechanism comes first and alone. The dispatcher, the result forms, the list and refusal shapes, the state type and the progress shape are in files every package touches.
  • Name lists hide in the machinery. scope.rs, platform_policy.rs and render.rs hold call names as strings. They move onto the table entries in the mechanism phase, or every rename collides there.
  • Shared files that every family touches: the count assert in calls_table.rs, the family list in lib.rs, the generated typings, and profiles.js, which throws on a call it does not classify. Family packages do not regenerate and do not edit the manual; one integrator does, after each merge.
  • All six doctors live in layerfs-control. The crate order is home, machine, store, sandbox, control, so a machine doctor cannot sit in the machine crate and still check its Stores.
  • The engine keeps its method names, so a public rename never reaches the engine.
  • dsh-layerfs moves on one pinned CLI. Its test requires every host call to exist in the pinned table, so each new pin is a flag day for the whole plugin.

Rules for every package

Branch
LayerFS work lands on layerfs_v2_0_0 through one pull request per package. dsh-layerfs work is edited directly on its layerfs_v2_0_0 branch, with no pull request and no side branch (owner, 2026-11-18). No CI lane runs for either branch, so each package verifies its own scope and reports what it ran and what it did not.
Worktrees
For LayerFS, one worktree per agent from the parallel worktree launcher, with its own Cargo target and its own writable Stores, homes and containers. dsh-layerfs has one checkout, the one port 3080 runs from, so its packages own separate folders and each commits only its own files. Two packages never write the same file.
Tests
No test command runs longer than 2 minutes. A test that is hard to adapt is deleted and listed in the commit message, never weakened. Behaviour that still holds gets a test on the new code.
Commits
Each records production lines before, after and the difference, from the pinned counter. A rename pass reports its relocation as relocation.
Calls
One attempt, no retry, no replay of a lost reply. Disposable profile only. No context environment variables. Engine method names do not change.
Files
Production files stay under 999 lines. A package that would push op.rs or a doctor target over it splits the file first.
Not touched
fs-bench-pro stays frozen. The Store format does not change. Third-party code is not patched.
The UI
Anything shown in dsh-layerfs is verified in the page itself across success, progress and failure, not only from the command line. Status is a signal and a tip.
The 3080 dsh
The plugin is built and checked on the default dsh at port 3080, with no side server (owner, 2026-11-18). A client change needs only a bundle rebuild. A host change needs a restart, which ends every live agent turn and changes the sign-in link, so host changes are batched and loaded only while no run is live. The LayerFS runtime under it moves only at a pin.

What was not checked

  • Nothing was built or run. The reviewers read source and the manual. I re-read the lines behind the most serious claim in each report and they match; I did not re-verify every finding.
  • The mock: no real screen reader, no real touch input, and the DSH Button and HoverCard were inferred from how the plugin calls them, since the primitives are not in the snapshot.
