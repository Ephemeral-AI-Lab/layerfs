Short form and long form

Short form · default

For agents. Only what the call produced: the id or handle the next call takes, and anything that changed. No result tag, since the call already says what was done. No echoed inputs. Fields that are null, false or empty are left out. An action with nothing to return answers {"ok":true}.

$ layerfs file write shop/api agent /src/app.ts < app.ts
{"commit":"12d1c0ffee58"}
Long form · --detail

For UIs, operators and debugging. Names the outcome in outcome and adds fields that were already read: full Commit references, internal ids, hashes, timestamps, record bookkeeping. It costs no extra I/O. It shows every field of its schema, nulls and empty lists included, so a UI reads a stable shape.

$ layerfs file write shop/api agent /src/app.ts --detail < app.ts
{"outcome":"Committed","branch":"agent",
 "commit":{"id":"12d1c0ffee58…","kind":"Commit","branch":"agent","root":"9f…"},
 "parent":"7a0b…","message":"Apply filesystem changes","created_at":1794985419000}
Cost options · named for what they fetch

Anything that probes a machine, walks a disk or reads more of the Store is its own option, so neither form is ever slow by surprise: --live, --stats, --space, --usage, --docker, --platforms, --include-storage, --patch. Each answers under its own key.

$ layerfs store get shop --live
{"name":"shop","type":"sqlite","machine":"dev",…,
 "live":{"state":"idle","observed_at":1794985419000}}

In Node and Python the long form is { detail: true } / detail=True. A UI asks for --detail once, in its client, and every agent gets the short form without asking.

Why this shape

Agents pay for every byte

An agent reads every result into its context, on every call. Today a file write answers about 650 B for one id, and workspace.exec wraps every command's output in 138 B of fields an agent never reads.

mirage, drive9 and cloudflare/computer all answer writes with the path or one id, and command runs with exit code and output.

A result feeds the next call

The id a call returns is named like the argument the next call takes: commit out, commit or --at in; workspace from mount, workspace into exec.

Today workspace.mount answers a 32-hex token in workspace, which exec does not accept; the handle is in ws.

One question, one call

Three pairs of calls answered the same question with different shapes (commit.*/branch.* history), and Store kinds were split into separate calls. Kind and platform are data on the record, not part of the name.

commit.get pages a Branch's history on the caller's side, about 21 Store calls for a 1000-Commit history.

A screen gets what it needs in one call

Every UI call is a CLI process in a lane of 4. The Storage list makes four reads per project plus a size call per row; the History tab can read about 625 pages; the Machines view probes every machine every 5 s.

So list calls carry the summary a row shows, and probes are explicit options.

Simple, but not by dropping history

The simple examples have no Branches, Commits, shared Store or several machines. LayerFS keeps all of these; it hides them behind defaults, short ids and the long form, not by removing them.

Their automatic retries, idle shutdown and output files inside the workspace break LayerFS rules and are not copied.

Rules for every call

Call form
layerfs <family> <call> <positionals> [--options]. Two levels only. Positionals go from the outside in: owner, Branch, path or new name, other inputs.
Short and long
Default is the short form. --detail adds fields already read. Cost options add reads and answer under their own key.
Argument names
An existing thing is named by its own word: project, branch, workspace, sandbox, machine, store, bucket. name only for the thing a call creates.
Commits in
Reads pin a Commit with --at <commit> (a full id or a prefix of 8+ characters, resolved by the Store). Writes take --expected <commit> and refuse Conflict, naming the current head, if the Branch moved.
Commits out
A plain id string named commit, the same word as the input, so it can be passed straight back. The full {id, kind, branch, root} reference is in the long form only.
No echo, no empties
A single-target result doesn't repeat the project, Branch, path or name it was given; list items always carry their identity. Null, false and empty fields are left out of the short form.
Paging
In: --page-size N --cursor C, default 100, at most 1000. Out: {"items":[…],"next_cursor":"…"|null}. A page ends early at 64 KiB and returns a cursor; it is never refused Capacity. The cursor alone continues: it carries the pins and filters.
Windows
Text by lines: --offset N --limit N (default 2000 lines), answering next_offset. Logs by lines: --cursor/--before and --limit, with has_more. Bytes (UI file views): --byte-offset/--byte-length.
Inline lists
A list inside a result (conflicts, LWW facts, overwritten Layers, changes) shows its first 20 entries plus <field>_count. The rest comes from the call that owns the list, with a cursor. A field never changes type when cut.
No result tag
The short form has no kind. A write answers its commit; a create answers the new handle; an action with nothing to return answers {"ok":true}. When an outcome can differ, a plain field says how: unchanged, merged, cancelled, conflicts, auto_resolved. The long form names it in outcome.
Result fields
A Store's engine is type. Times are *_at in epoch ms; durations *_ms. Free disk is disk_free. Lists are items. Plain words over jargon: auto_resolved, not lww.
Refusals
{"error","message","fix"}: error holds the code, so failure is the presence of error (and a non-zero exit). detail only in the long form. fix names the next call, e.g. layerfs branch fork shop/api mywork main for a write to main. A wrong argument count prints the usage line.
Errors
One code per meaning: NotFound, Exists, Capacity, Conflict, Busy, Unavailable, Unknown.
Progress
--progress (on_progress) on every call that can take seconds, one event shape {"phase","done","total"}.

Agent profile

Agents get a small set of tools. Operators and UIs keep the full table. Every call names its project and Branch, or its Workspace, explicitly, as today: LayerFS adds no environment variables or bound context.

Branch tools
file.read, file.list, file.glob, file.grep, file.write, file.edit, file.rm, file.mv, commit.list, commit.diff. Each write is one Commit on the named Branch. For small changes without a Sandbox.
Workspace tools
workspace.exec, workspace.status, workspace.commit, plus sandbox.create --mount to get one. Files are read and written through the mount by the commands the agent runs.
Hidden by default
machine, store, backup, home and the doctors, behind the MCP server's full profile. Write tools are hidden when the caller cannot write; a write to main is refused with a fix naming branch fork.
kept extended renamed / reshaped merged new

Outputs are the proposed shape, one line of JSON on stdout. Field names come from today's results, renamed by the rules. Ids are shortened here for reading; JSON carries them in full (--text shortens them to 12 characters). Example values are illustrative.

Backup status

Today the host keeps each bucket's last backup.list in memory and lists again only on List, on opening the Backups dialog, or at the end of a backup or restore. So "up to date" means "as of the last listing", which can be any age.

  • Commits after a backup leave the badge and the Store's Health row on "up to date" until someone lists again. The Health row also turns green when nothing was checked.
  • A failed listing keeps the old rows but resets the time, so it reads "listed just now". Only the bucket page shows the error.
  • A lost reply on an upload that landed reads "Bucket changed… another Store or home". Every later backup to that file is Conflict, because the link was never saved.
  • Reconnecting a bucket suggests the old file name, and that backup is refused every time. A restore is counted as a backup in coverage.
  • A VM Store costs 1 + 2N CLI calls per listing, because backup.list reads heads on native only. The host's own fingerprint is wrong both ways.
Store ahead of backup?
[API] store.get answers behind for each backup link (link heads ≠ current heads). A local read, no network, correct on every refresh, including VM Stores through their worker.
Bucket copy intact?
Needs the network, so only this half is cached, shown with its age and last error. [API] backup.list items add sha256, exported_from and a binding match in the long form.
Last attempt
[API] the link records attempt: {op, at, outcome, phase, sha256}, kept on Unknown, so an uncertain upload that landed can be adopted instead of Conflict forever.
Labels
Up to date · Behind · Never backed up · Backup file exists, not linked · Bucket unreachable since T · Last attempt failed / uncertain (T) · Copy changed by another writer · Restored (not counted as a backup)

Cache and freshness

The host and client have 17 cache layers, lasting from 2 s up to forever. They fail both ways: one failed read becomes a state, two slow reads turn every project in the sidebar to "Machine unavailable", a Sandbox recreated under the same name inherits old history and metrics, and other clients' changes arrive only by polling or not at all.

Freshness envelope
Every cached value is {value, observed_at, failure: {code, since, count}}; observed_at is when the read began.
Bounded keep
Keep the last good answer for about 60 s or 3 failures, labelled "unreachable since T"; then show Unknown. A failure never becomes Down, Stopped, Removed, empty or 0.
Errors are not state
A failed read goes in its own field; only LayerFS's answer sets the label. Remove the 30 s Busy cache, or tie it to the op id.
Key by identity
Name plus created (Sandboxes: id), so a recreated thing never inherits old data.
Invalidate on change
Bump a write generation when a write finishes and drop results read under an older one. Clear caches on call-log events, which see every writer.
Show the age
Every view that can be stale shows how old it is.
LayerFS asks
[API] observed_at on every live read; reason codes on down_reason; one home-wide change counter; "observed down" distinct from "could not observe"; a created id on machine records.
