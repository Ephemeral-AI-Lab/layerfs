PostgreSQL: one Store, many routes

A machine can use any number of PostgreSQL Stores, and a Store can be used from any number of machines, each reaching it its own way: directly, through a proxy, through a tunnel. So nothing is configured per pair. The connection a machine uses is put together from three parts that vary independently.

Identity and ownership

A Store is its data
A Store is identified only by the id LayerFS writes into the database at first connect (the branch calls it the binding). Never by its address, which differs per machine and per proxy; never by its login, which is shared and rotates; never by its name, which is a label in one home.
Every route is proven
Each connect is checked from the machine that will dial, and must read the same id. That is what makes two addresses "the same Store". This check exists on the branch today.
The server owns the data
LayerFS connects to a database it did not make and never deletes it. disconnect forgets the home's records; the data stays. That is why the verbs differ from sqlite's create and remove.
The home owns the records
The Store's name, its saved login, its connections and a local copy of its project list. The project list is checked against the live Store on each read, so it can be shown, marked blocked, when the Store cannot be reached.
No machine owns a Store
A machine owns only its own connection and its Sandboxes. Any connected machine reads and writes; the database arbitrates writers. Removing a machine removes its connections and never touches a Store.
No default machine
A PostgreSQL Store records no machine: no "runs on" and no default for its Sandboxes. The machine is chosen when a Sandbox is created, with sandbox create --machine; without it the Sandbox runs on this computer, as today.
A Sandbox keeps its route
A running Sandbox keeps the connection it started with. Editing a connection affects new Sandboxes only.
Two homes, one database
Allowed. Each home has its own name, login and connections for it; the id in the data is the same.

The calls

Save a login once, connect two databases 
$ layerfs store save-auth pg-app --user app --password-stdin
$ layerfs store connect shop postgres://db.internal:5432/shop --auth pg-app
$ layerfs store connect shop2 postgres://db.internal:5432/shop2 --auth pg-app
One machine reaches the same Store through a proxy 
$ layerfs store connect shop postgres://proxy.lab:6432/shop --machine lab
$ layerfs store connect shop postgres://proxy.lab:6432/shop --machine lab --auth pg-app
{"error":"InvalidInput","message":"a machine's own connection takes no --auth; shop uses pg-app"}
$ layerfs store disconnect shop --machine lab
Is it reachable from where Sandboxes run? 
$ layerfs store doctor shop                  # probes from each machine with a Sandbox of shop
$ layerfs store doctor shop --machine lab    # and from lab, Sandbox or not
$ layerfs sandbox create shop/api tests --machine lab
URL is where, auth is who
The URL holds host, port, database and TLS options. A URL with a user or a password in it is refused. The saved login holds the user and password and no address, so one login covers every database and every route.
First connect
store connect <store> <url> --auth A. It names the Store's saved login, sets the connection every machine uses, and is made from this computer, which reads or writes the id and the project list. --auth is required here and only here. A Store with a different login is changed with store update --auth.
A machine's own address
store connect <store> <url> --machine M, on a Store that is already connected. It sets the address that one machine dials and is proven from that machine. It refuses --auth: a machine never has its own login. A Store has at most one default connection and one per machine. Without its own, a machine dials the default by itself (localhost is rewritten to the machine's name for this computer, as today).
Rotation
save-auth again under the same name. Every Store and machine using it picks it up; running Sandboxes keep their session.
Reach is observed
Whether a machine reaches a Store is never configured. store doctor <store> probes from each machine that has a Sandbox of that Store, so the Doctor page's Check all sees a Sandbox whose machine cannot reach its Store. --machine M probes from one more machine and stays a command-line option. sandbox create on a machine that can't reach refuses with the one address to set.
This computer needs a route
File, Branch and Commit calls on a PostgreSQL Store run in the caller's process on this computer. There is no worker route for browsing a Store this computer cannot reach.
Proxies
A pass-through proxy (a tunnel, a TCP forwarder, a pooler in session mode) is fine. A pooler in transaction mode is not supported, because compaction relies on session-level locks. This is documented, not detected.

Machine chips
One per machine: green reached, hollow grey machine stopped, red can't reach with Set address for that machine only, a dash for not probed. A machine on its own connection carries a small mark; the tip shows the address and latency. The dots come from the Store's doctor, which probes the machines that have a Sandbox of the Store.
Logins
The second half of the tab's switch ("Stores | Logins"), as SQLite has "Stores | Buckets". Each row: name, user, the Stores using it, Rotate, Remove (disabled while used). Not a page of its own.
Connect dialog
For a new Store: name, address and saved login (a picker with New login inline). For "Connect a machine" on a connected Store: the machine and its address only, with no login field. The address is prefilled from the last one used with that login. It then checks from the machine that will dial and fills in its dot.
Gone from the page
The address header with "Reachable · 3 ms" (this computer's view only), and "Runs on · Change" (one machine per Store, kept by the UI, not by LayerFS). Where a new Sandbox runs is chosen when it is created.
