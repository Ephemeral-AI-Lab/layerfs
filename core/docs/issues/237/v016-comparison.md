## The 10k rate and its denominator

The registered case is **10,000 regular files in 100 data directories, 300,000,000 logical bytes total**. The 100,000,000-byte anchor is one of those 10,000 files and is **inside** that 300,000,000-byte total, alongside 100 empty, 7,899 tiny, 1,500 small and 500 medium files ([registry](../../../../benchmark/fs-bench-pro/families/init_namespace/mod.rs#L71-L85)). The generator subtracts `anchor_bytes` from `logical_bytes` before distributing the remainder ([workload](../../../../benchmark/fs-bench-pro/workload/main.rs#L310-L344)); its validation sums every file size into one `logical_bytes` ([workload](../../../../benchmark/fs-bench-pro/workload/main.rs#L477-L492)). The reference product's `init_bytes_per_second` is `rate(fixture_manifest.logical_bytes, layerstack_init_ns)` ([timer](../../../../benchmark/fs-bench-pro/src/main.rs#L2974-L3017)).

Thus the 400 MB numerator in [ledger L69](../../../../docs/roadmap/0.1/0.1.6/evidence/issue151-experiment-ledger.md#l69--219-round-9-the-boundary-the-700-mbs-figure-and-the-correction-of-l68s-cpu-claim-2026-09-21) and the [#219 gap handoff](../../../../docs/roadmap/0.1/0.1.7/issue219-v016-gap-rca-handoff.md#1b-owner-correction-2026-09-21-the-700-mbs-figure-is-init_namespace) **double-counts the anchor**. It makes 578.245 ms look like 691.8 MB/s; the product's 300 MB numerator gives **518.8 MB/s**. The first two historical rows do exceed 700 decimal MB/s on the product definition (744.9 and 736.0 MB/s), subject to the custody and cache limits below. This correction does not rewrite either historical receipt or its contemporaneous verdict.

## Which work is actually timed

The reference's public call is `client.initialize_layerstack(name, LayerStackInitialization::Directory(fixture))`; `layerstack_init_ns` begins immediately before and ends immediately after it. Store create, client/container binding and teardown are outside the timer ([benchmark main](../../../../benchmark/fs-bench-pro/src/main.rs#L2936-L3017)). The product dispatches to `LayerStackStore::initialize_layerstack`, plans a bounded frontier and streams files into `CheckedOutputAdmission` ([layerstack.rs](../../../../crates/layerfs-layerstack-store/src/layerstack.rs#L20-L103), [direct path](../../../../crates/layerfs-layerstack-store/src/layerstack.rs#L1230-L1257)). It uses available parallelism capped at eight and, for the small-content format, four construction workers ([direct path](../../../../crates/layerfs-layerstack-store/src/layerstack.rs#L1279-L1285), [worker cap](../../../../crates/layerfs-layerstack-store/src/objects.rs#L48)). The frontier has an 8 MiB owned-metadata budget and 1,000 task limit ([constants](../../../../crates/layerfs-layerstack-store/src/layerstack.rs#L948-L963)); finalized producer pages feed an admission consumer, with a final namespace/publication phase ([direct path](../../../../crates/layerfs-layerstack-store/src/layerstack.rs#L1314-L1435), [final phase](../../../../crates/layerfs-layerstack-store/src/layerstack.rs#L1536-L1553)). The 10k case used 73 admission transactions in every numeric retained row ([ledger L69](../../../../docs/roadmap/0.1/0.1.6/evidence/issue151-experiment-ledger.md#l69--219-round-9-the-boundary-the-700-mbs-figure-and-the-correction-of-l68s-cpu-claim-2026-09-21)). Its payload lives as actual SQLite `object_packs.data` BLOBs, not a permanent spill file ([admission insert](../../../../crates/layerfs-layerstack-store/src/objects/admission.rs#L1525-L1562), [#219 source audit](../../../../docs/roadmap/0.1/0.1.7/evidence/issue219-ns19r-algogap-20260921T095811Z/README.md#step-2--h2-is-settled-by-reading-the-references-payload-reaches-the-pager)).

The mainline Core native Init is a different public operation: one daemon `HistoryCommand::ImportNativeDirectory` request bound to an operator-configured source root. Its timer includes the request/reply and confirmed `StackCreated` result ([#231 contract](../../benchmark/fs-bench-pro/issue-231/SPEC.md#2-first-pass-case-registry-and-operation), [driver](../../../benchmark/fs-bench-pro/families/init_namespace.py#L155-L175)). The Service first scans names and metadata and creates a `Vec<PreparedEntry>` plus `Vec<Job>`, then four file constructors send finalized objects through an eight-object channel to one C2 save owner ([import_native.rs](../../../crates/layerfs-service/src/operation/import_native.rs#L45-L113), [workers](../../../crates/layerfs-service/src/operation/import_native.rs#L146-L191)). It then reserves inode serials, builds metadata/content prerequisites and a C1 namespace in further saves, and publishes C5 history ([history.rs](../../../crates/layerfs-service/src/operation/history.rs#L304-L345), [history_bootstrap.rs](../../../crates/layerfs-service/src/operation/history_bootstrap.rs#L114-L229)). At the #231 baseline, `FileView::open` is called for every regular file during prerequisites, even though `construct_file` already returned its content root ([history_bootstrap.rs](../../../crates/layerfs-service/src/operation/history_bootstrap.rs#L274-L291)); whether that validation is a major time term is **not measured by the reference receipts**. The previous #219 `pipeline-namespace-10000` is neither of these public imports: its C2 supplied-object timer excludes source scan and C1 file construction ([#219 boundary audit](../../../../docs/roadmap/0.1/0.1.7/evidence/issue219-squadD-chunk-20260921T044229Z/raw/09-timer-boundaries.md#d-cache-state-both-arms)). Do not use its subsecond operation time as native Init parity.

The Core #231 fixture preserves the case counts and 300 MB total but deliberately changes byte generation and the per-path size assignment: SHAKE-256 chunks and fixed class weights, with the anchor assigned first in path order, versus the reference's role-weight permutation and content profile ([#231 fixture contract](../../benchmark/fs-bench-pro/issue-231/SPEC.md#2-first-pass-case-registry-and-operation), [reference planner](../../../../benchmark/fs-bench-pro/workload/main.rs#L273-L344), [Core planner](../../../benchmark/fs-bench-pro/families/init_namespace.py#L40-L59)). Matching case IDs therefore do not imply matching source bytes, object IDs or path-to-size layout. #231 is a three-tier discovery cohort; 100k remains explicit `NOT_RUN`, and no v0.1.6 equivalence or performance gate is frozen ([#231 SPEC](../../benchmark/fs-bench-pro/issue-231/SPEC.md#1-decision-and-evidence-status)). Current #237 preregistration reports its control and metadata treatment returned `Unknown` before a C5 root, so those attempts cannot establish a Core Init speedup ([#237 preregistration](../../../../docs/roadmap/0.1/0.1.7/evidence/issue237-native-init-research/preregistration.md#d3-labelled-count-driven-localization-after-d1-failure)).

## Implementation handoff

1. Keep the Core public native import as the comparison route. Record the complete caller operation, Service child spans, source residency immediately before the call, process CPU/disk I/O, object counts/bytes, Store apparent/allocated bytes and full readback. The old reference 10k rows lack a cold contract, so use them as historical context; a future matched speed claim needs one prospectively declared cache state and matched source/product identities in both arms. Do not rerun an unchanged arm to select a favourable number.
2. Localize the Core's extra serial work by count before changing it: per-file `FileView::open`/Store reads in prerequisites, C1 namespace construction, C2 commits and SQL statements. The old path's bounded frontier plus producer/admission pipeline is the useful architectural reference. Core already has four constructors and a bounded channel; adding workers merely to pass a gate would miss the likely serial work and violate the fixed policy. Preserve input validation and bounded memory.
3. Preserve compactness separately from speed. The reference's later 10k Stores were 304.6–305.0 MB for 302.18 MB canonical bytes (about 1.008–1.009×), while the older 54.46k-object builds were about 1.19×; the Core #219 pipeline example had 332.92 MB of pack BLOB capacity for 301.87 MB written because `zeroblob(capacity)` reserves 256 KiB packs ([#219 algorithm audit](../../../../docs/roadmap/0.1/0.1.7/evidence/issue219-ns19r-algogap-20260921T095811Z/README.md#step-2--h2-is-settled-by-reading-the-references-payload-reaches-the-pager), [Core insert](../../../crates/layerfs-storage/src/sqlite/write.rs#L81-L101)). That is a measured *space* difference in a different route; its time cost is **NOT_MEASURED**. Any Init optimization must report pack occupancy and the #229 sparse-pack lane independently and reject readback or footprint regressions. Do not infer sparse-history health from a dense Init Store.
