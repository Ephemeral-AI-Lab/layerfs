# #237: v0.1.6 and Core native Init architecture at 10k

> **Status:** Research; informative and not a product contract.
> Source and retained-receipt comparison only. No product edit or public benchmark sample was made for this note. The sole fixed database setting in the proposed architecture experiments is the 4,096-byte SQLite page size. Source data must be cold at each timed call, and fixture reuse may save only untimed preparation.

## What the two public calls include

Both fixtures declare **10,000 regular files, 100 data directories and 300,000,000 logical bytes total**. The 100,000,000-byte anchor is part of the 300 MB, not an extra numerator: the [reference generator](../../../../benchmark/fs-bench-pro/workload/main.rs#L332-L344) subtracts it before apportioning the other bytes. Core's [planner](../../../benchmark/fs-bench-pro/families/init_namespace.py#L28-L59) preserves the class counts but assigns the anchor first in path order, uses fixed class weights and SHAKE-256 source bytes; v0.1.6 permutes roles and uses its own [content profile](../../../../benchmark/fs-bench-pro/workload/main.rs#L273-L344). The two cases are not byte-identical or path-to-size-identical.

The architectures' memory accounting differs. The reference bounds its frontier and slab queue, while Core retains all 10,101 scan entries/jobs and the C1 input vectors, besides its bounded object channel and C2 wave. D9 sampled **58.5 MB** Service maximum RSS, but the monitor did not cover both timer boundaries, so it is descriptive rather than a whole-operation peak ([D9 analysis](file-ingest-10k-next.md#observed-bound-and-700-mbs-arithmetic)). A larger SQLite page cache, worker count or transaction size is an alternate **product policy** experiment and needs its own declared bounded-memory and comparison identity; none is an innocent retiming of the existing gate.

## What 518.8 MB/s would require under a cold-source contract

The historical `578,245,125 ns` public call gives **518.8 decimal MB/s** (`300,000,000 / 0.578245125`). Its recorded disk reads were **zero**, cache contract was null, source tree was dirty, full verifier was NOT_RUN, and its 54,463-object format differs from the later compact rows. It consumed **1.691 s CPU** in **0.578 s wall**, or 2.92 implied cores, but this is evidence of overlap under that row's uncontrolled cache, not of cold throughput ([six-row inventory](../../../../docs/roadmap/0.1/0.1.7/evidence/issue219-ns19r-algogap-20260921T095811Z/README.md#step-1--the-commissions-1a-is-re-derived-and-it-holds)). The later 25,158-object clean rows read 337.4/322.2 MB from storage and took 1.020/1.101 s: **294.0/272.6 MB/s**. They still had no independently enforced whole-input cold contract. No retained v0.1.6 row establishes 518.8 MB/s with cold source bytes, let alone cold directory metadata and full independent readback.

D9 Core's release public call was **1.590847 s**, or **188.6 MB/s**, with an immediately preceding nonfaulting check of zero resident source payload pages out of 27,503 ([receipt and cold sidecar](throughput-10k.md#present-release-profile-budget)). To reach the historical time at the same 300 MB, it must lose **1.012602 s (63.6%)**. The direct C1 prototype's one candidate was **1.317539 s**, or **227.7 MB/s**, leaving **0.739293 s (56.1%)** to cut. Its file stage alone took **1.162959 s**; if its remaining caller work stayed at **0.154580 s**, file ingest would need to finish within **0.423665 s**, a **0.739293 s (63.6%)** reduction. This is a budget from one candidate receipt, not a forecast and not an accepted speedup. The candidate's zero-resident *payload* check did not establish cold metadata, and its strict equality/semantic checks failed.

The reference's transferable traits are **work organization**, not its headline time: bounded producer/admission overlap, compact direct initial namespace assembly, and multi-group/multi-row pack publication. Its near-zero device reads, uncontrolled directory metadata cache, distinct bytes/object format and 32 MiB page-cache policy do not transfer as evidence. Core's full public timer must continue to contain source scanning/reading, Store writes and C5 publication. Reusing the prepared source can reduce only setup time; it cannot supply resident source data to the timed operation. Keep `PRAGMA page_size=4096` in every experimental arm.

## Ranked next architecture experiments

1. **Complete the direct C1 fresh-build route, with deterministic public identities.** It has the only measured algorithmic 10k speed signal here: 246 ms lower caller time in one pair, with file-stage times essentially unchanged. Freeze equal stack/scope before the pair, preserve the old ordering failure/boundary guarantees through update tests, and check exact root plus full reopened readback and Store geometry. Even crediting its entire observed 246 ms leaves roughly **739 ms** to the 518.8 MB/s target; C1 alone is insufficient. This is a correctness/attribution prerequisite before a production claim, not a reason to rerun an unchanged timing arm ([prototype](c1-direct-prototype.md#implementation-handoff)).
2. **Prototype bounded bulk C2 admission for fresh imports, with on-demand dependency flush.** The reference assembles and inserts multiple groups/locators per bounded batch; Core's 7,696 file-save groups each force an immediate placement, pack write and usually a separate row INSERT. A legitimate Core treatment would queue framed groups up to a declared byte/row limit, publish packs and locator rows in engine-limited pages, flush before same-save reads, collision reuse, delta bases, wave boundaries and COMMIT, and preserve exact canonical IDs/rollback. The simple one-pack queue was rejected because those dependencies are real ([feasibility analysis](c2-grouping-prototype.md)); this requires a deliberate import-specific admission design, not a one-line `select_many` change. D12 charged **123.805 ms** to pack-write calls and **71.157 ms** to object INSERTs, nested within a 771 ms owner accept, and D11 charged **192 ms SQL + 227 ms COMMIT** over the entire Save ([D12](c2-detail-diagnostic.md#one-retained-diagnostic), [D11](c2-grouping-10k.md#what-d11-actually-charged)). Erasing only pack-write and row-INSERT call overhead has a **195 ms local ceiling** in D12, well short of the ~739 ms needed after C1. A viable design must also improve owner handoff/transaction critical path and preserve the sparse-pack #229 space/readback guardrail. Altered wave/transaction sizes may be measured as a separate product-policy treatment, with bounded memory; a bigger limit by itself is not a causal explanation.
3. **Change how completed objects reach C2, then measure owner occupancy.** The reference queues slabs; Core sends 24,562 individual object messages through eight slots. A bounded slab channel using the same canonical objects could reduce wakeups and let workers prepare while the owner publishes, but D11's **2.880 s summed send wall** is chiefly overlapping backpressure and must not be claimed as removable overhead. Require counters for objects/slab, sender block vs active construction, receiver idle by reason, pack/SQL/COMMIT calls, peak live bytes and source device reads. Extra construction workers alone would likely wait on the one SQLite writer: in D11 the receiver was already busy for 0.786 s of a 1.147 s file span. A worker-topology change is a separately identified product architecture experiment, not a same-policy benchmark gate pair ([pipeline sources](../../../../crates/layerfs-layerstack-store/src/objects.rs#L372-L491), [Core handoff](../../../crates/layerfs-service/src/operation/import_native.rs#L143-L229)).

Do not spend the next 10k arm on collision lookup or a smaller prefix reserve. D12 charged **43.306 ms** to all collision queries, below its registered 50 ms threshold ([decision](c2-detail-diagnostic.md#one-retained-diagnostic)); the standalone prefix test found a **0.446 ms slowdown** for a 4 KiB initial reserve and broke the existing capacity bound ([decision](prefix-probe-experiment.md#decision)). Neither can explain a 739 ms gap. The 4 KiB *database page* rule is unrelated to the prefix-reserve test and remains fixed.
