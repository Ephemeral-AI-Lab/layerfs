# #237 file-ingest bottleneck and reference pipeline

> **Status:** Research; informative and not a product contract.
>
> Read-only analysis, 2026-09-23. No product, harness, fixture, Store, or receipt was changed for this note. No new sample or speedup is claimed. Source pin for the clean D6 diagnostic: `0615c5f4acf60420c6471616a8ff845c01e753e0`; its receipt remains `INCOMPLETE` because full verification timed out.

## Comparable facts and an identity blocker

The Core public Init runs one daemon `HistoryCommand::ImportNativeDirectory`. Service scans the configured source root, queues 10,000 file jobs, constructs files on four workers, sends finalized objects through an eight-message bounded channel, and saves on the receiving thread ([source scan and job creation](../../../crates/layerfs-service/src/operation/import_native.rs#L45-L113), [producer/consumer](../../../crates/layerfs-service/src/operation/import_native.rs#L143-L229)). Construction streams each file and checks device/inode before reading and length/mtime afterward; those checks protect source identity and are not removable merely to improve a timer. `SaveHandoff::accept` calls the single C2 `SaveOperation::accept`, which buffers up to 512 objects and under 4 MiB canonical bytes per wave ([handoff](../../../crates/layerfs-storage/src/cas/store.rs#L821-L860), [batch](../../../crates/layerfs-storage/src/cas/batch.rs#L13-L67), [limits](../../../crates/layerfs-storage/src/policy.rs#L117-L140)). The channel limits queued **objects**, not the complete Service heap: the `PreparedEntry` and `Job` vectors each grow with file count.

The clean D6 10k receipt records one **7.362191042 s caller operation**, with `history.import_files` **6.455689125 s** (87.7% of the caller span), `history.import_scan` 55.111 ms, `history.import_finish_save` 6.828 ms, and `history.finish_tree_save` 258.156 ms. Service CPU in its sampled caller window is **14.500256 s user + 1.082269 s system**, with sampled maximum RSS **60,243,968 B**. Its Store has **24,683 objects**, including 24,364 from file save; it is **333,905,920 B apparent**, with **331,087,872 B pack capacity**, **305,975,489 B assembled pack bytes**, and **4,096 B SQLite pages** ([D6 receipt](../../../../docs/roadmap/0.1/0.1.7/evidence/issue237-native-init-research/raw/d6-gap/daemon-host/init_namespace/namespace-10000/receipt.json), [D6 geometry](../../../../docs/roadmap/0.1/0.1.7/evidence/issue237-native-init-research/raw/d6-gap/store_geometry.json)). The independent cold-source sidecar found zero resident pages across 10,000 files / 300,000,000 B, but the runner still labels the sample `source-cache-uncontrolled-v1` and `admission_eligible=false`; the 5 s full verifier returned `TIMEOUT`. These qualifications preclude a passing cold or full-readback claim ([D6 cold preflight](../../../../docs/roadmap/0.1/0.1.7/evidence/issue237-native-init-research/raw/d6-gap/daemon-host/init_namespace/namespace-10000/cold-preflight.json), [D6 verification](../../../../docs/roadmap/0.1/0.1.7/evidence/issue237-native-init-research/raw/d6-gap/daemon-host/init_namespace/namespace-10000/verification.json)).

**The build profile must be fixed before comparing throughput.** D6's `build.json` is a `cargo build --locked` command without `--release`; the runner copies executables from `target/debug` ([D6 build record](../../../../docs/roadmap/0.1/0.1.7/evidence/issue237-native-init-research/raw/d6-gap/build.json), [Core runner](../../../benchmark/fs-bench-pro/runner.py#L26-L30), [binary archiving](../../../benchmark/fs-bench-pro/runner.py#L96-L125)). Yet the frozen #231 specification requires `cargo ... --locked --release` ([spec](../../benchmark/fs-bench-pro/issue-231/SPEC.md#L355-L359)), and the reference's host build uses release ([reference runner](../../../../benchmark/fs-bench-pro/shared/runner.py#L1255-L1278)). The impact of this profile mismatch on the 6.456 s file span is **not measured**; calling it the cause of the gap would be an inference. It does make a direct v0.1.6/Core speed ratio invalid. Pin a new release binary identity and a fresh output for the next row; retain D6 as a debug-profile diagnostic.

The retained v0.1.6 `namespace-10000` rows range from **402.721 ms** on dirty, nearly zero-disk-read source to **1,100.711 ms** on a clean later source. All six numeric historical rows have an undeclared cache contract and verification `NOT_RUN`; earlier and later rows differ in object count. The sealed #219 reference reproduction is **944.881 ms**, but has a different operation surface, fixture/content profile, build and cache identity from D6 ([reference comparison](v016-comparison.md#the-10k-rate-and-its-denominator)). The reference itself also has four small-content constructors and a bounded queue, but sends **256 KiB / 512-object slabs** through four queue slots into one admission owner ([reference constants](../../../../crates/layerfs-layerstack-store/src/objects.rs#L39-L48), [pipeline](../../../../crates/layerfs-layerstack-store/src/objects.rs#L372-L480), [native Init path](../../../../crates/layerfs-layerstack-store/src/layerstack.rs#L1230-L1435)). Its batching is a useful mechanism to inspect, not evidence that changing Core's channel alone removes seconds. The #219 `pipeline-namespace-10000` receipt prices a different C2 supplied-object route at 955.938 ms accept and 317.652 ms construction, and expressly excludes native source scan/read from its timer; it cannot be substituted for public native Init ([#219 receipt](../../../../docs/roadmap/0.1/0.1.7/evidence/issue219-ns21-100k-20260921T155500Z/raw/ns21-A1-10000-pinned-20260921T155500Z/pipeline-namespace-10000/receipt.json), [route audit](v016-comparison.md#which-work-is-actually-timed)).

## What the existing counts do and do not localize

The D3 instrumented derivative failed later in C1, so its **file-save counts are diagnostic only**. By its file-save completion it had inserted **24,364** objects and reused **198**, created **1,255** packs and appended **6,444** times, committed **92** transactions, issued **7,753** object-row insert statements and **67** presence-query waves. The completed save reported **304.781 ms** in `SaveProfile.sql_ns` and **278.607 ms** in `commit_ns`, totaling **583.388 ms**. Its file phase took about **6.676 s** (`files_done` 6.747 s minus `scan_done` 0.071 s), while `file_save_done` at 6.802 s includes final save completion ([D3 raw stderr](../../../../docs/roadmap/0.1/0.1.7/evidence/issue237-native-init-research/raw/d3-phasecounts/daemon-host/init_namespace/namespace-10000/service.stderr), [D3 instrumentation diff](../../../../docs/roadmap/0.1/0.1.7/evidence/issue237-native-init-research/d3-instrumentation.diff)). The SQL/commit charges are only about 8.7% of that file-phase wall. **The other 91.3% is not necessarily one owner's serial time:** four workers run concurrently with the save owner, and D3 did not record construction time, sender blocking, receiver idle, or the other five SaveProfile buckets. D3 and D6 have different source/build identities and are not a matched performance pair.

The source's critical path is a producer/consumer maximum, not the sum of producer CPU and owner CPU. A producer can be stalled on the eight-object channel while C2 is busy; conversely, a receiver can wait while the four workers read, hash and chunk files. The present counts cannot distinguish those cases. The 7,753 inserts and 92 commits identify finite C2 work, but no evidence supports widening a wave, adding workers, changing the SQLite cache or touching the **4 KiB page size** as the first lever. The C2 save already batches 512 objects / 4 MiB, and the legacy #219 campaign had separately priced SQL, commit, pack writes and codec work; those figures came from another route and binary ([C2 batch](../../../crates/layerfs-storage/src/cas/batch.rs#L13-L67), [#219 attribution](../../../../docs/roadmap/0.1/0.1.7/issue219-ns19-algorithm-gap-handoff.md#1b-where-the-rows-own-12189-ms-is-all-of-it-measured)).

## One prospective diagnostic, then the smallest justified treatment

First correct the Core runner's release build contract and seal the build profile in its identity. On **one new release-profile 10k diagnostic identity**, retain the same public request, fixture, four workers, eight-object channel, 4 KiB SQLite pages, cache preflight, deadlines and output oracle. Add aggregate counters only: each worker's file construction wall, source-read bytes/calls and `SyncSender::send` blocked nanoseconds/count; receiver idle nanoseconds and `handoff.accept` wall; all seven existing `SaveProfile` buckets plus `DiagProfile` totals from the completed file `SaveOutcome`; and file-save object/pack/statement/commit counts. Emit one bounded summary per worker and one owner summary, not per-object telemetry. `SaveProfile` already exists, so this needs only diagnostic reporting plus a few boundary clocks, not a new profiling framework ([profile](../../../crates/layerfs-storage/src/cas/owner.rs#L39-L92), [source send and receive](../../../crates/layerfs-service/src/operation/import_native.rs#L25-L43), [worker loop](../../../crates/layerfs-service/src/operation/import_native.rs#L155-L189)). Label the run diagnostic and retain its raw receipt; do not compare its wall to D6 as an optimization result. A wall improvement claim requires a separately preregistered same-profile control/treatment pair, one sample each, and full reopened readback.

If receiver idle dominates and worker send blocking is small, target construction only after the per-byte/per-file counts identify a redundant operation. Keep the frozen CDC partition and source stability checks; a different chunk profile changes canonical IDs. If send blocking and owner accept dominate, test **bounded slab handoff**, reusing the reference's idea with Core's existing `PendingBatch`/wave limits: at most 256 KiB or 512 objects per producer slab, four queued slabs, one C2 owner. This reduces channel wakeups, but it is a *hypothesis* and may save little because `SaveOperation::accept` still handles each object. Bound producer partial slabs and queue bytes explicitly; do not make the queue an unbounded `Vec`. If the owner profile instead points to a specific pack or SQL call, target that call once and verify its count and cost before changing packing. A pack layout, `zeroblob` capacity or representation change must carry a separate #229 sparse-history guardrail and full reopened readback because dense Init occupancy cannot prove sparse-history compactness ([sparse-pack note](sparse-pack.md#minimum-prospective-controltreatment-check-for-an-init-change)).

For a later 100k release route, repeat the same count schema after its registry and cold-source contract are prospectively registered. The current 100k case is `NOT_RUN`; neither the 10k wall nor this bottleneck split may be extrapolated to it ([100k route note](100k-route.md#current-public-route-and-scaling-obligations)).
