# #237: C2 grouping on the 10k native Init path

> **Status:** Read-only research, 2026-09-23. No product or harness edit and no new timed sample. The retained D11 run is a dirty, instrumented, one-sample diagnostic with `verification=SKIPPED` and `admission_eligible=false`. Its source preflight and immediately preceding recheck each found zero resident pages, but the official receipt still says `source-cache-uncontrolled-v1`; no number below is a cold admission PASS.

## What D11 actually charged

D11 used the public daemon-host native import, 10,000 files and 300,000,000 logical source bytes. Its [receipt](../../../../docs/roadmap/0.1/0.1.7/evidence/issue237-native-init-research/raw/d11-ingest-counts/daemon-host/init_namespace/namespace-10000/receipt.json) records a **1.492577209 s** caller operation (200.99 decimal MB/s) and a **1.146652917 s** `history.import_files` child. The temporary [source instrument](../../../../docs/roadmap/0.1/0.1.7/evidence/issue237-native-init-research/d11-instrumentation.diff.gz) counted 24,562 object messages, 0.785606657 s summed receiver-side `handoff.accept`, and 0.357453370 s receiver waiting. Their sum leaves 0.003592890 s of file-loop overhead; the four worker and send totals overlap each other and this owner span, so they must not be added to it. `scan_and_save` runs four constructors through an eight-object channel into one Save owner ([Service source](../../../crates/layerfs-service/src/operation/import_native.rs#L143-L229)).

The file Save inserted **24,364** objects, reused **198**, created **1,257** packs, appended to packs **6,439** times, issued **7,750** object-row INSERT statements, and committed **79** times. D11's disjoint `SaveProfile` buckets aggregate the **whole Save**, including its final drain/publication, so they do not partition `handoff.accept` alone:

| Bucket | Time, ms | Interpretation |
| --- | ---: | --- |
| SQL | 192.313 | Pack I/O, object rows and other charged SQL; D11 did not split pack BLOB and object INSERT cost. |
| COMMIT | 227.454 | 79 transactions, mean 2.879 ms each; a mean is not a per-call distribution. |
| FULL encode | 71.265 | Record encoding. |
| Group codec | 16.729 | Group framing/codec. |
| Placement | 11.979 | Pack placement. |
| **Five-bucket sum** | **519.740** | Disjoint charges over the whole Save, not solely accept. |

`flush_batch=556.774 ms` is **nested inside** `accept_plumbing=783.889 ms`, which almost equals the receiver's `owner_accept=785.607 ms`; neither is an additional bucket. `finish_call=54.223 ms` is a separate call outside `history.import_files`. The arithmetic `785.607 - 519.740 = 265.866 ms` is only a **lower bound** on accept's uncharged remainder if all five buckets arose in accept; as much as 54.223 ms of those buckets can belong to finish, giving an upper bound of 320.090 ms. The D11 printout cannot isolate that split. Source: [SaveProfile definitions](../../../crates/layerfs-storage/src/cas/owner.rs#L30-L73), [accept and finish](../../../crates/layerfs-storage/src/cas/store.rs#L493-L566), and D11's one-line Service diagnostic in the receipt.

I queried D11's closed `store.sqlite` read-only with Python `sqlite3.connect('file:<path>?mode=ro', uri=True)` and grouped `objects WHERE save_id=1` by `(pack_id, group_number)`. It has exactly **7,696** physical file-save groups: **805** contain whole-file objects, **6,877** contain chunks, and 14 contain other file mapping/state roles. The three categories are disjoint in this retained Store. The 13,920 chunk objects therefore account for most group activity; their 6,877 groups average only 2.02 chunks each. The whole file save contains 9,399 whole-file objects. The SQLite page size is **4,096 B**, with 1,257 file-save pack rows and 329,515,008 B of reserved pack BLOBs. The query is a Store-geometry diagnostic, not a new operation sample.

The count identity is decisive: **1,257 creations + 6,439 appends = 7,696 group placements**. `seal_group` calls `LanePlacement::select_many(lane, vec![group], ...)`, then writes that one group and inserts its object rows immediately ([C2 seal](../../../crates/layerfs-storage/src/cas/placement.rs#L110-L218)). The existing placement API can already accept several groups and makes one increment per receiving pack ([placement](../../../crates/layerfs-storage/src/pack/placement.rs#L103-L216)). The 7,750 statements are 7,696 one-group INSERT calls plus 54 extra chunks where a group exceeded SQLite's 128-row statement cap ([SQL writer](../../../crates/layerfs-storage/src/sqlite/write.rs#L176-L242)). Thus batching *within* each group is already done, but batching *across* groups is unused on this route. The reference v0.1.6 path prepared packs from many groups and inserted locators in bounded multi-row pages ([reference admission](../../../../crates/layerfs-layerstack-store/src/objects/admission.rs#L1440-L1561)); its historical fast 10k rows had no proven cold-source contract and a different object count, so they cannot supply a matched time delta ([comparison](v016-comparison.md)).

## One prospective candidate: coalesce adjacent sealed groups

Keep the existing group target, pack format, 4 KiB SQLite page, 512-object/4 MiB waves, current transaction cadence (79 COMMITs in D11), and one C2 owner. Within a wave, queue only **consecutive sealed groups of the same lane** up to one ordinary pack limit (256 KiB of encoded group bytes); flush that queue on lane switch, at the bound, before a same-save read or candidate base needs a queued object, and at the wave boundary. Move the existing encoded groups into the queue, then pass the vector to `LanePlacement::select_many`; write each returned pack increment once and insert all resulting locator rows in the existing engine-limited 128-row chunks. Singleton groups continue directly. The queue itself is capped at one pack, but selected increments and locator rows can coexist with it during a flush; count the simultaneous live capacity and enforce an explicit 1 MiB additive ceiling rather than assuming the wave bound covers those allocations.

The dependency barrier is part of the candidate, not an optional optimization. `pending_base_for` seals an unplaced whole-file candidate before selection, and a chunk can name an advisory predecessor ([selection](../../../crates/layerfs-storage/src/cas/selection.rs#L28-L155), [selector](../../../crates/layerfs-storage/src/encoding/delta/select.rs#L257-L264)). Exact reuse can demand a group that has no locator yet ([wave](../../../crates/layerfs-storage/src/cas/save.rs#L75-L129)). Those paths must recognize queued groups and flush them before resolving through SQLite. Otherwise this treatment silently loses intra-save delta candidacy or reports a false absence. Preserve the current exact collision comparison and end-of-wave candidate validation. Flush before a lane switch to retain the original cross-lane group/pack-ID order; batching consecutive groups changes how often a pack is written, not which groups it contains or their ordinals. The existing in-place BLOB writer already avoids whole-pack rewrites ([writer](../../../crates/layerfs-storage/src/sqlite/write.rs#L81-L168)); replacing it with a whole-BLOB UPDATE is a regression.

This is a **hypothesis**, not a measured improvement. The unattainable ideal of one write per D11 pack would reduce 7,696 pack-write calls to 1,257 (83.7% fewer); lane switches, 256 KiB flushes, candidate barriers and wave boundaries make the real count higher. The 128-row SQLite cap gives an ideal lower bound of `ceil(24,364/128)=191` object INSERT statements, but the same barriers make the real count higher. D11 has no chronological group-seal trace, so neither attainable count nor wall saving can be inferred from its Store. A cheap first diagnostic should count queue flush reasons, groups per flush, actual pack writes, object INSERTs, and bytes held at peak; no new performance sample is needed to learn whether barriers defeat coalescing. Do not tune workers, cache warmth, transaction/buffer limits or timeout to make it look good.

The public call must fall by **1.064006 s** to reach **0.428571 s**, the time required for 700 decimal MB/s. D11's whole-Save SQL bucket is only **192.313 ms**; simple subtraction would still leave 1.300 s, but that is not a causal floor because workers block behind the bounded channel and may accelerate if C2 does. The worker/owner overlap prevents predicting a call-level speedup from C2 bucket subtraction. C1 and other public-call work still need their own evidence.

## Reject or advance by counts and independent proof

- **Mechanism screen:** with the same 10k object/group geometry, reject this queue if it does not halve both 7,696 pack-write calls and 7,750 object INSERT statements, if queued encoded group bytes exceed 256 KiB, or if simultaneous added queue/increment/row capacity exceeds 1 MiB. Keep created packs, group count, inserted/reused identities, FULL/PREFIX choices and wave COMMIT count visible; a change in them needs a causal explanation before timing is interpreted. This screen is a research decision threshold, not a release gate.
- **Matched public time:** only if the count screen passes, take one control and one treatment public Init sample with separate fresh outputs, exact binary/source/harness seals and independently checked cold source before each call. Retain both outcomes, including failures. Compare complete caller time, process CPU, measured peak resident memory and command wall; never select a repeat of either arm.
- **Integrity and space:** reopen each Store and read every file's path, kind, metadata, size and SHA-256 against the manifest in a separate proof. Record SQLite page size **4,096**, Store apparent/allocated bytes, pack capacity/used/slack, group/pack distribution and roots. Reject if treatment regresses dense Store geometry or reopened readback. Independently run the [#229 sparse-history guardrail](sparse-pack.md) with matched advisory/depth settings and full readback; dense Init compactness cannot stand in for that lane. A timed improvement with skipped verification remains diagnostic until the frozen final-source proof passes.

No production optimization was implemented in this note, and no D11 receipt was altered.
