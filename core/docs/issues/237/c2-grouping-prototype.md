# #237: C2 adjacent-group batching feasibility

> **Status:** Research; informative and not a product contract. Source inspection only, 2026-09-23. No product edit, build, or timed sample was made for this candidate.

## Proposed mechanism and decision

The proposed treatment was to collect consecutive sealed groups from one lane, bounded to one 256 KiB ordinary pack, and call the existing `LanePlacement::select_many` once with the collected groups. This would reduce pack BLOB writes and object-row `INSERT` calls without changing the 4 KiB SQLite page size, group framing, worker count, transaction cadence, or cache state. The retained D11 10k diagnostic counted 7,696 group placements, 1,257 pack creations, 6,439 pack appends, and 7,750 object-row statements ([analysis](c2-grouping-10k.md)). Those counts motivated the idea; they are not a time prediction.

**Decision: stop this prototype before measurement.** The current ordinary/native `seal_group` is also the operation that publishes a group's locator rows. Calling `select_many` with several groups requires delaying that publication across multiple seals. The existing callers consume the rows and their stored bytes during the same save. A local change to the placement call cannot preserve those behaviors. This is an implementation-feasibility rejection, not evidence that correct deferred grouping would be slow.

## The barriers found in source

| Boundary | Existing guarantee | Effect of queuing a sealed group |
| --- | --- | --- |
| [`seal_group`](../../../crates/layerfs-storage/src/cas/placement.rs) | Frames one group, calls `select_many(vec![group])`, writes the pack and locator rows, updates `Availability` and `sealed_rows`, then acknowledges the step when outside a wave. | A queued group has no locator, and `sealed_rows` would no longer mean that its SQLite row exists. The write and row insertion would have to move together into a later flush. |
| [`flush_wave`](../../../crates/layerfs-storage/src/cas/save.rs) | The membership snapshot predates this wave. If an identity appears later in the wave, `sealed_rows` leads to a SQLite lookup and exact byte comparison. `wave_rows` contains every row written for one collision validation before the wave ends. | The lookup must force a queue flush; recording a queued identity as sealed without flushing produces `Integrity("sealed identity has no row")` or a false duplicate admission. The queue must also drain before wave validation and COMMIT. |
| [`pending_base_for`](../../../crates/layerfs-storage/src/cas/selection.rs) and [delta selection](../../../crates/layerfs-storage/src/encoding/delta/select.rs) | A whole-file predecessor or winner-cache candidate is placed before the dependent is selected; a chunk can use an advisory predecessor. | Candidate acquisition must detect IDs in the queued groups and flush before reading. Otherwise a valid same-save base may silently select FULL or fail. A queued ID cannot be treated as ordinary `PendingGroup` because its encoded bytes have already been framed and the existing predicate scans only unframed members. |
| [same-save read](../../../crates/layerfs-storage/src/cas/store.rs) | `seal_pending` writes an unfinished group's row before a read resolves it through the Store. | It must also drain any already framed queue holding the requested ID; otherwise the requested object is absent from both `PendingBatch` and SQLite. |
| [wave and publication lifecycle](../../../crates/layerfs-storage/src/cas/lifecycle.rs) | One wave owns one transaction and releases its arbitration lock only after acknowledgment. `finish_inner` seals remaining groups before publication. | A queue cannot cross a wave, reservation step, transaction boundary, or final publication. The placement state, object rows, pack watermark, collision check, and transaction counters must remain in the same acknowledged step. |

The existing [pooled metadata lane](../../../crates/layerfs-storage/src/cas/pool_lane.rs) does call `select_many` with multiple value groups, but it builds all of them from **one leaf** before exposing that leaf's body. It is not a reusable queue for ordinary groups admitted across separate objects and waves. The ordinary group target is 48 KiB, the ordinary pack limit 256 KiB, and the wave canonical byte limit 4 MiB minus one byte ([policy](../../../crates/layerfs-storage/src/policy.rs)); retaining encoded groups, returned increments, and locator rows simultaneously would also need an explicit additive memory bound.

A correct implementation would need a new bounded intermediate state and changes to placement, save membership/reuse, selection, same-save read, and wave/final flush boundaries. Those are coupled behavior changes, so a small placement-only prototype would provide misleading benchmark evidence. No control or treatment arm was run. No receipt was discarded. The D11 receipt remains the sole count diagnostic for this hypothesis; its zero-resident **source payload** check does not prove cold directory metadata, and its verifier was skipped. Further C2 work should start with a separately scoped semantic design and tests for these barriers, then preregister one matched 10k cold-source pair. It should not infer a speedup from D11's SQL or placement buckets.
