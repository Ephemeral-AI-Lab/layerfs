# #237: next count-driven 10k file-ingest experiment

> **Status:** Research; informative and not a product contract.
> Read-only handoff, 2026-09-23. No product, harness, Store or receipt changed for this note; no sample taken. Only the 10,000-file public native Init is considered. All quoted times are one observation from the retained D9 release diagnostic, not a distribution or an admitted cold result.

## Observed bound and 700 MB/s arithmetic

D9 uses a sealed release binary on the 10,000-file, 300,000,000-B source. Its independent whole-source preflight and immediately preceding nonfaulting recheck each saw **0 resident pages / 27,503 pages**, with a **1.061 ms** recheck-to-timer gap; the official receipt nevertheless retains `source-cache-uncontrolled-v1`, `admission_eligible=false`, and verification `SKIPPED` ([receipt](../../../../docs/roadmap/0.1/0.1.7/evidence/issue237-native-init-research/raw/d9-release-fast/daemon-host/init_namespace/namespace-10000/receipt.json), [recheck](../../../../docs/roadmap/0.1/0.1.7/evidence/issue237-native-init-research/raw/d9-release-fast/daemon-host/init_namespace/namespace-10000/cold-recheck.json), [launch](../../../../docs/roadmap/0.1/0.1.7/evidence/issue237-native-init-research/raw/d9-release-fast/daemon-host/init_namespace/namespace-10000/cold-launch.json)). Caller Init is **1.590847333 s** (188.58 decimal MB/s); `history.import_files` is **1.249613667 s**, while every other caller cost is **0.341233666 s**. The Service root is 1.590233583 s; its named children leave **0.257326459 s unnamed**, principally around the unwrapped C1 build. The file span itself includes four constructors, their eight-object channel, and one C2 save owner ([source](../../../crates/layerfs-service/src/operation/import_native.rs#L143-L229)).

For 700 decimal MB/s, `300,000,000 / 700,000,000 = 0.428571429 s`. D9 exceeds that by **1.162275904 s**. If all other caller work stayed at 0.341233666 s, file ingest would have only **0.087337763 s**, a **93.0%** reduction from D9's file span. Even if all other work vanished, file ingest alone would need a **65.7%** reduction to fit 0.428571429 s. This is why an ingest-only micro-optimization cannot be called a 700 MB/s solution without a measured result; C1 and the other caller work also need attention.

The Service caller window reports **1.094231 s user + 1.057509 s system CPU** (2.151740 s total, process shared) and **58,458,112 B sampled maximum RSS**. These are not exact file-phase CPU or a complete phase-local RSS peak: the local monitor sampled 17 times with an approximately 105 ms maximum gap and did not cover both timing boundaries ([receipt `m2_local_roots`](../../../../docs/roadmap/0.1/0.1.7/evidence/issue237-native-init-research/raw/d9-release-fast/daemon-host/init_namespace/namespace-10000/receipt.json)). Logical source input is 300 MB, but D9 does not report actual device-read bytes. Its Store has **24,683 objects** and **334,184,448 B apparent** at SQLite `page_size=4096`; **24,364 objects** and **1,259 packs** belong to the file save. Pack BLOB capacity is **331,350,016 B** and assembled pack bytes are **305,977,888 B** (25,372,128 B spare). These are final space facts, not bytes written by the OS or a #229 sparse-history compactness proof ([D9 geometry](../../../../docs/roadmap/0.1/0.1.7/evidence/issue237-native-init-research/raw/d9-release-fast/store_geometry.json)). A read-only `SELECT count(*) FROM (SELECT pack_id,group_number FROM objects WHERE save_id=1 GROUP BY pack_id,group_number)` on D9's retained Store returns **7,706 file-save groups**; the grouping is one C2 `seal_group`/pack write per group, so it exposes thousands of serialized pack/locator operations ([seal](../../../crates/layerfs-storage/src/cas/placement.rs#L106-L220), [pack write](../../../crates/layerfs-storage/src/cas/placement.rs#L225-L278)). Their wall cost is not published by D9.

The fixture's source-defined sizes are 100 empty files, 7,899 tiny files of 325–326 B, 1,500 small files of 20,782 B, 500 medium files of 332,506 B, and one 100 MB anchor ([fixture planner](../../../benchmark/fs-bench-pro/families/init_namespace.py#L28-L59)). The Store's file-save roles agree: **9,399 whole-file**, **13,920 chunk**, and **1,045 file mapping/state** objects. These counts explain why bytes alone are not a cost model: the worker opens and validates 10,000 files, and the C2 owner accepts 24,364 file-save objects. A structural avoidable operation is visible in the shared streaming constructor: it requests **131,072 B prefix capacity for every file before reading any byte** at the default cutoff ([constructor](../../../crates/layerfs-content/src/file/content.rs#L279-L316), [default cutoff](../../../crates/layerfs-content/src/policy.rs#L13-L21)). That is **1,310,720,000 B of cumulative capacity requests** across this fixture, although at most four workers have live probes at once. The request is bounded in live memory, and its actual allocator/kernel time is **not measured**. It is a plausible small-code treatment, not evidence of a 1.162 s saving.

## D11: one diagnostic identity, then one conditional treatment

On one new, explicitly labelled **release-profile diagnostic** at the same public route, fixture, four workers, channel capacity eight, cold-source preflight, deadline and 4 KiB SQLite page size, publish only aggregate counters. Per worker: job count, `construct_file` wall, source read calls/bytes, prefix-reserve call count/requested bytes/elapsed time (and peak actual capacity), and `ChannelConsumer::accept` object-send count/wall. Count and time `Done` sends separately. On the receiver: `recv_timeout` idle count/wall, `handoff.accept` count/wall, and the completed file `SaveOutcome` counts plus its existing seven `SaveProfile` buckets and nested `DiagProfile` totals ([worker/receiver](../../../crates/layerfs-service/src/operation/import_native.rs#L143-L229), [profile](../../../crates/layerfs-storage/src/cas/owner.rs#L39-L92), [outcome](../../../crates/layerfs-storage/src/cas/store.rs#L24-L81)). Emit one summary per worker and one owner summary; no per-object telemetry. The worker totals overlap each other and the owner, so never add them into a fictitious phase time. A blocked send can mean the C2 owner is busy; it is not automatically removable channel overhead.

If prefix allocation has a material measured charge, the smallest treatment is to start `construct_stream`'s prefix at `min(cutoff, 4096)` capacity and let its existing bounded read grow only for files that need it. Keep the same read limit, CDC partition, source-stability checks, object IDs and four workers; check peak `Vec` capacity under every accepted power-of-two cutoff before claiming the old memory bound. If receiver accept and C2 profile dominate instead, use that profile to select one exact serial call site (group seal, pack write, locator insert, commit or codec) and first prove its count and microseconds per call. The existing 512-object/4 MiB C2 waves and in-place BLOB append already avoid the obvious per-object transaction and whole-pack rewrite ([batch](../../../crates/layerfs-storage/src/cas/batch.rs#L13-L67), [in-place write](../../../crates/layerfs-storage/src/sqlite/write.rs#L81-L168)); widening limits or changing page size is not a treatment. A faster candidate needs a separately registered release control/treatment pair, one public Init sample per arm, full reopened readback outside the performance timer, and no worse dense Store geometry or #229 sparse-history lane ([space guardrail](sparse-pack.md#minimum-prospective-controltreatment-check-for-an-init-change)).
