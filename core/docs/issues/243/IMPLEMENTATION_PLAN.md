# #243 Generic Workspace shell rollout plan

> **Status:** Current planning checklist; no release candidate exists.

Parent: [#232](https://github.com/Ephemeral-AI-Lab/layerfs/issues/232). This is the rollout plan for the separately registered **Workspace filesystem workflow** requested in [#243](https://github.com/Ephemeral-AI-Lab/layerfs/issues/243). It authorizes no product change, benchmark collection, or performance claim. The public method is `WorkspaceApi::exec(command)`, which runs `/bin/sh -c` in the mounted Workspace; “Workspace shell” names the product workflow, not another SDK method. Ordinary commands reach FUSE through the POSIX operations they actually issue.

The prior [route correction](../232/SHELL_ROUTE_CORRECTION.md) and [POSIX count diagnostic](../232/evidence/posix-count-diagnostic/REPORT.md) are evidence for planning. The 56-case [ioctl campaign](../232/evidence/phase2-all-ioctl/REPORT.md) remains historical opt-in evidence. Its receipts, registries, and targets are immutable; no ioctl PASS becomes a generic-shell PASS. This workflow is **not** an SDK range-edit family: [benchmark rules §2](../../../../docs/general/benchmark_rules.md#2-measure-the-authentic-operation) require a separately registered filesystem/Workspace scenario with its own operation surface, counters, schema, and admission claim.

## Target and route

```text
prepared Workspace + immutable replacement fixture
  -> public SDK Project/Branch/Sandbox/Workspace lifecycle
  -> WorkspaceApi::exec(ordinary shell command)
  -> /bin/sh -c -> CREATE / WRITE / SETATTR / RENAME / UNLINK / READ
  -> mounted FUSE -> private Workspace overlay
  -> one explicit WorkspaceApi::commit -> new Branch head
  -> independent read-only Store/history verifier and cleanup
```

The [test-workspace specification](TEST_WORKSPACE_AND_COMMANDS.md) owns exact package names, bytes, commands, and oracles. Its mixed three-package refresh is an integration case, alongside **separate** focused cases for one-byte/4 KiB positional overwrite, append/truncate, in-place insert/delete, repeated small writes, and command failure before Commit. A package refresh cannot silently substitute for #232's 56 registered edit shapes. Before claiming #232 completion, prospectively amend its scenario to state which of those shapes remain required under ordinary POSIX commands, the selected command algorithm for each, and which new package cases are additional. A temp-file/rename command is a different algorithm from an in-place suffix shift even if the final bytes match.

## Causal checks and limits

The retained v2 POSIX shift commands copy the suffix through FUSE; eleven failed cases exceed the **8 MiB** existing-file replay bound by source/registry derivation, although their observed outcome was the **five-second silent Exec `Unknown`** first. At the capped-500 MiB size, a new temp-file stream would require at least **4,000** 128 KiB FUSE writes against the present **1,024-piece** index ceiling. These are structural findings, not new timed failures. The [source-level study](../232/generic-shell-edit-and-commit-design.md) and [retained count receipt](../232/evidence/posix-count-diagnostic/REPORT.md) explain the current full-list work. A shell program that itself moves a large suffix still requests those bytes; the product can remove extra metadata work and make bounded completion possible, but cannot infer a one-call insertion from generic WRITE callbacks.

For each candidate, record the actual FUSE READ/WRITE/SETATTR/CREATE/RENAME/UNLINK counts and bytes, forbidden ioctl count, old/new pieces, cumulative index visits and pages written, replacement/spool/Store bytes, construction worker count, and failure location. Count-driven diagnostics may be separately labelled and retained, but must not replace or rerun a performance arm. For Commit, distinguish final drain from save-wide nested totals; never add overlapping LFT1 scopes or assign an earlier flush to final drain. For Exec, identify progress across an in-flight POSIX callback rather than increasing the deadline to make a miss pass.

## Measurement, verification, and custody

- Follow [repository rules](../../../../AGENTS.md), [Core rules](../../../AGENTS.md), [Core benchmark rules](../../../benchmark/fs-bench-pro/AGENTS.md), and [general benchmark rules](../../../../docs/general/benchmark_rules.md). One sample per case per arm; no best-of, unchanged-arm resampling, timeout inflation, worker increase, cache priming, or dropped failure.
- A reused master must be a validated, closed, independent **writable byte copy** (`--setup clone` where supported); record the copy method. Build/image reuse is sealed and explicit. A clone is not a cold-cache claim. Freeze and enforce an equal cache contract for both arms, including input and Edit-written FUSE/Store backing. Do not move eviction or product work outside the timer to manufacture a cold row; if relevant residency cannot be qualified, numeric latency is `INELIGIBLE`. Never pool warm and cold rows.
- Public SDK calls own Project/Branch/Sandbox/Workspace lifecycle, Exec, Commit, Status, Unmount and Delete. The verifier uses a separate identity-matched read-only path to check complete final-tree paths, lengths, modes and hashes, removed paths, the new Branch head, and the unchanged old Commit. The failed-command case checks that no Commit was issued and the Branch head stayed unchanged; do not assume Exec failure automatically rolls back private Workspace mutations.
- Freeze budgets prospectively. The repository default is a complete performance command **≤15 s**, with only a declared small exception list up to **25 s**; independent verification is **under 10 s**. If a case cannot fit, retain its actual outcome or mark `NOT_RUN` with reason—never shorten the command, move timed work into setup, or raise the bound after seeing a result. Construction uses one worker for this non-Init family.
- Keep raw outputs, receipts, hashes, source/build/image/tool identities, failures, cache qualification, and exact reproduction commands in fresh append-only paths. Record product-only LOC before/after/delta for **each commit**; migration subtotals remain separate. Run focused tests for changed modules and final Core `cargo +1.85.1 test/clippy/fmt --manifest-path core/Cargo.toml --locked`, `core/tools/check_product_boundary.py`, and its self-tests before claiming implementation verification. Report gaps exactly; there is no CI or aggregate preflight gate.
